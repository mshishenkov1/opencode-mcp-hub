| **N5-B1** | `--version` валидируется регулярным выражением `^[0-9]+\.[0-9]+\.[0-9]+-magnit\.[0-9]+$` (иначе код `2`); строковые значения, попадающие в манифест, экранируются в JSON | находка 7 (minor) |
| **N5-I5**, **N5-U1** | Задвоенный маркированный блок профиля схлопывается в один; предупреждение о чужом `NODE_EXTRA_CA_CERTS` выдаётся только на присваивание, не на комментарий или упоминание | находки 8 и 9 (minor) |

Новые критерии приёмки: **AC-135** (небезопасный `app_name`/`install_name` → код `2`, ни одной
файловой операции — для установки, `--uninstall` и `--dry-run --uninstall`), **AC-136** (три ветки
`Invoke-Uninstall` на Windows), **AC-137** (провал деинсталлятора Desktop → код выхода `1`).
Набор стал AC-01…AC-137.

Документация: `install-admin.md` §3 — строка про удаление Desktop приведена к фактическому
поведению; `install-user.md` — уточнение про Desktop в разделе «Как удалить».

## 1. Назначение

Итерация I-5 даёт то, что пользователь скачивает с портала и запускает:

1. **пакет на ОС/архитектуру** — корпоративная сборка OpenCode (CLI/TUI), корпоративный CA-bundle,
   при наличии — Desktop-установщик, манифест с хешами и установщик;
2. **установщик** (`install.sh` для macOS/Linux, `install.ps1` + `install.bat` для Windows) —
   ставит CA, бинарник в PATH, Desktop; ничего не спрашивает, ключей не просит, пользовательский
   конфиг не меняет; идемпотентен; умеет `--dry-run`, `--check`, `--uninstall`, `--purge`;
3. **`installers/release.sh`** — сборка пакетов из готовых артефактов CI форка;
4. **документацию** для пользователя и для администратора.

Отдельным разделом (§11) идёт бэклог Hub по `reports/review-i3-2.json` — правила `H5-*`. Они
**реализуются в репозитории Hub, в ветке от `pipeline/i3-hub-oauth-facade-proxy`** (I-3+), к
установщикам отношения не имеют и в общий набор AC I-5 не смешиваются (для них — отдельный раздел
`hub_backlog_criteria` с идентификаторами `HAC-*`).

### 1.1. Границы объёма

**Входит:** структура пакета и манифест; установщики трёх ОС; идемпотентность/обновление/откат;
удаление; `--dry-run`/`--check`; `release.sh`; тесты bats/Pester; эталонный файл CI; документация RU.

**Не входит:**
- скачивание артефактов из сети — установщик и `release.sh` работают только с локальными файлами
  (N5-P6, N5-B5); сборка форка (`bun run corp/build.ts`) — предмет I-4;
- подпись Windows Authenticode и macOS Developer ID / notarization — решение ИБ (R-14, D-7, S-B9);
  вместо подписи — документированный обход предупреждений ОС (N5-D1), только для пилота;
- `.pkg` для macOS (в I5-01 помечен как опциональный) — не делаем, ставим бинарник напрямую;
- Desktop для Linux — форк его не собирает (S-B3: цели `mac-arm64` и `win-x64`);
- импорт CA в системное хранилище сертификатов ОС (это изменение системных настроек, требует
  прав администратора и согласования ИБ) — ставится только пользовательская копия CA и
  пользовательская переменная окружения;
- интеграция с порталом (карточка загрузок, автообновление) — ручная выкладка AI Lab, D-8;
- параметры корпоративной сборки Desktop, кроме имени бандла: `appId` (`ai.opencode.desktop.magnit`)
  и адрес внутреннего сервера автообновления (задаётся переменной сборки; без неё апдейтер
  выключен) — предмет сборки форка, установщики их не читают и не пишут. Из переименования в объём
  I-5 входит **только** имя бандла `OpenCode Magnit.app` (N5-I9, N5-P3).

## 2. Входы и выходы

**Входы установщика:** каталог распакованного пакета (см. N5-P2) рядом со скриптом; аргументы
командной строки (N5-I1); окружение пользователя (`$HOME`, `$SHELL`, `XDG_CONFIG_HOME`,
`%USERPROFILE%`, `%LOCALAPPDATA%`, `PATH`, `NODE_EXTRA_CA_CERTS`); при `--system` — дополнительно
`SUDO_USER`, вывод `logname` и запись базы пользователей об исходном пользователе (N5-I14).

**Выходы установщика:** файлы в домашнем каталоге пользователя и (при `--system`) в `/usr/local/bin`;
маркированный блок в файле профиля shell; пользовательские переменные окружения Windows; строки
отчёта в stdout, ошибки в stderr; код выхода (N5-I1).

**Входы `release.sh`:** локальный каталог с артефактами CI форка; версия; CA-файл; адрес Hub.
**Выходы `release.sh`:** архивы `opencode-magnit-<os>-<arch>-<ver>.tar.gz|zip`, `SHA256SUMS`.

## 3. Правила: пакет, манифест, репозиторий (N5-P*)

- **N5-P1. Состав каталога `installers/` в репозитории.** Обязательные пути:

  | Путь | Назначение |
  |---|---|
  | `installers/common/install-posix.sh` | единственная реализация установщика для macOS и Linux |
  | `installers/common/manifest.schema.json` | JSON-схема манифеста (N5-P3), используется тестами |
  | `installers/common/manifest.example.json` | пример заполненного манифеста |
  | `installers/macos/install.sh` | лончер: определяет свой каталог и передаёт управление `install-posix.sh` |
  | `installers/linux/install.sh` | то же для Linux |
  | `installers/windows/install.ps1` | установщик для Windows |
  | `installers/windows/install.bat` | тонкий лончер PowerShell (N5-I2) |
  | `installers/release.sh` | сборка пакетов (N5-B1) |
  | `installers/ci/installers.yml` | эталонный workflow CI (N5-T4) |
  | `installers/docs/spec.md`, `installers/docs/acceptance-criteria.yaml` | эта спецификация и AC |
  | `installers/docs/install-user.md`, `installers/docs/install-admin.md` | документация (N5-D1, N5-D2) |
  | `installers/tests/bats/` | тесты bats (N5-T1) |
  | `installers/tests/pester/` | тесты Pester (N5-T2) |
  | `installers/tests/fixtures/` | фикстуры: искусственные пакеты и манифесты |

  Логика установки для macOS и Linux не дублируется: `macos/install.sh` и `linux/install.sh`
  содержат только определение собственного каталога, установку `OPENCODE_INSTALLER_PLATFORM`
  (`macos`/`linux`) и вызов общего файла. Расхождения поведения между ОС выражаются внутри
  `install-posix.sh` ветвлением по этой переменной, а не двумя копиями скрипта.

- **N5-P2. Состав распространяемого пакета.** Пакет, который пользователь скачивает и распаковывает,
  самодостаточен: после распаковки установка выполняется без обращений к репозиторию, сети и
  внешним утилитам сверх базовых (N5-P6, N5-I3). Раскладка:

  ```
  opencode-magnit-<os>-<arch>-<ver>/
  ├── install.sh                (macOS/Linux; исполняемый бит выставлен)
  ├── install.ps1               (Windows)
  ├── install.bat               (Windows)
  ├── common/
  │   ├── manifest.json
  │   └── install-posix.sh      (только в POSIX-пакетах)
  ├── bin/
  │   └── opencode | opencode.exe
  ├── certs/
  │   └── tander-ca-bundle.pem
  ├── desktop/                  (только если Desktop входит в пакет)
  │   └── <штатный установщик Desktop>
  └── README.md                 (N5-D3)
  ```

  В POSIX-пакет кладутся только `install.sh` + `common/install-posix.sh`, в Windows-пакет —
  только `install.ps1` + `install.bat`. Установщик находит `common/manifest.json` относительно
  каталога, в котором лежит он сам, а не относительно текущего рабочего каталога: запуск из любого
  каталога (`bash /path/to/pkg/install.sh`) работает одинаково.

- **N5-P3. `manifest.json`.** Единственный источник правды о содержимом пакета. Поля:

  | Поле | Тип | Обязательное | Смысл |
  |---|---|---|---|
  | `schema` | целое | да | версия схемы, для I-5 ровно `1` |
  | `product` | строка | да | ровно `opencode-magnit` |
  | `version` | строка | да | версия сборки, формат `<upstream>-magnit.<N>` (S-B1), например `1.17.9-magnit.1` |
  | `os` | строка | да | `darwin` \| `linux` \| `windows` |
  | `arch` | строка | да | `arm64` \| `x64` |
  | `hub_url` | строка | да | адрес Hub, печатается в отчёте и в `--check`; установщик его никуда не записывает (адрес зашит в сборку, S-C2) |
  | `built_at` | строка | да | момент сборки пакета, ISO-8601 UTC |
  | `source_release` | строка | да | тег релиза форка, из которого взяты артефакты (`v<version>`, S-B4) |
  | `ca` | объект | да | `{file, sha256, install_name}` — CA-bundle |
  | `artifacts` | массив | да | элементы `{kind, file, sha256, size, ...}`, ровно один с `kind:"cli"`, не более одного с `kind:"desktop"` |
  | `purge_paths` | массив строк | да | пути, удаляемые при `--purge` (N5-R2); допускаются подстановки `~`, `${XDG_CONFIG_HOME}`, `${XDG_DATA_HOME}`, `%USERPROFILE%`, `%LOCALAPPDATA%` |

  Элемент `artifacts` с `kind:"cli"` дополнительно содержит `install_name` (`opencode` или
  `opencode.exe`). Элемент с `kind:"desktop"` дополнительно содержит `installer_type`
  (`dmg` \| `nsis` \| `msi`), `app_name` (**обязательно и непусто** при `installer_type:"dmg"`,
  для корпоративной сборки — `OpenCode Magnit.app`, ревизия 1.5) и для Windows — `silent_args`
  (массив строк, например `["/S"]`).

  Все `file` — пути относительно корня пакета, с разделителем `/`, без ведущего `/`, без `..` и без
  букв дисков. Те же ограничения действуют на `ca.install_name`, `artifacts[].install_name` и
  `artifacts[].app_name`: в схеме все пять полей используют одно определение `pkgPath`. В
  установщике `app_name` дополнительно проходит **более строгую** проверку, чем прочие четыре поля
  (ревизия 1.2): это имя приложения, а не путь внутри пакета, и оно обязано быть непустым после
  отбрасывания пробельных символов (ревизия 1.4) — полный список и обоснование см. N5-P4.

  **Набор допустимых символов (ревизия 1.5).** Значения `ca.install_name`,
  `artifacts[].install_name` и `artifacts[].app_name` попадают не только в файловые операции, но и
  в **генерируемый код** файла профиля (N5-I5, N5-I13), поэтому они ограничены белым списком:
  латинские буквы `A-Za-z`, цифры `0-9`, точка, подчёркивание, дефис и — только для путей внутри
  пакета — разделитель `/`; для `app_name` дополнительно допускается пробел `U+0020`, но не первым
  и не последним символом. Любой другой байт делает манифест невалидным (N5-P4). Ограничение
  распространяется только на эти три поля: `purge_paths` содержит шаблоны `~`, `${XDG_CONFIG_HOME}`
  и `%USERPROFILE%` по определению (N5-R2), а `hub_url`, `version` и прочие строки в код оболочки
  не подставляются — они только печатаются в отчёте. Поле `url` в элементе `artifacts` допускается (I5-01) и является исключительно справочным:
  установщик его никогда не запрашивает (N5-P6).

- **N5-P4. Валидация манифеста.** До любых изменений системы установщик читает и проверяет манифест:
  файл существует и разбирается как JSON; `schema == 1`; `product == "opencode-magnit"`; все
  обязательные поля присутствуют и непусты; `os`/`arch` — из допустимых значений; каждый `sha256` —
  ровно 64 символа `[0-9a-f]` (сравнение регистронезависимое, значение приводится к нижнему
  регистру); каждое путевое поле проходит проверку пути, а каждый `file` дополнительно существует
  внутри пакета; ровно один артефакт `kind:"cli"`. Любое нарушение → ничего не изменено, сообщение
  с именем поля и путём к манифесту в stderr, код выхода `2`. То же для отсутствующего манифеста.

  **Путевые поля — полный список (уточнено в ревизии 1.2).** Проверка пути (`is_safe_pkg_path` в
  `install-posix.sh`, `Test-PackagePath` в `install.ps1`) применяется ко **всем** полям манифеста,
  значение которых участвует в построении файловых путей:

  | Поле | Проверка | Дополнительно |
  |---|---|---|
  | `ca.file` | путь внутри пакета | файл существует внутри пакета |
  | `ca.install_name` | путь внутри пакета | — |
  | `artifacts[].file` | путь внутри пакета | файл существует внутри пакета |
  | `artifacts[].install_name` (для `kind:"cli"`) | путь внутри пакета | обязательно и непусто |
  | `artifacts[].app_name` (для `kind:"desktop"`) | **имя приложения** (строже) | **обязательно и непусто при `installer_type:"dmg"`**; при прочих `installer_type` — проверяется, если задано |

  Проверка пути внутри пакета (`is_safe_pkg_path` / `Test-PackagePath`) запрещает: `..` как
  отдельный сегмент (`..`, `../*`, `*/../*`, `*/..`), ведущий `/`, обратный слэш `\` в любой
  позиции, префикс с буквой диска (`C:`), пустое значение, а также (ревизия 1.2) формы, при которых
  `<каталог>/<значение>` схлопывается в сам каталог: `.`, `./x`, `x/.` и завершающий `/`.

  **Белый список символов (ревизия 1.5).** Дополнительно значение обязано целиком состоять из
  символов `A-Za-z0-9._-` и разделителей `/` (для `app_name` — без `/`, но с пробелом, см. ниже).
  Проверка сформулирована как **белый список**, а не как перечень запрещённого: перечислять
  метасимволы поимённо — значит гарантированно что-то забыть, а забытый символ снова попадает в
  генерируемый код профиля. Отвергаются, в частности: `$`, `` ` ``, `"`, `'`, `\`, `;`, `&`, `|`,
  `<`, `>`, `(`, `)`, `{`, `}`, `[`, `]`, `*`, `?`, `!`, `#`, `~`, `%`, `:`, `=`, `,`, `^`, `@`,
  `+`, пробел (кроме `app_name`), символы перевода строки, возврата каретки и табуляции, любой
  управляющий символ `< 0x20`, байт `0x7f` и любой байт `>= 0x80` (не-ASCII). Обе платформы
  применяют один и тот же набор: то, что принято на macOS/Linux, обязано быть принято и на
  Windows, и наоборот (посегментное сравнение, замечание ревью о расхождении `..` внутри сегмента).

  Значение с любым из этих символов делает манифест невалидным: сообщение называет поле, код выхода
  `2`, ни одной файловой операции, ни одной строки в файле профиля. Установка с таким `install_name`
  **не может** завершиться кодом `0` (N5-I13).

  **JSON-экранирование `\uXXXX` (ревизия 1.5.1).** Набор принимаемых манифестов одинаков на обеих
  платформах, поэтому вердикт выносится по **строке**, а не по её записи в файле: escape-запись
  `\uXXXX` разбирается по кодовой точке. `"\u0074ander-ca-bundle.pem"` — корректная по RFC 8259
  запись строки `tander-ca-bundle.pem`, и такой манифест обязан приниматься и на POSIX, и на
  Windows, где разбор выполняет `ConvertFrom-Json`. Декодируются кодовые точки диапазона
  `0x20`–`0x7e` (печатный ASCII) — ровно те, что вообще могут оказаться разрешёнными белым списком.
  Любая другая кодовая точка (`\u0000`–`\u001f`, `\u007f`, всё `>= 0x80`), а также запись без
  четырёх шестнадцатеричных цифр и короткие escape-последовательности `\n`, `\t`, `\r`, `\b`,
  `\f` заменяются маркером управляющего символа — байтом, запрещённым во **всех** путевых полях,
  то есть дают код `2` с именем поля.

  Декодирование не «отмывает» запрещённый символ в разрешённый: результат подаётся в белый список
  как есть, единственное место, где задан допустимый набор символов, — там же. Поэтому
  `"\u0024pwn.pem"` отвергается кодом `2` как `$pwn.pem` (сообщение называет поле и декодированное
  значение), а `"\u0020"` внутри `app_name` — это обычный пробел, допустимый по правилу о пробеле
  в имени приложения ниже.

  Проверка имени приложения (`is_safe_app_name` / `Test-AppName`, ревизия 1.2) строже: значение
  обязано быть **ровно одним именем каталога** — оно проходит проверку пути внутри пакета и
  дополнительно не содержит разделителей `/` и `\`, не равно `.` или `..`, а на Windows не
  содержит подстановочных символов `*`, `?`, `[`, `]` (они участвовали бы в сопоставлении записей
  реестра, см. N5-R1).

  **Пробел в имени приложения (ревизия 1.5).** `app_name` — единственное из трёх полей, где
  допускается пробел `U+0020`: корпоративный бандл называется `OpenCode Magnit.app`. Пробел не
  может быть первым или последним символом значения (`" OpenCode Magnit.app"`,
  `"OpenCode Magnit.app "` → код `2`), два пробела подряд не запрещены, но и не используются.
  Пробел безопасен именно здесь: `app_name` в генерируемый код оболочки не попадает (в блок профиля
  идут только `ca_target` и `bin_dir`), а все подстановки имени в `ditto`, `rm -rf`, `hdiutil` и в
  сопоставление записей реестра выполняются одним закавыченным аргументом и по расщеплению по
  пробелу не разъезжаются (AC-154).

  **Пробельное имя (ревизия 1.4).** Значение, пустое после отбрасывания пробельных символов
  (`"   "`, `"\t\n "`), отвергает и `is_safe_app_name`, и `Test-AppName` — не только первая линия
  проверок в `manifest_load`. Требование сформулировано так намеренно: вторая линия защиты
  (`desktop_target_path`, `find_installed_desktop`) обязана быть не слабее первой, иначе при
  обойдённой или изменённой загрузке манифеста имя `"   "` дошло бы до `"<каталог назначения>/   "`
  и до `ditto`/`rm`. Обязательность поля для `installer_type:"dmg"` остаётся отдельным требованием
  (см. ниже) — проверка имени и проверка обязательности не подменяют друг друга. Обе платформы
  ведут себя одинаково: заявленный в `install.ps1` паритет с `Test-AppName` (`IsNullOrWhiteSpace`)
  стал истинным.

  **Обязательность `app_name` для `dmg` (ревизия 1.2).** Если у артефакта `kind:"desktop"` задан
  `installer_type:"dmg"`, поле `artifacts[].app_name` обязательно и непусто; значение, состоящее из
  одних пробельных символов, равносильно пустому. Нарушение → сообщение с именем поля
  `artifacts.<i>.app_name` и код выхода `2`, выдаваемые в `manifest_load`, то есть **до любой
  файловой операции** — на установке, `--check`, `--dry-run`, `--uninstall`, `--purge` и любых их
  комбинациях. Пустое значение не «подставляется по умолчанию» и не игнорируется: манифест
  признаётся невалидным целиком.

  **Момент проверки.** Вся валидация выполняется внутри `manifest_load` — то есть на шаге (2)
  порядка N5-I3 (разбор аргументов → манифест → ОС/архитектура → …), **до любой файловой операции**
  и до выбора режима. Поэтому она одинаково срабатывает на всех путях исполнения: установка,
  `--check`, `--dry-run`, **`--uninstall`** и **`--dry-run --uninstall`**. Ни один режим не имеет
  «облегчённой» загрузки манифеста; в частности, `--uninstall` не является исключением, хотя
  проверка хешей (N5-P5) на нём не выполняется.

  > **Исправление уязвимости №1 (ревизия 1.1).** До ревизии 1.1 поле `artifacts[].app_name` было
  > единственной строкой манифеста, участвующей в файловых операциях и не проходящей проверку пути.
  > Оно подставляется в `rm -rf "<dest>/<app_name>"` при установке Desktop и в удаление
  > `/Applications/<app_name>` при `--uninstall`, поэтому подменённый манифест со значением вида
  > `../../<абсолютный путь>/victim` удалял произвольный каталог вне `/Applications`, а при
  > `--system` — от имени `root` через `sudo`. Требование: такое значение отвергается кодом `2` до
  > любых изменений системы, каталог-жертва остаётся нетронутым (AC-135). Схема
  > `common/manifest.schema.json` — вторая линия защиты: `app_name` использует то же определение
  > `pkgPath`, что `file` и `install_name`.

  > **Исправление уязвимости №2 (ревизия 1.2).** Проверка ревизии 1.1 срабатывала только для
  > **заданного** `app_name`: отсутствующее, пустое или пробельное значение считалось «поле не
  > задано» и пропускалось. При `installer_type:"dmg"` шаг установки Desktop подставлял его в
  > `"<каталог назначения>/<app_name>"`, что при пустом значении давало сам каталог назначения:
  > условие «приложение уже установлено» истинно всегда, и выполнялось `rm -rf
  > "<каталог назначения>/"` — то есть удаление **всего** `/Applications` (или `~/Applications`),
  > а при `--system` — от имени `root` через `sudo`. Требование: такой манифест отвергается кодом
  > `2` до любой файловой операции, каталог назначения и всё его содержимое остаются нетронутыми
  > (AC-138).
  >
  > **Вторая линия защиты — `desktop_target_path`.** Независимо от валидации манифеста путь
  > установленного приложения вычисляется отдельной функцией, которая возвращает значение, только
  > если путь лежит **строго внутри** каталога назначения: не равен самому каталогу и не является
  > его родителем. Проверка выполняется до первой файловой операции шага (в том числе до `mkdir`).
  > Отказ означает: при установке Desktop (`install_desktop`) — невалидный манифест, код `2`, ни
  > `rm`, ни `ditto` не выполняются; при поиске установленного приложения для удаления
  > (`find_installed_desktop`) — «Desktop не найден», то есть ни одна файловая операция не
  > выполняется и код выхода `--uninstall` не портится (N5-R3).

- **N5-P5. Обязательная проверка хеша.** Перед копированием/запуском любого файла из пакета
  (CLI-бинарник, CA, Desktop-установщик) установщик вычисляет его sha256 и сравнивает со значением
  из манифеста. Несовпадение → **отказ**: файл не копируется и не запускается, ранее выполненные
  шаги не откатываются, но и не продолжаются; сообщение содержит имя файла, ожидаемый и фактический
  хеш; код выхода `4`. Отключить проверку нельзя — флага «пропустить проверку хеша» не существует.
  Проверка выполняется и в режиме `--dry-run` (это только чтение), поэтому `--dry-run` пригоден как
  валидация целостности пакета.

  Хеш считается первой доступной утилитой из списка: `sha256sum`, `shasum -a 256`,
  `openssl dgst -sha256` (POSIX) и `Get-FileHash -Algorithm SHA256` (Windows). Если на POSIX нет ни
  одной — код выхода `3` с перечислением искомых утилит.

- **N5-P6. Установщик оффлайновый.** Шаги установки, удаления, `--dry-run` и `--check` не выполняют
  ни одного сетевого обращения: в исходниках установщиков нет вызовов `curl`, `wget`, `nc`,
  `Invoke-WebRequest`, `Invoke-RestMethod`, `System.Net.WebClient`, `git`, `npm`, `brew`, `apt`,
  `winget`, `choco`. Отсутствие сети не является ошибкой и не влияет на код выхода. Единственное
  исключение — информационный финальный шаг `opencode corp status` (N5-I12), который сетью
  пользуется, выполняется после всех изменений и на код выхода установщика не влияет.

- **N5-P7. Имена и версия.** Имя каталога и архива пакета —
  `opencode-magnit-<os>-<arch>-<version>`, где `os`/`arch`/`version` берутся из манифеста.
  Расширение: `.tar.gz` для `darwin` и `linux`, `.zip` для `windows` (N5-B2). Версия в имени, версия
  в манифесте и версия, которую печатает установленный бинарник (`opencode --version`), — одно и то
  же значение; расхождение имени архива и манифеста — ошибка сборки пакета (N5-B2), а не установки.

- **N5-P8. CA в пакете.** Файл `certs/tander-ca-bundle.pem` входит в каждый пакет, его sha256 — в
  манифесте (`ca.sha256`), имя устанавливаемого файла — `ca.install_name`
  (по умолчанию `tander-ca-bundle.pem`). Содержимое CA установщик не разбирает и не проверяет на
  валидность сертификатов — только целостность по хешу.

- **N5-P9. Единая нормализация путей (ревизия 1.4).** Проверка безопасности пути обязана
  выполняться над тем же значением, которое затем попадёт в файловую операцию. Ядро нормализует
  путь само (`//` эквивалентно `/`, `/./` эквивалентно `/`, завершающий разделитель
  отбрасывается), поэтому сравнение **сырых строк** обходится эквивалентной записью того же пути —
  именно так были устроены уязвимости №2 и №3. Правило: **каждый** путь до первой файловой операции
  проходит через одну функцию нормализации — `path_normalize` в `install-posix.sh`,
  `ConvertTo-NormalPath` в `install.ps1`, — и все дальнейшие проверки, сообщения и операции ведутся
  только над её результатом.

  Нормализация выполняет ровно следующее:

  | Вход | Поведение |
  |---|---|
  | ведущие `~` и `~/` (POSIX), шаблоны `${HOME}`, `${XDG_CONFIG_HOME}`, `${XDG_DATA_HOME}`, `%USERPROFILE%`, `%LOCALAPPDATA%` в `purge_paths` | разворачиваются в фактические значения **до** нормализации |
  | повторяющиеся разделители (`//`, `\\`) | схлопываются в один |
  | сегмент `.` и завершающие разделители | отбрасываются |
  | сегмент `..` в любой позиции | **отказ**: лексический «подъём» намеренно не выполняется — он маскирует намерение вызывающего и на символьных ссылках расходится с поведением ядра |
  | относительный путь | достраивается от **явно переданной** базы (для `--prefix` база — текущий каталог); базы нет — отказ. На Windows относительный путь отвергается всегда: достраивать его от текущего каталога процесса при удалении недопустимо |
  | результат | **всегда абсолютный** нормализованный путь |

  Через нормализацию обязаны проходить: значения `manifest.purge_paths` (N5-R2), аргумент
  `--prefix` / `-Prefix`, каталог бинарника `bin_dir` и целевой путь бинарника, путь резервной
  копии (`<целевой путь>.bak`), каталог конфига `<config_dir>` (в том числе полученный из
  `XDG_CONFIG_HOME`) и целевой путь CA, каталог назначения Desktop и путь приложения
  `<каталог назначения>/<app_name>`.

  Непригодный путь — ошибка входных данных, а не аварии по ходу работы: сообщение
  `Небезопасный путь (<что>): <значение>` в stderr, код выхода `2`, ни одной файловой операции.

  **Строгая вложенность.** `path_is_inside` / `Test-PathInside` принимают два **уже
  нормализованных** пути и истинны только тогда, когда «потомок» лежит строго **ниже**
  «родителя»: не равен ему и не является его родителем. Передача ненормализованных значений
  запрещена — именно на ней шаблон вида `"$HOME"/?*` засчитывал второй разделитель за
  содержательный символ. На Windows сравнение регистронезависимое и учитывает оба разделителя
  (`\` и `/`), поскольку Pester-набор гоняется и на `pwsh` под macOS/Linux (N5-T2).

  На строгую вложенность опираются: путь приложения внутри каталога назначения Desktop (N5-P4),
  целевой файл внутри своего каталога (`artifacts[].install_name`, `ca.install_name`) и путь
  `--purge` внутри домашнего каталога (N5-R2).

## 4. Правила: общий контракт установщика (N5-I1, N5-I2)

- **N5-I1. Аргументы, режимы и коды выхода.** Оба установщика (`install.sh` и `install.ps1`)
  поддерживают один и тот же набор режимов и одни и те же коды выхода.

  | POSIX | Windows | Смысл |
  |---|---|---|
  | `--dry-run` | `-DryRun` | напечатать план, ничего не менять (N5-C1) |
  | `--check` | `-Check` | проверить среду, ничего не менять (N5-C2) |
  | `--uninstall` | `-Uninstall` | удалить установленное (N5-R1) |
  | `--purge` | `-Purge` | вместе с `--uninstall` — удалить и пользовательские данные (N5-R2) |
  | `--system` | — | ставить в `/usr/local/bin` (N5-I7); на Windows не применимо |
  | `--prefix <dir>` | `-Prefix <dir>` | переопределить корень установки (используется тестами) |
  | `--no-desktop` | `-NoDesktop` | пропустить шаг Desktop |
  | `--no-launch` | `-NoLaunch` | не выполнять финальный `opencode corp status` |
  | `--quiet` | `-Quiet` | печатать только итог и ошибки |
  | `--help` | `-Help` | напечатать справку в stdout и выйти с кодом `0` |
  | `--version` | `-ShowVersion` | напечатать `opencode-magnit <version> (<os>-<arch>)` из манифеста и выйти с кодом `0` |

  Неизвестный аргумент → справка в stderr, код `2`, ничего не изменено. Взаимоисключающие
  комбинации (`--dry-run` с `--check`, `--check` с `--uninstall`, `--purge` без `--uninstall`,
  `--system` с `--prefix`) → сообщение и код `2`. Комбинация `--dry-run --uninstall` допустима и
  печатает план удаления. Интерактивных вопросов установщик не задаёт ни в одном режиме: значения по
  умолчанию выбираются сами, флага подтверждения нет.

  Коды выхода:

  | Код | Значение |
  |---|---|
  | `0` | успех; для `--check` — состояние полностью соответствует пакету |
  | `1` | непредвиденная ошибка выполнения (в т.ч. неуспех шага Desktop при установке — N5-I9/N5-I10 — и провал штатного деинсталлятора Desktop при `--uninstall` — N5-R1) |
  | `2` | ошибка входных данных: аргументы, отсутствующий или невалидный манифест (N5-P4) |
  | `3` | несовместимая среда: ОС/архитектура/версия PowerShell/нет утилиты хеширования (N5-I3) |
  | `4` | несовпадение sha256 (N5-P5) |
  | `5` | нет прав на запись в целевой каталог (N5-I7) |
  | `6` | целевой файл занят другим процессом (N5-I8) |
  | `7` | только для `--check`: обнаружены расхождения (N5-C3) |

  Весь пользовательский вывод — на русском языке. Секреты установщик не печатает и не читает: он не
  обращается ни к `auth.json`, ни к переменным с ключами, ни к `opencode.json`.

- **N5-I2. `install.bat`.** Тонкий лончер, единственная задача — запустить `install.ps1` рядом с
  собой в обход политики выполнения и вернуть его код выхода:
  `powershell -NoProfile -ExecutionPolicy Bypass -File "%~dp0install.ps1" %*` и затем
  `exit /b %ERRORLEVEL%`. Собственной логики (проверок, установки, вывода на русском) в `.bat` нет;
  содержимое файла — только символы ASCII (N5-T6). Аргументы передаются в PowerShell без изменений.

## 5. Правила: шаги установки (N5-I3…N5-I12)

Порядок шагов фиксирован: (1) разбор аргументов → (2) манифест (N5-P4) → (3) ОС/архитектура →
(4) CA → (5) CLI-бинарник и PATH → (6) Desktop → (7) пользовательский конфиг → (8) итог и первый
запуск. Шаг, завершившийся ошибкой с кодом `2`, `3` или `4`, останавливает установку до внесения
изменений в систему.

- **N5-I3. Проверка ОС и архитектуры.** POSIX: `uname -s` (`Darwin` → `darwin`, `Linux` → `linux`,
  прочее → отказ) и `uname -m` (`arm64`/`aarch64` → `arm64`; `x86_64`/`amd64` → `x64`; прочее →
  отказ). Windows: `windows` и `x64` при `$env:PROCESSOR_ARCHITECTURE -eq 'AMD64'`; ARM64-Windows и
  32-разрядная система → отказ (цели `win32-arm64` форк не собирает, S-B2). Несовпадение с `os`/`arch`
  манифеста → код `3`, сообщение вида «пакет собран для `<os>-<arch>`, система — `<os>-<arch>`»;
  запуск сборки `darwin-x64` на Apple Silicon через Rosetta молча не допускается — это тот же отказ.
  Дополнительно `install.ps1` требует PowerShell ≥ 5.1 (`#Requires -Version 5.1`); на более старой
  версии — код `3` с указанием найденной версии.

- **N5-I4. Установка CA-файла.** Каталог конфига:
  `${XDG_CONFIG_HOME:-$HOME/.config}/opencode` на macOS/Linux и `%USERPROFILE%\.config\opencode` на
  Windows (факт §3 `docs/req-mvp.md`). Каталог создаётся при отсутствии (права `0755` на POSIX).
  Файл `certs/<ca.file>` после проверки хеша (N5-P5) копируется в `<config_dir>/<ca.install_name>`
  с правами `0644`. Если файл уже есть и его sha256 совпадает с манифестом — копирование
  пропускается со строкой отчёта «CA: уже установлен». Если отличается — перезаписывается
  (предыдущая копия не сохраняется: это корпоративный CA, а не пользовательские данные).

  **Многосегментный `ca.install_name` (ревизия 1.5.1).** N5-P3 намеренно разрешает разделитель `/`
  внутри `ca.install_name`, и проверка пути такое значение принимает — значит недостающие
  промежуточные каталоги внутри каталога конфига создаёт **сам установщик**, тем же порядком, что
  и каталог конфига: права `0755`, а при `--system` — с владельцем исходного пользователя,
  назначаемым каждому созданному звену цепочки (N5-I14). Для `ca.install_name` =
  `certs/corp/tander-ca-bundle.pem` установка завершается кодом `0`, CA лежит по пути
  `<config_dir>/certs/corp/tander-ca-bundle.pem`, `NODE_EXTRA_CA_CERTS` указывает на него, а
  повторный запуск на уже созданной цепочке идемпотентен (N5-U1). Обрыв установки кодом `1` с
  системной англоязычной диагностикой копирования (`cp: … No such file or directory` на POSIX,
  непойманное исключение `Copy-Item` на Windows) недопустим: всё общение установщика — по-русски
  (N5-I1), а значение, которое спецификация разрешает и валидация принимает, не может приводить
  к отказу такого рода. Требование одинаково для обеих платформ: пакет, принятый одной, ставится
  и другой (N5-P4).

  Правило относится к `ca.install_name` — единственному путевому полю, значение которого
  спецификация оставляет свободным внутри каталога конфига. Для `artifacts[].install_name` при
  `kind:"cli"` N5-P3 задаёт одно из двух фиксированных имён (`opencode`, `opencode.exe`) без
  разделителя, и сборщик пакета (N5-B2) другого значения не порождает; поведение установщика на
  многосегментном значении этого поля правилами не определено — см. §14.

- **N5-I5. `NODE_EXTRA_CA_CERTS` на macOS/Linux.** Значение записывается в файл профиля shell
  внутри маркированного блока:

  ```
  # >>> opencode-magnit >>>
  export NODE_EXTRA_CA_CERTS='<config_dir>/<ca.install_name>'
  export PATH='<bin_dir>':"$PATH"
  # <<< opencode-magnit <<<
  ```

  **Кавычки — часть контракта (ревизия 1.5).** Значения печатаются в **одинарных** кавычках, а
  `$PATH` намеренно остаётся вне их: он обязан раскрываться оболочкой пользователя, а `<config_dir>`
  и `<bin_dir>` — не обязаны и не должны. Правила экранирования и обоснование — N5-I13.

  Файл профиля выбирается по `$SHELL` (по имени исполняемого файла): `zsh` → `~/.zshrc`;
  `bash` → `~/.bash_profile` на macOS и `~/.bashrc` на Linux; `fish` →
  `~/.config/fish/conf.d/opencode-magnit.fish` (тем же блоком, но синтаксисом
  `set -gx NODE_EXTRA_CA_CERTS '…'` / `fish_add_path '…'` — со своими правилами экранирования,
  N5-I13); всё прочее и пустой `$SHELL` → `~/.profile`.
  Редактируется **ровно один** файл. Отсутствующий файл создаётся.

  Идемпотентность: если блок с маркерами уже есть, его содержимое заменяется целиком, второй блок не
  добавляется; если блок уже содержит нужные строки — файл не изменяется вовсе (mtime не трогается).
  Перед первой вставкой блока делается резервная копия `<файл>.opencode-magnit.bak`; при
  последующих запусках она не перезаписывается.

  **Правка блока на месте и схлопывание задвоенного блока (уточнено в ревизии 1.2).** Если
  маркированный блок в файле уже есть, правка выполняется **на месте**: содержимое **первого**
  блока заменяется новым, а все последующие маркированные блоки вырезаются. Поэтому:

  - если в файле профиля по каким-то причинам оказалось два и более маркированных блока (например,
    после ручного копирования строк пользователем), очередной запуск установщика схлопывает их в
    один — гарантия N5-U1 «в профиле ровно один маркированный блок» держится и при внешних правках
    файла;
  - **позиция уже существующего блока сохраняется**: он не переносится в конец файла, порядок
    остальных строк профиля не меняется. В ревизии 1.1 замена делалась как «вырезать все блоки и
    дописать один в конец», из-за чего блок из середины файла переезжал в конец — это выглядело как
    самовольная правка порядка строк пользовательского файла.

  В конец файла блок дописывается только тогда, когда его в файле ещё нет вовсе. Идемпотентность
  сохраняется: повторный запуск с тем же содержимым блока файл не изменяет.

  Строка `export PATH=…` добавляется в блок, только если `bin_dir` ещё не входит в `$PATH` текущего
  процесса.

  **Предупреждение о чужом `NODE_EXTRA_CA_CERTS` (уточнено в ревизии 1.2).** Чужим считается
  **присваивание** переменной вне нашего блока со значением, отличным от нашего пути. Строка
  профиля разбивается на сегменты по разделителям команд (`;`, `&&`, `||`, `|`, `&`, скобки), у
  сегмента отбрасываются ведущие пробелы и табуляции, управляющие слова составной команды
  (`then`, `do`, `else`, `elif`) и объявляющие префиксы с их ключами; остаток обязан **начинаться**
  с формы присваивания. Распознаются:

  | Форма | Пример |
  |---|---|
  | простое присваивание | `NODE_EXTRA_CA_CERTS=/path/ca.pem` |
  | `export` | `export NODE_EXTRA_CA_CERTS=/path/ca.pem` |
  | `declare -x` | `declare -x NODE_EXTRA_CA_CERTS=/path/ca.pem` |
  | `typeset -x` | `typeset -x NODE_EXTRA_CA_CERTS=/path/ca.pem` |
  | `readonly` | `readonly NODE_EXTRA_CA_CERTS=/path/ca.pem` |
  | префикс команды `env` | `env NODE_EXTRA_CA_CERTS=/path/ca.pem node app.js` |
  | `setenv` (csh) | `setenv NODE_EXTRA_CA_CERTS /path/ca.pem` |
  | `set -gx` (fish) | `set -gx NODE_EXTRA_CA_CERTS /path/ca.pem` |
  | присваивание внутри составной строки | `if [ -f /p/ca.pem ]; then export NODE_EXTRA_CA_CERTS=/p/ca.pem; fi` |

  Любое другое упоминание имени переменной предупреждения **не** вызывает — в частности,
  строка-комментарий (`# NODE_EXTRA_CA_CERTS больше не нужен`) и упоминание внутри строкового
  литерала (`echo "NODE_EXTRA_CA_CERTS=..."`): там имя не стоит в начале сегмента как присваивание.
  Чужая строка не изменяется, но в отчёт добавляется предупреждение с именем файла и номером
  строки: какое из присваиваний победит в новой сессии, зависит от их взаимного порядка в файле
  (наш блок правится на месте и в конец файла не переезжает), поэтому решение остаётся за
  пользователем.

  Переменные окружения для GUI-процессов на macOS/Linux установщик не задаёт: штатного
  пользовательского механизма для этого нет, а изменение `launchd`/`systemd --user` окружения выходит
  за границы «без прав администратора». Desktop-сборка получает CA из файла в каталоге конфига
  (N5-I4). Ограничение печатается отдельной строкой отчёта и описывается в `install-admin.md`
  (N5-D2). **[проверить]** — подтверждается на стороне форка при первом прогоне сквозного сценария.

- **N5-I6. `NODE_EXTRA_CA_CERTS` на Windows.** Значение записывается в переменную **пользователя**:
  `[Environment]::SetEnvironmentVariable("NODE_EXTRA_CA_CERTS", "<config_dir>\<ca.install_name>", "User")`.
  Запись выполняется, только если текущее пользовательское значение отличается от целевого
  (иначе строка отчёта «NODE_EXTRA_CA_CERTS: уже задан»). Переменные уровня `Machine` не
  изменяются никогда, права администратора не требуются. Той же переменной пользуется и Desktop
  (Electron-сборка наследует пользовательское окружение), отдельной переменной для Desktop нет.
  Импорт CA в системное хранилище сертификатов не выполняется (§1.1).

- **N5-I7. CLI-бинарник и PATH на macOS/Linux.** Каталог назначения (`bin_dir`):
  `$HOME/.local/bin` по умолчанию; `/usr/local/bin` при `--system`; `<prefix>/bin` при `--prefix`.
  Каталог создаётся при отсутствии. Порядок: проверка sha256 (N5-P5) → копирование во временный файл
  `<bin_dir>/.opencode.new.<pid>` в том же каталоге → `chmod 0755` → атомарное переименование поверх
  цели. Копирование-с-переименованием обязательно: так уже запущенный процесс `opencode` не ломается,
  а частично записанного бинарника в PATH не появляется ни на одну секунду.

  Права: при отсутствии права на запись в `bin_dir` установщик **не** повышает права молча. Без
  `--system` он завершается кодом `5` с подсказкой. С `--system`: если процесс не root, а `sudo`
  доступен — привилегированные операции выполняются через `sudo` (создание каталога, перенос файла,
  `chmod`); если `sudo` недоступен или отказал — код `5` с текстом «нужны права root: запустите под
  root или без `--system` (установка в `$HOME/.local/bin`)». Установка по умолчанию (без `--system`)
  никогда не вызывает `sudo`.

  Если `bin_dir` не входит в `$PATH`, он добавляется в маркированный блок профиля (N5-I5) и в отчёт
  добавляется строка «откройте новый терминал».

  **Что именно делает `--system` (уточнено в ревизии 1.5).** Через `sudo` выполняются операции
  **только** с `bin_dir`: создание каталога, копирование, `chmod`, переименование, удаление.
  Пользовательская часть — CA-файл (N5-I4), каталог конфига, файл профиля (N5-I5) и резервные
  копии — при `--system` не становится «системной»: она по-прежнему относится к домашнему каталогу
  **исходного** пользователя и принадлежит ему. Требования и порядок определения этого пользователя
  — N5-I14.

- **N5-I8. CLI-бинарник и PATH на Windows.** Каталог назначения —
  `%LOCALAPPDATA%\Programs\opencode` (или `<Prefix>` при `-Prefix`), создаётся при отсутствии.
  Замена занятого файла: существующий `opencode.exe` сначала переименовывается в `opencode.exe.bak`
  (Windows позволяет переименовать запущенный исполняемый файл), затем записывается новый. Если
  переименование не удалось (файл заблокирован антивирусом или иным процессом) — код `6` с текстом
  «файл занят: закройте OpenCode и повторите запуск», новый файл не записывается.

  PATH пользователя правится через реестр `HKEY_CURRENT_USER\Environment`:
  значение читается с `RegistryValueOptions.DoNotExpandEnvironmentNames` (иначе `%…%` внутри PATH
  будут развёрнуты и запись их уничтожит) и записывается обратно с сохранением исходного
  `RegistryValueKind` (`ExpandString`, если он был таким). Каталог добавляется, только если его ещё
  нет: сравнение поэлементное, регистронезависимое, с отбрасыванием завершающего `\`. После записи
  рассылается `WM_SETTINGCHANGE` (`SendMessageTimeout`, `HWND_BROADCAST`, `"Environment"`,
  таймаут 5000 мс), чтобы новые процессы увидели изменение без перезахода в систему; неуспех рассылки
  — предупреждение, а не ошибка.

- **N5-I9. Desktop на macOS.** Если в манифесте есть артефакт `kind:"desktop"` с
  `installer_type:"dmg"` и не задан `--no-desktop`: проверка sha256 → `hdiutil attach -nobrowse
  -readonly` → копирование `<app_name>` через `ditto` в `/Applications` → `hdiutil detach`.

  **Имя бандла (ревизия 1.5).** Корпоративная сборка Desktop называется `OpenCode Magnit.app`:
  установленный путь — `/Applications/OpenCode Magnit.app` (или `~/Applications/OpenCode Magnit.app`
  без прав на `/Applications`), запись деинсталляции на Windows ищется по имени без суффикса
  `.app` — `OpenCode Magnit` (N5-R1). Имя нигде не вычисляется из константы в коде установщика: оно
  приходит **только** из `artifacts[].app_name` манифеста, а в манифест — из единственной константы
  сборки в `release.sh` (ветка `*.dmg`). Пробел в имени безопасен (N5-P4), но требует, чтобы каждая
  подстановка была одним закавыченным аргументом: `ditto "<mount>/<app_name>" "<dest>/<app_name>"`,
  `rm -rf "<dest>/<app_name>"`, сравнение `CFBundleShortVersionString` по пути в кавычках.
  Смена `appId` (`ai.opencode.desktop.magnit`) и адрес внутреннего сервера автообновления
  установщиков не касаются: `installers/` их не читает и не пишет (граница объёма §1.1). Отмонтирование
  выполняется всегда, в том числе при ошибке копирования и при прерывании (ловушка на выходе):
  оставленный примонтированный образ — дефект. Существующее приложение перед копированием удаляется
  (для каталога `.app` резервная копия не делается — это сборка, а не пользовательские данные).
  При отсутствии прав на `/Applications`: с `--system` — через `sudo`; без него — установка в
  `~/Applications` и предупреждение в отчёте. Совпадение версии установленного приложения с версией
  пакета (`CFBundleShortVersionString` из `Info.plist`) → шаг пропускается со строкой «Desktop: уже
  установлен».

- **N5-I10. Desktop на Windows и его отсутствие.** Если есть артефакт `kind:"desktop"` и не задан
  `-NoDesktop`: проверка sha256 → запуск штатного установщика `Start-Process -Wait -PassThru` с
  аргументами из `silent_args` манифеста. Если `silent_args` в манифесте нет — установщик **не**
  угадывает ключи тихой установки: печатает путь к файлу и строку «Desktop: запустите установщик
  вручную», код выхода не меняется. Ненулевой код штатного установщика → строка
  «Desktop: ошибка (код `<n>`)» и общий код выхода `1`; при этом установка CLI и CA **не
  откатывается** — она уже завершена и работоспособна.

  Если артефакта `kind:"desktop"` в манифесте нет (Linux-пакет, CLI-only пакет) — шаг пропускается со
  строкой «Desktop: не входит в пакет», это не ошибка. При `--no-desktop` — строка
  «Desktop: пропущен (--no-desktop)».

- **N5-I11. Пользовательский конфиг и ключи.** Установщик **не создаёт и не изменяет**
  `<config_dir>/opencode.json`, не пишет туда адрес Hub, провайдера, модель и умолчания (это делает
  корпоративная сборка на уровне build-констант, S-C2/S-C3), не создаёт и не читает `auth.json`, не
  запрашивает и не сохраняет никаких ключей и токенов.

  Семантически сравнить пользовательский конфиг с корпоративными умолчаниями установщик не может и
  не пытается (разбора JSON нет), поэтому конфликтом считается сам факт существования файла: если
  `<config_dir>/opencode.json` существует и рядом ещё нет `opencode.json.bak`, создаётся резервная
  копия `opencode.json.bak` (страховка на случай, если будущая версия сборки изменит формат). При
  повторных запусках существующий `.bak` не перезаписывается — иначе он затрёт заведомо исправную
  копию. Отчёт содержит строку «Конфиг: `<путь>` (не изменялся)».

- **N5-I12. Итог и первый запуск.** После всех шагов установщик печатает отчёт фиксированного вида
  (регистр и порядок строк — часть контракта, на них опираются тесты N5-T3 и `--check`):

  ```
  Готово: OpenCode <version> установлен.
    Бинарник: <путь>
    CA: <путь>
    Desktop: <путь> | не входит в пакет | пропущен (--no-desktop) | ошибка (код <n>)
    Конфиг: <путь> (не изменялся)
    Hub: <hub_url>
  Дальше:
    1. Откройте новый терминал (или выполните: source <файл профиля>)
    2. Запустите: opencode
    Вход по корпоративному SSO предложат при первом запуске.
  ```

  Строка «1. Откройте новый терминал…» печатается только если установщик правил профиль или PATH.
  Затем, если не задан `--no-launch`, выполняется `"<bin_dir>/opencode" corp status` (S-A11): его
  вывод печатается как есть, а его код выхода **игнорируется** — сразу после установки ключа ещё нет,
  и `corp status` штатно возвращает `1` (S-A11, D-13). Автоматически ни `opencode`, ни Desktop
  установщик не запускает: он лишь печатает, что запускать.

- **N5-I13. Экранирование значений в генерируемом коде оболочки (ревизия 1.5).** Установщик
  **генерирует код**: блок в файле профиля (N5-I5) — это строки, которые оболочка пользователя
  исполнит при следующем входе. Любое значение, попадающее в такой блок, — потенциальная команда.
  До ревизии 1.5 значения печатались в двойных кавычках (`export NODE_EXTRA_CA_CERTS="%s"`), а
  `ca.install_name` проверялся только как путь внутри пакета, где `$`, `` ` ``, `"` и `;` не
  запрещены. Наблюдаемое следствие (PoC ревью): `ca.install_name = 'pwn$(touch PWNED).pem'` —
  установка завершается кодом `0`, в `~/.bash_profile` попадает подстановка команды, при входе в
  оболочку команда исполняется, а `NODE_EXTRA_CA_CERTS` получает путь к несуществующему файлу, то
  есть доверие к корпоративному CA молча ломается; `ca.install_name = 'a.pem"; touch BREAKOUT; x="'`
  даёт в профиле отдельную команду. Требование состоит из двух независимых линий защиты; выполнены
  обязаны быть обе.

  **Линия 1 — проверка (значения манифеста).** Поля `ca.install_name`, `artifacts[].install_name`,
  `artifacts[].app_name` обязаны проходить проверку по белому списку символов N5-P4. Значение с
  метасимволом оболочки не «экранируется и используется», а делает манифест невалидным: сообщение
  называет поле (`ca.install_name`, `artifacts.<i>.install_name`, `artifacts.<i>.app_name`) и путь
  к манифесту, код выхода `2`, ни одной файловой операции, файл профиля не создан и не изменён.
  Установка с таким значением **обязана завершаться отказом, а не кодом `0`** — во всех режимах
  (установка, `--check`, `--dry-run`, `--uninstall`, `--dry-run --uninstall`, `--uninstall --purge`),
  так как проверка выполняется в `manifest_load` (N5-P4, «Момент проверки»).

  **Линия 2 — экранирование (значения окружения).** `$HOME`, `XDG_CONFIG_HOME` и `--prefix`
  проверке по белому списку не подлежат: каталог пользователя вправе называться `pre$fix`, содержать
  обратную кавычку, апостроф, точку с запятой или пробел, и установка в него обязана проходить
  штатно, кодом `0`. Поэтому
  производные от них значения — `config_dir`, `bin_dir`, `ca_target` — попадают в блок профиля
  только в экранированном виде, различном для двух семейств оболочек:

  | Профиль | Форма строк | Правило экранирования |
  |---|---|---|
  | POSIX (`sh`, `bash`, `zsh`, `~/.profile`) | `export NODE_EXTRA_CA_CERTS='<значение>'`, `export PATH='<значение>':"$PATH"` | значение целиком в **одинарных** кавычках; каждый апостроф внутри значения заменяется на `'\''` (закрыть кавычку, экранированный апостроф, открыть снова); больше ничего не заменяется, не удаляется и не добавляется |
  | fish (`~/.config/fish/conf.d/opencode-magnit.fish`) | `set -gx NODE_EXTRA_CA_CERTS '<значение>'`, `fish_add_path '<значение>'` | значение целиком в одинарных кавычках fish; внутри них экранируются **ровно два** символа: `\` → `\\` и `'` → `\'`. `$`, `` ` ``, `;`, `(`, `)` внутри одинарных кавычек fish не имеют специального смысла и не экранируются |

  Двойные кавычки для значения, пришедшего из окружения, запрещены в обоих семействах. Единственное
  место, где двойные кавычки остаются, — `"$PATH"` в POSIX-профиле: это намеренное раскрытие
  переменной оболочкой пользователя, а не подстановка нашего значения.

  **Перевод строки в пути.** Блок профиля построчный, маркеры распознаются по целой строке (N5-I5),
  поэтому путь, содержащий символ перевода строки (`\n`) или возврата каретки (`\r`), не
  экранируется, а отвергается как небезопасный путь (N5-P9): сообщение
  `Небезопасный путь (<что>): <значение>`, код выхода `2`, файл профиля не создан и не изменён.

  **Наблюдаемый результат (как проверяется).** После установки в каталог, имя которого содержит
  `$(…)`, `` ` ``, `"`, `'`, `;`, `&` и пробел: код выхода `0`; исполнение сгенерированного профиля
  в изолированном каталоге не создаёт ни одного постороннего файла (канарейка отсутствует), значение
  `NODE_EXTRA_CA_CERTS` после исполнения **побайтово** равно фактическому пути установленного
  CA-файла, файл по этому пути существует и его sha256 равен `ca.sha256`, а `PATH` содержит
  `bin_dir` и сохраняет прежнее значение хвостом (AC-146, AC-147). Повторный запуск оставляет ровно
  один блок и не меняет файл (N5-U1).

  **Windows.** `install.ps1` кода оболочки не генерирует: значения пишутся в реестр и в переменные
  пользователя через API, аргументы передаются массивом (`-ArgumentList`), `Invoke-Expression`
  отсутствует. Это и есть требование: появление в `install.ps1` генерации исполняемой строки
  (`Invoke-Expression`, `iex`, `cmd /c "<сцепленная строка>"`, `powershell -Command "<сцепленная
  строка>"`) запрещено; паритет с POSIX обеспечивается отсутствием такой генерации, а не
  экранированием.

- **N5-I14. Пользовательская часть при `--system` (ревизия 1.5).** `--system` (N5-I7) означает
  «бинарник в системный каталог», а не «вся установка от имени `root`». До ревизии 1.5 правило не
  говорило, чей дом правится и кому принадлежат созданные файлы, и код это не компенсировал: CA,
  каталог конфига и блок профиля писались без повышения прав, от имени текущего процесса. При
  штатном `sudo ./install.sh --system` это давало один из двух дефектов: при сброшенном `HOME`
  пользовательская часть уезжала в дом `root` (пользователь не получал ни CA, ни
  `NODE_EXTRA_CA_CERTS`, а код выхода был `0`), при сохранённом `HOME` — в доме пользователя
  появлялись файлы, принадлежащие `root`, которые он не может обновить без `sudo`.

  **Целевой пользователь и его дом.** Пользовательская часть всегда относится к **исходному**
  пользователю — тому, кто запустил установщик. Порядок определения фиксирован, берётся первое
  подходящее значение:

  | # | Условие | Исходный пользователь |
  |---|---|---|
  | 1 | эффективный uid процесса ≠ 0 | текущий пользователь (`id -un`) |
  | 2 | uid = 0 и `SUDO_USER` непуст и не равен `root` | `$SUDO_USER` |
  | 3 | uid = 0 и `logname` дал непустое имя, не равное `root` | вывод `logname` |

  Домашний каталог берётся **из базы пользователей** (`getent passwd <user>` на Linux,
  `dscl . -read /Users/<user> NFSHomeDirectory` на macOS), а не из `$HOME`: под `sudo` `$HOME`
  указывает либо на `/var/root` (`/root`), либо на дом пользователя — в зависимости от настроек
  `env_reset`/`env_keep`, то есть на него опираться нельзя. Полученный путь проходит нормализацию
  (N5-P9) и обязан существовать и быть каталогом. Случай 1 (запуск не под `root`) ничего не меняет:
  это текущее поведение, `$HOME` и есть дом исходного пользователя.

  `XDG_CONFIG_HOME` при `--system` учитывается, только если его значение после нормализации лежит
  **строго внутри** дома исходного пользователя (N5-P9); иначе используется `<home>/.config` —
  переменная окружения `root` не должна определять, куда встанет CA пользователя.

  **Владелец созданных файлов.** Каждый объект пользовательской части, созданный или изменённый
  установщиком, принадлежит исходному пользователю и его первичной группе: каталог конфига,
  CA-файл, **каждый промежуточный каталог, созданный установщиком в доме исходного пользователя**
  (ревизия 1.5.1), каталог файла профиля (для fish), сам файл профиля, резервная копия
  `<файл>.opencode-magnit.bak` и **резервная копия пользовательского конфига `opencode.json.bak`**
  (N5-I11, ревизия 1.5.1). Если эффективный uid процесса `0`, а исходный пользователь — не
  `root`, установщик выполняет `chown <uid>:<gid>` для каждого такого пути. Права не меняются:
  `0755` для каталогов, `0644` для CA (N5-I4), права файла профиля сохраняются, а у созданного —
  `0644`. Проверяемо: `stat -c '%U'` (Linux) / `stat -f '%Su'` (macOS) для каждого пути из строк
  отчёта `CA:` и `Конфиг:` и для файла профиля возвращает имя исходного пользователя, а не `root`.

  **Цепочка каталогов и граница «создано установщиком» (ревизия 1.5.1).** `mkdir -p` создаёт не
  один каталог, а всю недостающую цепочку: в пустом доме это `<дом>/.config`, `<дом>/.config/fish`
  и `<дом>/.config/fish/conf.d`, в каталоге конфига — промежуточные каталоги многосегментного
  `ca.install_name` (N5-I4). Промежуточное звено — такая же пользовательская часть, как и лист:
  `root`-овый `<дом>/.config` означает, что пользователь не может создать в собственном `~/.config`
  ничего нового без `sudo`. Поэтому владелец и права `0755` назначаются **каждому** звену цепочки
  от листа до первого уже существовавшего предка **исключительно**. Граница вычисляется **до**
  `mkdir`: объекты, существовавшие в доме до установки, владельца не меняют — ни сам домашний
  каталог, ни обжитый `<дом>/.config`, ни каталог конфига, ни пользовательский `opencode.json`
  (менять владельца чужого объекта установщик не вправе). Проверяемо: после `--system` в доме
  исходного пользователя нет ни одного **нового** пути, принадлежащего `root`, а множество
  `chown`-вызовов не пересекается с множеством путей, существовавших до запуска.

  Файлы в `bin_dir` (`/usr/local/bin`) остаются `root`-овыми с правами `0755`: это системный
  каталог, смена владельца там не требуется и не выполняется.

  **Исходного пользователя определить нельзя.** Если эффективный uid `0`, `SUDO_USER` пуст или
  равен `root`, `logname` имени не дал (либо у найденного пользователя нет существующего домашнего
  каталога) — это ошибка входных данных, а не повод «поставить куда получится». Установщик
  завершается кодом `5` с сообщением «`--system`: не удалось определить исходного пользователя
  (`SUDO_USER` и `logname` пусты) — запустите `sudo ./install.sh --system` от имени пользователя
  или установите без `--system`», **не выполнив ни одной файловой операции** ни в `/usr/local/bin`,
  ни в каком домашнем каталоге, и ни разу не вызвав `sudo` для записи. Установка в дом `root` с
  кодом `0` запрещена: это ровно тот исход, при котором пользователь остаётся без CA и без
  `NODE_EXTRA_CA_CERTS`, а установщик рапортует об успехе.

  **Момент проверки.** Исходный пользователь и его дом определяются на шаге (3) порядка N5-I3 —
  после проверки манифеста и ОС/архитектуры, но **до** шага CA и до любой файловой операции, чтобы
  отказ по коду `5` не оставлял частичной установки. В `--dry-run` и `--check` те же значения
  вычисляются и печатаются (пути CA, конфига и профиля — внутри дома исходного пользователя, каталог
  бинарника — `/usr/local/bin`), ФС не меняется, `sudo` не вызывается (N5-C1, N5-C4).

  **Отчёт.** При `--system` строки `CA:` и `Конфиг:` содержат пути внутри дома исходного
  пользователя, строка «1. Откройте новый терминал…» относится к его файлу профиля; отдельной
  строкой печатается, от имени какого пользователя выполнена пользовательская часть:
  `Пользователь: <имя> (<домашний каталог>)`.

## 6. Правила: идемпотентность, обновление, откат (N5-U*)

- **N5-U1. Идемпотентность.** Два подряд запуска установщика с одинаковыми аргументами оставляют
  одинаковое состояние: в профиле ровно один маркированный блок, в PATH ровно один экземпляр
  `bin_dir`, ровно одна пользовательская переменная `NODE_EXTRA_CA_CERTS`, ровно один
  `opencode.json.bak`, ровно один `opencode.bak`. Оба запуска завершаются кодом `0`. Ни один шаг не
  требует «чистой системы»: установка поверх уже установленного — штатный сценарий.

  Гарантия «ровно один маркированный блок» — не только про повторный запуск установщика: если в
  профиле уже оказалось несколько блоков, очередной запуск схлопывает их в один. При этом
  существующий блок правится **на месте** и не переезжает в конец файла — его позиция и порядок
  остальных строк профиля сохраняются (N5-I5, ревизия 1.2).

- **N5-U2. Обновление.** Если установленный бинарник отличается от бинарника пакета, перед заменой
  он копируется в `<bin_dir>/opencode.bak` (Windows: переименовывается в `opencode.exe.bak`),
  перезаписывая предыдущий `.bak`; хранится ровно одна предыдущая версия. Откат — ручной:
  документируется в `install-admin.md` как переименование `.bak` обратно (N5-D2). Каталог конфига,
  `opencode.json`, `auth.json` и `opencode.json.bak` при обновлении не изменяются.

- **N5-U3. Пропуск при совпадении.** Если sha256 установленного бинарника совпадает с манифестом,
  шаг установки бинарника пропускается целиком: файл не перезаписывается, `.bak` не создаётся и не
  изменяется. Строка отчёта — «Бинарник: уже установлен (`<version>`)». То же для CA (N5-I4) и
  Desktop (N5-I9).

- **N5-U4. Другая версия.** Установщик не сравнивает версии как порядок и не запрещает установку
  более старого пакета поверх более нового: устанавливается ровно то, что лежит в пакете. В отчёте и
  в `--check` при различии печатается «другая версия (установлена `<a>`, в пакете `<b>`)», без слов
  «новее»/«старее».

## 7. Правила: удаление (N5-R*)

- **N5-R1. `--uninstall`.** Удаляются только то, что ставил установщик: файл `opencode`
  (`opencode.exe`) и `opencode.bak` из `bin_dir`; маркированный блок из файла профиля (сам файл и
  строки вне блока не изменяются; блок вырезается целиком, включая обе строки-маркера);
  запись `bin_dir` из пользовательского PATH на Windows (с той же реестровой техникой, что и в
  N5-I8) и рассылка `WM_SETTINGCHANGE`; пользовательская переменная `NODE_EXTRA_CA_CERTS` — только
  если её текущее значение равно установленному нами пути (чужое значение не трогается);
  установленный CA-файл `<config_dir>/<ca.install_name>`; Desktop-приложение (`/Applications/<app_name>`
  или `~/Applications/<app_name>`; на Windows — запуск штатного деинсталлятора, см. ниже).

  Каталог конфига, `opencode.json`, `opencode.json.bak`, `auth.json` и любые пользовательские данные
  при `--uninstall` **сохраняются**. Отчёт перечисляет каждый удалённый и каждый пропущенный объект.

  **Удаление Desktop на Windows (ревизии 1.1 и 1.2).** Установщик не удаляет файлы Desktop-приложения
  сам: приложение ставится своим инсталлятором (nsis/msi), поэтому и снимается своим
  деинсталлятором. Порядок:

  1. По `artifacts[].app_name` ищется запись в `HKCU\…\Uninstall` и `HKLM\…\Uninstall`
     (сопоставление по `DisplayName`). **Сопоставление литеральное (ревизия 1.2):** ключ поиска —
     `app_name` без суффикса `.app` — перед сравнением экранируется
     (`[System.Management.Automation.WildcardPattern]::Escape`), поэтому подстановочные символы
     `*`, `?`, `[`, `]` в значении не расширяют совпадение, а ищутся как обычные символы; пустой
     после отбрасывания `.app` ключ совпадением не считается. Те же символы отвергаются валидацией
     манифеста (N5-P4), то есть это вторая, независимая линия защиты.
  2. Команда деинсталляции выбирается так: если у записи непустая `QuietUninstallString` — берётся
     она (она уже содержит тихие ключи); иначе берётся `UninstallString`, и к его аргументам
     добавляются `silent_args` из манифеста (например `["/S"]`). `silent_args` не добавляются к
     `QuietUninstallString`, чтобы не задваивать ключи.
  3. Строка деинсталляции разбирается на исполняемый файл и аргументы. Поддерживаются:
     `"C:\…\uninstall.exe" /S` (путь в кавычках), `MsiExec.exe /X{GUID}` и — с ревизии 1.2 —
     **некавыченный путь с пробелами** (`C:\Program Files\App\unins000.exe /S`): его граница
     определяется по расширению исполняемого файла (`.exe`, `.com`, `.bat`, `.cmd`,
     регистронезависимо). Аргументы разбираются с учётом кавычек: значение с пробелом внутри
     кавычек (`/D="C:\Program Files\App"`) остаётся **одним** аргументом. Затем процесс
     запускается и установщик **дожидается его завершения**.
  4. Результат отражается фактическим кодом процесса: `0` → строка отчёта «`Desktop: удалён
     (<путь>)`»; ненулевой код `N` → «`Desktop: ошибка (код N)`».
  5. Если записи в реестре нет либо и `QuietUninstallString`, и `UninstallString` пусты —
     деинсталлятор не запускается, печатается «`Desktop: удалите вручную через «Приложения и
     возможности»`». Это **не ошибка**: код выхода при этом не портится.
  6. **Неоднозначный разбор (ревизия 1.2).** Если в строке деинсталляции есть пробел, но
     однозначной границы исполняемого файла нет (некавыченный путь без известного расширения), или
     после разбора путь пуст, — деинсталлятор **не запускается**. Печатается строка контракта
     «`Desktop: строка деинсталляции разобрана неоднозначно (<строка целиком>), запуск отменён`», за
     ней — «`Desktop: удалите вручную через «Приложения и возможности»`». Строка «`Desktop:
     удалён`» не печатается, **код выхода не изменяется** (запустить чужой процесс хуже, чем
     попросить удалить вручную).

  Печатать «`Desktop: удалён`», не запустив деинсталлятор, запрещено: отчёт обязан отражать
  фактически выполненное действие.

  **Код выхода при провале деинсталлятора Desktop.** Ненулевой код деинсталлятора даёт итоговый код
  выхода `1` — по тому же принципу, что и неуспех шага Desktop при установке (N5-I10). Удаление
  CLI, PATH, переменной окружения и CA к этому моменту уже выполнено и **не откатывается**: их
  строки отчёта остаются, за ними идёт строка ошибки Desktop. Все прочие объекты `--uninstall`
  обрабатываются как обычно, `--purge` (если запрошен) выполняется, и только затем возвращается
  код `1`.

- **N5-R2. `--purge`.** Действует только вместе с `--uninstall` и дополнительно удаляет пути из
  `manifest.purge_paths` — по умолчанию каталог конфига (`<config_dir>`) и каталог данных
  (`${XDG_DATA_HOME:-$HOME/.local/share}/opencode`, на Windows `%USERPROFILE%\.local\share\opencode`),
  где лежит в том числе сохранённый ключ LiteLLM. **[проверить]** — фактическое размещение
  auth-store форка подтверждается при сквозном прогоне; поэтому список задаётся манифестом, а не
  зашит в скрипт.

  **Проверка пути (ужесточено в ревизии 1.4).** Удаляются только пути, прошедшие проверку. Значение
  из списка сначала разворачивается (подстановки `~`, `${HOME}`, `${XDG_CONFIG_HOME}`,
  `${XDG_DATA_HOME}`, `%USERPROFILE%`, `%LOCALAPPDATA%`), затем **нормализуется** по N5-P9, и
  решение принимается **по нормализованному значению**: путь обязан лежать **строго внутри**
  домашнего каталога (`$HOME` / `%USERPROFILE%`) — не совпадать с ним, не быть его родителем и не
  выходить за его пределы; сегмент `..` отвергается и в исходной строке, и после подстановки.
  Поэтому одинаково отвергаются `~`, `~/`, `~//`, `${HOME}`, `${HOME}//`, `${HOME}///`,
  `${HOME}/.`, `${HOME}/./`, `${HOME}/sub/..`, `%USERPROFILE%\`, `%USERPROFILE%\.`,
  `%USERPROFILE%\.\`, `%USERPROFILE%\sub\..`, `/etc`, `~/../other` и любой относительный путь:
  всё, что после нормализации оказывается самим домашним каталогом или лежит вне его.

  Список проверяется целиком **до** первого удаления: одна не прошедшая запись отвергает весь
  список — не удаляется ничего, включая пути, проверку прошедшие; на каждую такую запись печатается
  предупреждение с исходным значением, затем строка об отвергнутом списке, код выхода `2`.

  **Проверка продублирована непосредственно в цикле удаления** (defense in depth): перед каждым
  `rm -rf` / `Remove-Item` путь проверяется повторно и независимо от валидации списка. Требование
  сформулировано по наблюдаемому результату: если валидация списка окажется обойдена, отключена или
  изменена, исходом обязан быть **отказ с кодом `2`, а не удаление**. Удаляется и печатается всегда
  ровно нормализованное значение — то же, что прошло проверку.

  Перед удалением каждый путь перечисляется в выводе; `--dry-run --uninstall --purge` печатает тот
  же список нормализованных путей, ничего не удаляя.

  > **Исправление уязвимости №3 (ревизия 1.4).** До ревизии 1.4 проверка сравнивала строки: «путь
  > начинается с `$HOME/` и не равен `$HOME`». Значение `purge_paths` вида `${HOME}//` (равно как
  > `~//` и `${HOME}///`) строкой не равно `$HOME`, а шаблон `"$HOME"/?*` засчитывал второй
  > разделитель за содержательный символ — запись проходила валидацию, после чего выполнялось
  > `rm -rf "$HOME//"`, то есть **удаление домашнего каталога пользователя целиком**, с печатью
  > «Данные: удалено» и кодом выхода `0`. PoC ревью на изолированном `$HOME`: до запуска шесть
  > записей, включая `Documents/very-important/data.txt` и `.ssh/id_rsa`; после
  > `install.sh --uninstall --purge` каталога нет, код `0`. Windows-паритет: `Test-PurgePathSafe`
  > снимала завершающие `\` и потому отбивала `%USERPROFILE%\\`, но `%USERPROFILE%\.` и
  > `%USERPROFILE%\.\` проходили `StartsWith` и попадали в
  > `Remove-Item -LiteralPath -Recurse -Force` — то же удаление профиля целиком.
  >
  > Это третий блокер одного класса (после уязвимостей №1 и №2 — путь из манифеста в `rm -rf`),
  > поэтому требованием стала не заплатка в сравнении, а **единая нормализация всех путей**
  > (N5-P9), строгая вложенность и дублирующая проверка в цикле удаления. Требование: любая форма,
  > схлопывающаяся в сам домашний каталог, отвергается кодом `2` до первой файловой операции,
  > домашний каталог и всё его содержимое остаются нетронутыми (AC-143).

- **N5-R3. Удаление того, чего нет.** `--uninstall` на системе, где ничего не установлено, — не
  ошибка: каждый отсутствующий объект даёт строку «`<объект>`: не найден», код выхода `0`. Повторный
  `--uninstall` идемпотентен так же, как установка (N5-U1).

- **N5-R4. `--purge` без `--uninstall`.** Ошибка аргументов: сообщение «`--purge` применяется только
  вместе с `--uninstall`», код `2`, ничего не удалено (N5-I1).

## 8. Правила: проверка без установки (N5-C*)

- **N5-C1. `--dry-run`.** Печатается нумерованный план шагов с абсолютными путями и конкретными
  значениями (какой файл куда копируется, какой профиль правится, какая переменная в какое значение
  ставится, что запускается для Desktop). Ни один файл и ни один каталог не создаётся, не изменяется
  и не удаляется; переменные окружения не пишутся; внешние установщики не запускаются. Проверка
  манифеста (N5-P4) и sha256 (N5-P5) выполняется — их провал даёт код `2`/`4` и в этом режиме.
  Успешный `--dry-run` завершается кодом `0`. `--dry-run` работает и вместе с `--uninstall`
  (план удаления) и с `--system` (план с путями `/usr/local/bin`, без вызова `sudo`).

- **N5-C2. `--check`: построчный контракт вывода.** Формулировки строк — часть контракта (как
  S-A11a в форке): на них опираются тесты N5-T3 и дымовая проверка CI, поэтому они правятся
  одновременно здесь, в тестах и в CI, а тесты сверяются с подстроками из одного источника констант.

  | Условие | Строка |
  |---|---|
  | всегда | `Пакет: opencode-magnit <version> (<os>-<arch>)` |
  | всегда | `Манифест: корректен` |
  | бинарник найден, версия получена | `Бинарник: установлен <version> (<путь>)` |
  | бинарник найден, версия отличается | `Бинарник: другая версия (установлена <a>, в пакете <b>)` |
  | бинарник найден, `--version` не отработал | `Бинарник: установлен, версия не определена (<путь>)` |
  | бинарника нет | `Бинарник: не установлен` |
  | `bin_dir` в PATH | `PATH: содержит <bin_dir>` |
  | `bin_dir` не в PATH | `PATH: не содержит <bin_dir>` |
  | CA совпадает с пакетом | `CA: установлен (<путь>)` |
  | CA есть, хеш отличается | `CA: отличается от пакета (<путь>)` |
  | CA нет | `CA: не установлен` |
  | переменная равна нашему пути | `NODE_EXTRA_CA_CERTS: задан (<путь>)` |
  | переменная задана иначе | `NODE_EXTRA_CA_CERTS: задан другой путь (<путь>)` |
  | переменной нет | `NODE_EXTRA_CA_CERTS: не задан` |
  | Desktop установлен | `Desktop: установлен (<путь>)` |
  | Desktop есть в пакете, но не установлен | `Desktop: не установлен` |
  | Desktop не входит в пакет | `Desktop: не входит в пакет` |
  | всегда | `Конфиг: <путь> (не изменяется установщиком)` |
  | всегда | `Hub: <hub_url>` |
  | расхождений нет | `Итог: всё установлено` |
  | есть расхождения | `Итог: требуется установка` |

  Версия установленного бинарника определяется запуском `"<путь>" --version`; неуспех запуска или
  ненулевой код — не ошибка `--check`, а строка «версия не определена».

  **Источник данных для строк (ревизия 1.1).** Общее правило: `--check` отвечает на вопрос
  «установлено ли», а не «видит ли это текущая сессия shell». Поэтому:

  - **`NODE_EXTRA_CA_CERTS` (macOS/Linux).** Строка относится к переменной текущего процесса **и** к
    содержимому нашего блока в профиле: если блок есть, переменная считается заданной, даже если
    текущая сессия его ещё не прочитала.
  - **`PATH` (macOS/Linux).** Так же: `PATH: содержит <bin_dir>` печатается, если `bin_dir` входит в
    `$PATH` текущего процесса **либо** упоминается в нашем маркированном блоке файла профиля.
    Признак определяется именно по нашему блоку (наличие маркеров + строка с `bin_dir` внутри), а не
    по произвольному упоминанию каталога в файле. Без этой поблажки `--check`, выполненный сразу
    после установки в том же процессе, всегда печатал бы «не содержит» — что и фиксирует AC-100.
  - **`Desktop` (Windows).** Подставляется не путь на диске, а значение `DisplayTarget` записи
    деинсталляции: `InstallLocation`, если оно в реестре есть, иначе `DisplayName`. Установщик не
    ставит Desktop сам и не знает его каталога — единственный достоверный источник — реестр. То же
    значение используется в строке отчёта `--uninstall` (N5-R1), чтобы вывод был согласован.
    На macOS в этой строке — обычный путь к `.app`.

- **N5-C3. Коды выхода `--check`.** `0` — все проверки в состоянии «установлено и совпадает»
  (Desktop, отсутствующий в пакете, расхождением не считается). `7` — хотя бы одно расхождение.
  `2`/`3`/`4` — как обычно (манифест, среда, хеш файлов пакета). `--check` не создаёт ни одного файла,
  не требует прав на запись и работает на системе, где ничего не установлено (там `7`).

- **N5-C4. Ни один диагностический режим не меняет систему.** `--help`, `--version`, `--check`,
  `--dry-run` не создают каталогов (включая `<config_dir>` и `bin_dir`), не правят профиль, не
  пишут переменные и не запускают внешние установщики. Проверяется сравнением снимка файловой
  системы фейкового `$HOME` до и после (N5-T3).

## 9. Правила: сборка пакета для портала (N5-B*)

- **N5-B1. Интерфейс `installers/release.sh`.**
  `release.sh --artifacts <dir> --version <ver> --ca <file> --hub-url <url> [--out <dir>]
  [--targets darwin-arm64,darwin-x64,linux-x64,windows-x64] [--publish]`.
  `--artifacts` — локальный каталог с уже собранными артефактами CI форка; `--out` по умолчанию
  `installers/dist`; `--targets` по умолчанию все четыре цели. Отсутствие любого обязательного
  аргумента → справка в stderr и код `2`.

  **Валидация `--version` (ревизия 1.1).** Значение обязано проходить ту же проверку формата, что и
  поле `version` в `manifest.schema.json`: регулярное выражение
  `^[0-9]+\.[0-9]+\.[0-9]+-magnit\.[0-9]+$` (например `1.17.9-magnit.1`). Несоответствие →
  сообщение с указанием ожидаемого формата и полученного значения, код выхода `2`, ни один пакет не
  собирается. Без этой проверки собрался бы пакет, не проходящий собственную схему: молчаливый
  выпуск такого пакета запрещён.

  **Экранирование строк в манифесте (ревизия 1.1; уточнено в ревизии 1.3).** Все строковые
  значения, которые скрипт подставляет в генерируемый `common/manifest.json` (в частности
  `--hub-url`, `--version`, имя desktop-файла и `app_name`), экранируются по правилам JSON:
  обратный слэш и двойная кавычка заменяются на `\\` и `\"`. Кавычка или слэш в аргументе не должны
  приводить к синтаксически битому манифесту.

  Требование сформулировано по результату, а не по списку символов: **при любом значении аргумента
  собранный `common/manifest.json` обязан быть валидным JSON по RFC 8259** — то есть проходить
  разбор строгим парсером, а не только самодельным awk-разбором `install-posix.sh`. Поэтому
  экранированию подлежат и управляющие символы (перевод строки, возврат каретки, табуляция и прочие
  с кодом ниже `0x20`), которые внутри строкового литерала JSON запрещены. Допустимая
  альтернатива — отвергнуть такое значение аргументной проверкой до сборки с кодом `2` (как это
  сделано для `--version`); недопустим только исход «код выхода `0` и невалидный манифест».
  Требование распространяется не только на синтаксис, но и на **сохранность значения**: строка,
  прошедшая через экранирование, сборку и разбор манифеста, обязана совпадать с исходной
  **побайтово** — ни один символ не потерян, не заменён и не удвоен. Молчаливая потеря символа
  (например, вырезанный перевод строки) недопустима наравне с битым JSON.

  Самопроверка собранного пакета (N5-B2) остаётся обязательной и после этого — она вторая линия
  защиты, а не замена экранированию. С ревизии 1.4 она этот класс поломок **ловит**: собранный
  `common/manifest.json` разбирается строгим парсером (`python3`), а при недоступном `python3`
  печатается предупреждение и выполняется побайтовая проверка на сырые управляющие символы
  (`bugs/BUG-I5-001.json` закрыт; состав шагов — N5-B2).

- **N5-B2. Сборка пакета.** Для каждой цели скрипт: находит артефакт CLI — принимается либо
  `opencode-<os>-<arch>-<ver>.zip`, либо распакованный каталог `opencode-<os>-<arch>/bin/opencode`
  (имена — по S-B2 форка, где `win32` в имени каталога записывается как `windows`); собирает дерево
  N5-P2; кладёт CA из `--ca`, установщики из `installers/`, `README.md` (N5-D3); вычисляет sha256
  всех файлов и генерирует `common/manifest.json` (N5-P3) с `version`, `hub_url`, `source_release =
  v<ver>`, `built_at`, `purge_paths` по умолчанию; упаковывает: `tar.gz` для `darwin`/`linux` с
  сохранением бита `+x` на `install.sh` и на `bin/opencode`, `zip` для `windows`. Desktop-артефакт
  (`*.dmg` для `darwin-arm64`, `*.exe`/`*.msi` для `windows-x64`) добавляется, если найден в
  `--artifacts`; для `linux-x64` и `darwin-x64` Desktop не собирается форком (S-B3) и в пакет не
  кладётся. Если версия в имени найденного артефакта не совпадает с `--version` — ошибка с обоими
  значениями, код `2`.

  **Самопроверка собранного пакета (состав уточнён в ревизии 1.4).** После упаковки скрипт
  распаковывает архив во временный каталог и выполняет по распакованному дереву:

  1. сверку sha256 файлов `bin/opencode` (`bin/opencode.exe` для Windows) и
     `certs/tander-ca-bundle.pem` со значениями, попавшими в манифест;
  2. **строгий разбор `common/manifest.json`** сторонним парсером (`python3`, `json.load`) — именно
     этот шаг ловит провал экранирования по N5-B1. Если `python3` на сборочной машине недоступен,
     шаг не пропускается молча: печатается предупреждение вида «python3 недоступен — манифест
     `<пакет>` проверен только на управляющие символы», и вместо строгого разбора выполняется
     побайтовая проверка того, что в файле нет сырых управляющих символов (RFC 8259 запрещает их в
     строковых литералах; допускается только перевод строки — манифест печатается многострочным, а
     отступы пробельные). Условие «нет `python3` — нет проверки и нет сообщения» запрещено;
  3. прогон установщика из распакованного пакета с `--dry-run` в изолированном `$HOME`; для пакета
     чужой ОС допустим код `3` («пакет для другой ОС», N5-I3), для Windows-пакета при недоступном
     `pwsh` проверяется только манифест.

  Любой непройденный шаг — ошибка сборки, и **архив цели удаляется из каталога `--out`**:
  печатается «Архив не прошёл самопроверку и удалён из каталога сборки: `<путь>`», `SHA256SUMS` не
  создаётся, код выхода `1`. Битый архив не должен оставаться рядом с годными: перепутать их проще,
  чем заметить сообщение об ошибке в журнале сборки.

- **N5-B3. `SHA256SUMS` и публикация.** Рядом с архивами создаётся один файл `SHA256SUMS` в формате
  `sha256sum` (`<хеш>  <имя архива>`), включающий все собранные архивы. Публикация выполняется только
  по явному флагу `--publish` (как S-B4 в форке): черновик GitHub Release приватного репозитория
  тегом `v<ver>` с архивами и `SHA256SUMS`; без флага скрипт печатает «публикация пропущена: добавьте
  --publish». Выкладка на портал AI Lab — ручная, описывается в `install-admin.md` (N5-D2, D-8).

- **N5-B4. Отсутствующий артефакт — ошибка, не пропуск.** Если для запрошенной цели в `--artifacts`
  нет CLI-артефакта, скрипт завершается ненулевым кодом и печатает список ожидаемых имён файлов.
  Молчаливый пропуск цели запрещён (то же правило, что S-B3 в форке).

- **N5-B5. Границы `release.sh`.** Скрипт не собирает форк (не вызывает `bun`, `corp/build.ts`), не
  скачивает артефакты из сети (вход — только локальный каталог) и не подписывает сборки (R-14, S-B9).
  Все три случая при попытке использования дают понятное сообщение со ссылкой на нужный инструмент.

## 11. Правила: тесты и CI (N5-T*)

- **N5-T1. bats: размещение и изоляция.** Тесты POSIX-установщика лежат в
  `installers/tests/bats/*.bats` и запускаются командой `bats installers/tests/bats`. Каждый тест
  выполняется в собственном временном каталоге: `HOME` и корень установки подменяются
  (`HOME="$BATS_TEST_TMPDIR/home"`, `--prefix "$BATS_TEST_TMPDIR/opt"`), `SHELL` задаётся явно.
  Тесты не вызывают `sudo`, не пишут вне временного каталога, не обращаются в сеть и не зависят от
  наличия настоящего OpenCode: «бинарник» в фикстурном пакете — крошечный shell-скрипт, печатающий
  версию по `--version` и строки `corp status` по `corp status`. Фикстурные пакеты и манифесты
  собираются вспомогательной функцией в `installers/tests/fixtures/`, хеши в манифесте считаются на
  лету — захардкоженных sha256 в тестах нет (кроме тестов на заведомо неверный хеш).

  **Штатное имя бандла задаётся параметром, а не `sed`-подстановкой по литералу (ревизия 1.5).**
  Фабрика фикстурного манифеста (`installers/tests/bats/helpers.bash`, поле `app_name`) — единственное
  место, где задано штатное значение; тесты, которым нужно другое имя, получают его **параметром
  фабрики**. Подстановка вида `sed 's/"app_name": "OpenCode.app"/…/'` запрещена: при смене штатного
  имени (переименование бандла в `OpenCode Magnit.app`) такое выражение перестаёт совпадать и
  **молча** ничего не меняет — `sed` не возвращает ошибки, тест остаётся зелёным и проверяет не то,
  что заявлено в его имени. То же относится к Pester-фабрике `New-ManifestPackage -AppName`.

- **N5-T2. Pester: что проверяется вне Windows.** `install.ps1` написан так, что его можно
  загрузить через dot-source без выполнения действий: весь исполняемый вход обёрнут условием вида
  `if ($MyInvocation.InvocationName -ne '.') { Invoke-Main @PSBoundParameters }`. Благодаря этому на
  `pwsh` под macOS/Linux (`Invoke-Pester installers/tests/pester`) проверяются: разбор и валидация
  аргументов и взаимоисключающих комбинаций, валидация манифеста, вычисление и сравнение sha256,
  построение плана шагов, текст `--dry-run` и построчный вывод `--check`, коды выхода. Работа с
  реестром, пользовательским PATH, переменными пользователя, `WM_SETTINGCHANGE`, замена занятого
  `opencode.exe` и тихая установка Desktop проверяются только на Windows и помечаются в
  `acceptance-criteria.yaml` типом `manual` (стенд — D-9); соответствующие функции изолированы за
  тонкими обёртками, которые в тестах подменяются моками (`Mock`).

  **Чем подтверждается Windows-часть (ревизия 1.5).** Ветки набора, которым нужна семантика путей
  Windows, на не-Windows помечаются `Set-ItResult -Skipped`, поэтому автоматикой они подтверждаются
  **только** заданиями `pester-pwsh` (`windows-latest`) и `pester-ps51` эталонного workflow GitHub
  Actions, где пропуски запрещены. Пайплайн `.gitlab-ci.yml` их не подтверждает: Windows-раннеров в
  корпоративном GitLab нет (N5-T4).

- **N5-T3. Обязательные сценарии.** Набор тестов покрывает как минимум: чистую систему; повторный
  запуск (идемпотентность, N5-U1); обновление с `.bak` (N5-U2); совпадение хеша → пропуск (N5-U3);
  существующий пользовательский `opencode.json` → создаётся ровно один `.bak`, файл не изменён
  (N5-I11); `--dry-run` и `--check` не меняют ФС (N5-C4, сравнение снимка каталога до/после);
  `--check` на чистой системе → код `7`; `--uninstall` и повторный `--uninstall` (N5-R1, N5-R3);
  `--purge` удаляет ровно перечисленные пути (N5-R2), а формы `purge_paths`, схлопывающиеся в сам
  домашний каталог (`~/`, `~//`, `${HOME}//`, `${HOME}/.`, `${HOME}/./`, `${HOME}/sub/..`),
  отвергаются с канарейкой внутри `$HOME` и сравнением снимка каталога до и после (N5-R2, N5-P9).
  Негативные сценарии обязательны:
  **неверный sha256** → код `4`, ничего не установлено; **повреждённый/отсутствующий манифест**
  (не-JSON, `schema: 2`, отсутствующее поле, `sha256` неверной длины, `file` с `..`) → код `2`;
  **несовпадение ОС/архитектуры** → код `3`; **нет утилиты хеширования** → код `3`; **нет прав на
  запись** в `bin_dir` → код `5`; **занятый бинарник на Windows** → код `6` (`manual`);
  **`--purge` без `--uninstall`** → код `2`; **неизвестный аргумент** → код `2`; **отсутствие сети** —
  полный прогон установки в среде без сети завершается кодом `0` (N5-P6).

- **N5-T4. CI (состав уточнён в ревизии 1.5).** Эталонный workflow лежит в
  `installers/ci/installers.yml` и содержит **шесть** заданий:

  | Задание | Где | Что делает |
  |---|---|---|
  | `bats` | матрица `ubuntu-latest`, `macos-latest` | `bats installers/tests/bats` — Linux- и macOS-ветка `install-posix.sh`, заодно bash 3.2 (N5-T5) |
  | `pester-pwsh` | матрица `ubuntu-latest`, `windows-latest`; оболочка `pwsh` (PowerShell 7) | `Invoke-Pester installers/tests/pester`; на `windows-latest` пропуски запрещены |
  | `pester-ps51` | `windows-latest`; оболочка `powershell` (встроенный Windows PowerShell 5.1) | тот же набор на целевой версии `install.ps1` (`#Requires -Version 5.1`, N5-T5); пропуски запрещены |
  | `lint` | `ubuntu-latest` | `shellcheck -s bash` для всех `*.sh` и `Invoke-ScriptAnalyzer` для `*.ps1`/`*.psm1` |
  | `release-dry-run` | `ubuntu-latest` | прогон `release.sh` на фикстурных артефактах и `--dry-run` собранного пакета (N5-B2) |
  | `installers-required` | `ubuntu-latest`, `needs: [bats, pester-pwsh, pester-ps51, lint, release-dry-run]` | агрегирующее задание: единственный required-check PR, ждёт все ветки матриц |

  Обязательны все три комбинации Pester: **ubuntu + pwsh**, **windows + pwsh**, **windows +
  PowerShell 5.1**. Первая — среда, в которой набор гоняется ежедневно; вторая и третья закрывают
  ветки, зависящие от семантики путей Windows, и расхождение между двумя оболочками Windows.

  **Почему три комбинации разведены по двум заданиям, а не заданы матрицей оболочек.** Оболочку
  нельзя выбирать выражением: `shell: ${{ matrix.shell }}` GitHub отвергает **workflow целиком** —
  прогон падает на старте, не создаётся ни одного задания, и в API нет внятной ошибки (проверено
  пробными прогонами). Поэтому оболочка в каждом задании задаётся **литералом** (`shell: pwsh`,
  `shell: powershell`), а матрица различает только площадку и флаги. Наличие в файле подстроки
  `shell: ${{` — дефект, а не стилистика (AC-128).

  **Пропуски на Windows запрещены.** Часть тестов набора (`PathSafety.Tests.ps1` и части
  AC-136/AC-139/AC-140) на не-Windows помечается `Set-ItResult -Skipped`, потому что схлопывание
  форм вида `%USERPROFILE%\.` выполняет только Windows-реализация `[IO.Path]::GetFullPath`. На
  Windows-раннерах такие пропуски означают, что Windows-ветка требований опять не подтверждена,
  поэтому оба Windows-задания завершаются **ошибкой**, если `SkippedCount > 0`: в лог печатается
  полный путь каждого пропущенного теста, код выхода `1`. Пустой прогон (`PassedCount < 1`) — тоже
  красный: «набор не нашёлся» не должно выглядеть как «всё зелено».

  Любое падение любого задания валит PR. Файл в `.github/workflows/` копирует человек: каталог
  `.github/` объявлен защищённым в `pipeline.config.yaml` и агентам недоступен; несоответствие
  `installers/ci/installers.yml` и установленного workflow отслеживается вручную.

  **Второй пайплайн: `.gitlab-ci.yml` (ревизия 1.5).** В корне репозитория лежит портированный на
  корпоративный GitLab пайплайн (`gates`, `bats`, `pester`, `lint-shell`, `lint-powershell`,
  `release-dry-run`). Он существует потому, что прогоны GitHub Actions на приватном репозитории
  упираются в платные минуты Windows (×2) и macOS (×10). **Windows- и macOS-раннеров в нём нет**:
  `bats` гоняется только на Linux, `pester` — только под `pwsh` в контейнере Linux, и ветки,
  требующие семантики путей Windows, там штатно помечаются `Skipped` (запрет пропусков к этому
  заданию не применяется). Отсюда явное правило об источнике подтверждения:

  | Требование | Чем подтверждается автоматикой |
  |---|---|
  | Windows-ветки (AC-136, AC-139, AC-140, Windows-часть AC-135/AC-143, PowerShell 5.1 по N5-T5) | **только** GitHub Actions: задания `pester-pwsh` (`windows-latest`) и `pester-ps51` |
  | macOS-ветка `install-posix.sh` и совместимость с bash 3.2 (N5-T5) | **только** GitHub Actions: задание `bats` на `macos-latest` |
  | Всё остальное (Linux-ветка bats, Pester под pwsh, линт, `release-dry-run`, гейты G1–G6) | оба пайплайна |

  Утверждать в документации и в отчётах, что Windows-требования «подтверждаются CI», без указания,
  каким именно пайплайном, запрещено: зелёный прогон GitLab Windows-ветку не проверяет вовсе.
  `.gitlab-ci.yml`, как и `.github/`, ведёт человек — агентам он недоступен.

- **N5-T5. Совместимость языков.** `install-posix.sh`, лончеры и `release.sh` совместимы с
  **bash 3.2** (штатный bash macOS): запрещены ассоциативные массивы (`declare -A`), `mapfile`/
  `readarray`, `${var^^}`/`${var,,}`, `local -n`, `&>>`, `${!prefix@}`, `**` в globstar. Разрешены
  `set -euo pipefail`, `[[ ]]`, функции, `printf`. Проверяется `shellcheck -s bash` без подавлений
  (точечные `# shellcheck disable=` допускаются только с комментарием-обоснованием) и запуском
  bats на macOS-раннере. `install.ps1` совместим с **PowerShell 5.1**: `#Requires -Version 5.1`,
  без тернарного оператора `? :`, без `??`/`?.`, без `ForEach-Object -Parallel`, без `Join-String`,
  без `$PSStyle`; проверяется `Invoke-ScriptAnalyzer` с правилом совместимости и запуском на стенде
  (D-9).

- **N5-T6. Кодировки файлов.** `install.ps1` сохраняется в UTF-8 **с BOM** — иначе PowerShell 5.1
  читает файл в кодировке системы и русские строки отчёта превращаются в мусор. `install.bat`
  содержит только символы ASCII (все сообщения — в `install.ps1`). Файлы `*.sh` — UTF-8 без BOM с
  переводами строк `LF` (BOM в начале shell-скрипта ломает shebang). Проверяется отдельным тестом
  и заданием `lint` в CI.

## 12. Раздел H5-*: бэклог Hub из `reports/review-i3-2.json`

> **Зона реализации — репозиторий Hub, ветка I-3+.** Правила H5-* реализуются в worktree
> `/Users/miroslavshishenkov/Documents/opencode-mcp-hub-i3` (ветка `pipeline/i3-hub-oauth-facade-proxy`
> или ветка, созданная от неё), в файлах `src/hub/proxy.py` и `src/hub/routes/oauth.py`. К
> установщикам они отношения не имеют; их критерии приёмки вынесены в отдельный раздел
> `hub_backlog_criteria` (идентификаторы `HAC-*`) и в общий набор AC I-5 не входят. Все четыре
> находки в `review-i3-2.json` имеют `severity: minor`, `must_fix: false`.

- **H5-1. TTL права на пробу circuit-breaker.** Правило R-P10 уточняется: TTL ключа
  `cb:<alias>:probe` перестаёт равняться `HUB_CB_RESET` и вычисляется как
  `max(HUB_CB_RESET, HUB_UPSTREAM_TIMEOUT, HUB_UPSTREAM_SSE_IDLE_TIMEOUT) + HUB_CB_PROBE_GRACE`, где
  `HUB_CB_PROBE_GRACE` — новая настройка, по умолчанию `5.0` секунды, `gt=0`. Значение `until` в
  записи пробы равно `now + <этот TTL>` и продолжает использоваться для `Retry-After` отказов в
  half-open (`max(until - now, 1.0)`). Наблюдаемая гарантия: пока пробный запрос не завершился —
  сколько бы он ни длился, вплоть до таймаута SSE, — право на пробу второй раз не выдаётся, и на
  лежащий upstream не уходит вторая проба; все прочие запросы получают 503 + JSON-RPC `-32004`
  `upstream_unavailable`. Длинный TTL не задерживает восстановление: право снимается сразу по
  завершении пробы (`record_success` — H5-3, `record_failure` — существующее удаление ключа).

- **H5-2. Валидация `X-Forwarded-For`.** Правило R-T5 уточняется: при `HUB_TRUST_PROXY=true` левое
  значение заголовка принимается, только если оно является корректным IP-адресом
  (`ipaddress.ip_address()`, IPv4 или IPv6; квадратные скобки и суффикс `:<port>` у IPv6/IPv4
  отбрасываются до разбора). До разбора значение длиннее 45 символов (максимальная длина текстового
  представления IPv6) отбрасывается без попытки парсинга. Некорректное значение → откат на
  `request.client.host`, а при его отсутствии — `"unknown"`; факт отклонения пишется в лог уровня
  `WARNING` **без самого значения** (только длина и имя заголовка, R-T4/R-K3). Тем самым в ключи
  `rl:register:<ip>` и `rl:token:<client_id>:<ip>` не попадают произвольные строки клиента: ни обхода
  лимита регистрации подстановкой мусора, ни неограниченной кардинальности и длины ключей Redis.
  Поведение при `HUB_TRUST_PROXY=false` не меняется: заголовок игнорируется полностью.

- **H5-3. Лишний `delete` на горячем пути `record_success`.** `CircuitBreaker.record_success`
  перестаёт безусловно удалять `cb:<alias>:probe`. Удаление выполняется только когда выключатель
  фактически был открыт или в half-open — признак берётся из записи `cb:<alias>`, уже прочитанной в
  `check()`, и передаётся вызывающим кодом (например, параметром `was_open: bool = False`); допустима
  альтернатива — объединение обеих операций KV в одну транзакцию/pipeline. Наблюдаемое поведение
  R-P10 не меняется ни в одном состоянии выключателя. Проверяемое следствие: в закрытом состоянии на
  один успешно проксированный запрос приходится ровно одна операция записи в KV и ноль операций
  удаления (считается счётчиком операций фейкового KV в тесте).

- **H5-4. Упрощение `record_failure`.** В ветке повторного открытия окна (`open_until > 0.0`)
  вместо `failures = max(failures, self.settings.cb_failures)` записывается
  `failures = self.settings.cb_failures`: счётчик в этой ветке никогда не превышает порог, поэтому
  `max` — эквивалентная страховка, скрывающая намерение (мутанты M6/M11 из `review-i3-2` эквивалентны
  именно из-за неё). Окно по-прежнему открывается немедленно на `HUB_CB_RESET` секунд, ключ пробы
  удаляется. Наблюдаемое поведение AC-151 спецификации I-3 (не путать с AC-151 этого набора) не меняется; после провала пробы состояние в KV равно
  `{failures: HUB_CB_FAILURES, open_until: now + HUB_CB_RESET}` и читается через `state()`.
