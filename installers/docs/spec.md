## 1. Назначение

Итерация I-5 даёт то, что пользователь скачивает с портала и запускает:

1. **пакет на ОС/архитектуру** — корпоративная сборка OpenCode (CLI/TUI), корпоративный CA-bundle,
   при наличии — Desktop-установщик, манифест с хешами и установщик;
2. **установщик** (`install.sh` для macOS/Linux, `install.ps1` + `install.bat` для Windows) —
   ставит CA, бинарник в PATH, Desktop; ничего не спрашивает, ключей не просит, пользовательский
   конфиг не меняет; идемпотентен; умеет `--dry-run`, `--check`, `--uninstall`, `--purge`;
3. **`installers/release.sh`** — сборка пакетов из готовых артефактов CI форка;
4. **документацию** для пользователя и для администратора.

Отдельным разделом (§11) идёт бэклог Hub по `reports/review-i3-2.json` — правила `H5-*`. Они
**реализуются в репозитории Hub, в ветке от `pipeline/i3-hub-oauth-facade-proxy`** (I-3+), к
установщикам отношения не имеют и в общий набор AC I-5 не смешиваются (для них — отдельный раздел
`hub_backlog_criteria` с идентификаторами `HAC-*`).

### 1.1. Границы объёма

**Входит:** структура пакета и манифест; установщики трёх ОС; идемпотентность/обновление/откат;
удаление; `--dry-run`/`--check`; `release.sh`; тесты bats/Pester; эталонный файл CI; документация RU.

**Не входит:**
- скачивание артефактов из сети — установщик и `release.sh` работают только с локальными файлами
  (N5-P6, N5-B5); сборка форка (`bun run corp/build.ts`) — предмет I-4;
- подпись Windows Authenticode и macOS Developer ID / notarization — решение ИБ (R-14, D-7, S-B9);
  вместо подписи — документированный обход предупреждений ОС (N5-D1), только для пилота;
- `.pkg` для macOS (в I5-01 помечен как опциональный) — не делаем, ставим бинарник напрямую;
- Desktop для Linux — форк его не собирает (S-B3: цели `mac-arm64` и `win-x64`);
- импорт CA в системное хранилище сертификатов ОС (это изменение системных настроек, требует
  прав администратора и согласования ИБ) — ставится только пользовательская копия CA и
  пользовательская переменная окружения;
- интеграция с порталом (карточка загрузок, автообновление) — ручная выкладка AI Lab, D-8.

## 2. Входы и выходы

**Входы установщика:** каталог распакованного пакета (см. N5-P2) рядом со скриптом; аргументы
командной строки (N5-I1); окружение пользователя (`$HOME`, `$SHELL`, `XDG_CONFIG_HOME`,
`%USERPROFILE%`, `%LOCALAPPDATA%`, `PATH`, `NODE_EXTRA_CA_CERTS`).

**Выходы установщика:** файлы в домашнем каталоге пользователя и (при `--system`) в `/usr/local/bin`;
маркированный блок в файле профиля shell; пользовательские переменные окружения Windows; строки
отчёта в stdout, ошибки в stderr; код выхода (N5-I1).

**Входы `release.sh`:** локальный каталог с артефактами CI форка; версия; CA-файл; адрес Hub.
**Выходы `release.sh`:** архивы `opencode-magnit-<os>-<arch>-<ver>.tar.gz|zip`, `SHA256SUMS`.

## 3. Правила: пакет, манифест, репозиторий (N5-P*)

- **N5-P1. Состав каталога `installers/` в репозитории.** Обязательные пути:

  | Путь | Назначение |
  |---|---|
  | `installers/common/install-posix.sh` | единственная реализация установщика для macOS и Linux |
  | `installers/common/manifest.schema.json` | JSON-схема манифеста (N5-P3), используется тестами |
  | `installers/common/manifest.example.json` | пример заполненного манифеста |
  | `installers/macos/install.sh` | лончер: определяет свой каталог и передаёт управление `install-posix.sh` |
  | `installers/linux/install.sh` | то же для Linux |
  | `installers/windows/install.ps1` | установщик для Windows |
  | `installers/windows/install.bat` | тонкий лончер PowerShell (N5-I2) |
  | `installers/release.sh` | сборка пакетов (N5-B1) |
  | `installers/ci/installers.yml` | эталонный workflow CI (N5-T4) |
  | `installers/docs/spec.md`, `installers/docs/acceptance-criteria.yaml` | эта спецификация и AC |
  | `installers/docs/install-user.md`, `installers/docs/install-admin.md` | документация (N5-D1, N5-D2) |
  | `installers/tests/bats/` | тесты bats (N5-T1) |
  | `installers/tests/pester/` | тесты Pester (N5-T2) |
  | `installers/tests/fixtures/` | фикстуры: искусственные пакеты и манифесты |

  Логика установки для macOS и Linux не дублируется: `macos/install.sh` и `linux/install.sh`
  содержат только определение собственного каталога, установку `OPENCODE_INSTALLER_PLATFORM`
  (`macos`/`linux`) и вызов общего файла. Расхождения поведения между ОС выражаются внутри
  `install-posix.sh` ветвлением по этой переменной, а не двумя копиями скрипта.

- **N5-P2. Состав распространяемого пакета.** Пакет, который пользователь скачивает и распаковывает,
  самодостаточен: после распаковки установка выполняется без обращений к репозиторию, сети и
  внешним утилитам сверх базовых (N5-P6, N5-I3). Раскладка:

  ```
  opencode-magnit-<os>-<arch>-<ver>/
  ├── install.sh                (macOS/Linux; исполняемый бит выставлен)
  ├── install.ps1               (Windows)
  ├── install.bat               (Windows)
  ├── common/
  │   ├── manifest.json
  │   └── install-posix.sh      (только в POSIX-пакетах)
  ├── bin/
  │   └── opencode | opencode.exe
  ├── certs/
  │   └── tander-ca-bundle.pem
  ├── desktop/                  (только если Desktop входит в пакет)
  │   └── <штатный установщик Desktop>
  └── README.md                 (N5-D3)
  ```

  В POSIX-пакет кладутся только `install.sh` + `common/install-posix.sh`, в Windows-пакет —
  только `install.ps1` + `install.bat`. Установщик находит `common/manifest.json` относительно
  каталога, в котором лежит он сам, а не относительно текущего рабочего каталога: запуск из любого
  каталога (`bash /path/to/pkg/install.sh`) работает одинаково.

- **N5-P3. `manifest.json`.** Единственный источник правды о содержимом пакета. Поля:

  | Поле | Тип | Обязательное | Смысл |
  |---|---|---|---|
  | `schema` | целое | да | версия схемы, для I-5 ровно `1` |
  | `product` | строка | да | ровно `opencode-magnit` |
  | `version` | строка | да | версия сборки, формат `<upstream>-magnit.<N>` (S-B1), например `1.17.9-magnit.1` |
  | `os` | строка | да | `darwin` \| `linux` \| `windows` |
  | `arch` | строка | да | `arm64` \| `x64` |
  | `hub_url` | строка | да | адрес Hub, печатается в отчёте и в `--check`; установщик его никуда не записывает (адрес зашит в сборку, S-C2) |
  | `built_at` | строка | да | момент сборки пакета, ISO-8601 UTC |
  | `source_release` | строка | да | тег релиза форка, из которого взяты артефакты (`v<version>`, S-B4) |
  | `ca` | объект | да | `{file, sha256, install_name}` — CA-bundle |
  | `artifacts` | массив | да | элементы `{kind, file, sha256, size, ...}`, ровно один с `kind:"cli"`, не более одного с `kind:"desktop"` |
  | `purge_paths` | массив строк | да | пути, удаляемые при `--purge` (N5-R2); допускаются подстановки `~`, `${XDG_CONFIG_HOME}`, `${XDG_DATA_HOME}`, `%USERPROFILE%`, `%LOCALAPPDATA%` |

  Элемент `artifacts` с `kind:"cli"` дополнительно содержит `install_name` (`opencode` или
  `opencode.exe`). Элемент с `kind:"desktop"` дополнительно содержит `installer_type`
  (`dmg` \| `nsis` \| `msi`), `app_name` (для `dmg`, например `OpenCode.app`) и для Windows —
  `silent_args` (массив строк, например `["/S"]`).

  Все `file` — пути относительно корня пакета, с разделителем `/`, без ведущего `/`, без `..` и без
  букв дисков. Те же ограничения действуют на `ca.install_name`, `artifacts[].install_name` и
  `artifacts[].app_name`: в схеме все пять полей используют одно определение `pkgPath`, в
  установщике — одну функцию проверки (полный список и обоснование — N5-P4). Поле `url` в элементе
  `artifacts` допускается (I5-01) и является исключительно справочным: установщик его никогда не
  запрашивает (N5-P6).

- **N5-P4. Валидация манифеста.** До любых изменений системы установщик читает и проверяет манифест:
  файл существует и разбирается как JSON; `schema == 1`; `product == "opencode-magnit"`; все
  обязательные поля присутствуют и непусты; `os`/`arch` — из допустимых значений; каждый `sha256` —
  ровно 64 символа `[0-9a-f]` (сравнение регистронезависимое, значение приводится к нижнему
  регистру); каждое путевое поле проходит проверку пути, а каждый `file` дополнительно существует
  внутри пакета; ровно один артефакт `kind:"cli"`. Любое нарушение → ничего не изменено, сообщение
  с именем поля и путём к манифесту в stderr, код выхода `2`. То же для отсутствующего манифеста.

  **Путевые поля — полный список (ревизия 1.1).** Проверка пути (`is_safe_pkg_path` в
  `install-posix.sh`, `Test-PackagePath` в `install.ps1`) применяется ко **всем** полям манифеста,
  значение которых участвует в построении файловых путей:

  | Поле | Проверка пути | Дополнительно |
  |---|---|---|
  | `ca.file` | да | файл существует внутри пакета |
  | `ca.install_name` | да | — |
  | `artifacts[].file` | да | файл существует внутри пакета |
  | `artifacts[].install_name` (для `kind:"cli"`) | да | обязательно и непусто |
  | `artifacts[].app_name` (для `kind:"desktop"`) | да | проверяется, если поле задано |

  Проверка пути запрещает: `..` как отдельный сегмент (`..`, `../*`, `*/../*`, `*/..`), ведущий `/`,
  обратный слэш `\` в любой позиции, префикс с буквой диска (`C:`), пустое значение.

  **Момент проверки.** Вся валидация выполняется внутри `manifest_load` — то есть на шаге (2)
  порядка N5-I3 (разбор аргументов → манифест → ОС/архитектура → …), **до любой файловой операции**
  и до выбора режима. Поэтому она одинаково срабатывает на всех путях исполнения: установка,
  `--check`, `--dry-run`, **`--uninstall`** и **`--dry-run --uninstall`**. Ни один режим не имеет
  «облегчённой» загрузки манифеста; в частности, `--uninstall` не является исключением, хотя
  проверка хешей (N5-P5) на нём не выполняется.

  > **Исправление уязвимости (ревизия 1.1).** До ревизии 1.1 поле `artifacts[].app_name` было
  > единственной строкой манифеста, участвующей в файловых операциях и не проходящей проверку пути.
  > Оно подставляется в `rm -rf "<dest>/<app_name>"` при установке Desktop и в удаление
  > `/Applications/<app_name>` при `--uninstall`, поэтому подменённый манифест со значением вида
  > `../../<абсолютный путь>/victim` удалял произвольный каталог вне `/Applications`, а при
  > `--system` — от имени `root` через `sudo`. Требование: такое значение отвергается кодом `2` до
  > любых изменений системы, каталог-жертва остаётся нетронутым (AC-135). Схема
  > `common/manifest.schema.json` — вторая линия защиты: `app_name` использует то же определение
  > `pkgPath`, что `file` и `install_name`.

- **N5-P5. Обязательная проверка хеша.** Перед копированием/запуском любого файла из пакета
  (CLI-бинарник, CA, Desktop-установщик) установщик вычисляет его sha256 и сравнивает со значением
  из манифеста. Несовпадение → **отказ**: файл не копируется и не запускается, ранее выполненные
  шаги не откатываются, но и не продолжаются; сообщение содержит имя файла, ожидаемый и фактический
  хеш; код выхода `4`. Отключить проверку нельзя — флага «пропустить проверку хеша» не существует.
  Проверка выполняется и в режиме `--dry-run` (это только чтение), поэтому `--dry-run` пригоден как
  валидация целостности пакета.

  Хеш считается первой доступной утилитой из списка: `sha256sum`, `shasum -a 256`,
  `openssl dgst -sha256` (POSIX) и `Get-FileHash -Algorithm SHA256` (Windows). Если на POSIX нет ни
  одной — код выхода `3` с перечислением искомых утилит.

- **N5-P6. Установщик оффлайновый.** Шаги установки, удаления, `--dry-run` и `--check` не выполняют
  ни одного сетевого обращения: в исходниках установщиков нет вызовов `curl`, `wget`, `nc`,
  `Invoke-WebRequest`, `Invoke-RestMethod`, `System.Net.WebClient`, `git`, `npm`, `brew`, `apt`,
  `winget`, `choco`. Отсутствие сети не является ошибкой и не влияет на код выхода. Единственное
  исключение — информационный финальный шаг `opencode corp status` (N5-I12), который сетью
  пользуется, выполняется после всех изменений и на код выхода установщика не влияет.

- **N5-P7. Имена и версия.** Имя каталога и архива пакета —
  `opencode-magnit-<os>-<arch>-<version>`, где `os`/`arch`/`version` берутся из манифеста.
  Расширение: `.tar.gz` для `darwin` и `linux`, `.zip` для `windows` (N5-B2). Версия в имени, версия
  в манифесте и версия, которую печатает установленный бинарник (`opencode --version`), — одно и то
  же значение; расхождение имени архива и манифеста — ошибка сборки пакета (N5-B2), а не установки.

- **N5-P8. CA в пакете.** Файл `certs/tander-ca-bundle.pem` входит в каждый пакет, его sha256 — в
  манифесте (`ca.sha256`), имя устанавливаемого файла — `ca.install_name`
  (по умолчанию `tander-ca-bundle.pem`). Содержимое CA установщик не разбирает и не проверяет на
  валидность сертификатов — только целостность по хешу.

## 4. Правила: общий контракт установщика (N5-I1, N5-I2)

- **N5-I1. Аргументы, режимы и коды выхода.** Оба установщика (`install.sh` и `install.ps1`)
  поддерживают один и тот же набор режимов и одни и те же коды выхода.

  | POSIX | Windows | Смысл |
  |---|---|---|
  | `--dry-run` | `-DryRun` | напечатать план, ничего не менять (N5-C1) |
  | `--check` | `-Check` | проверить среду, ничего не менять (N5-C2) |
  | `--uninstall` | `-Uninstall` | удалить установленное (N5-R1) |
  | `--purge` | `-Purge` | вместе с `--uninstall` — удалить и пользовательские данные (N5-R2) |
  | `--system` | — | ставить в `/usr/local/bin` (N5-I7); на Windows не применимо |
  | `--prefix <dir>` | `-Prefix <dir>` | переопределить корень установки (используется тестами) |
  | `--no-desktop` | `-NoDesktop` | пропустить шаг Desktop |
  | `--no-launch` | `-NoLaunch` | не выполнять финальный `opencode corp status` |
  | `--quiet` | `-Quiet` | печатать только итог и ошибки |
  | `--help` | `-Help` | напечатать справку в stdout и выйти с кодом `0` |
  | `--version` | `-ShowVersion` | напечатать `opencode-magnit <version> (<os>-<arch>)` из манифеста и выйти с кодом `0` |

  Неизвестный аргумент → справка в stderr, код `2`, ничего не изменено. Взаимоисключающие
  комбинации (`--dry-run` с `--check`, `--check` с `--uninstall`, `--purge` без `--uninstall`,
  `--system` с `--prefix`) → сообщение и код `2`. Комбинация `--dry-run --uninstall` допустима и
  печатает план удаления. Интерактивных вопросов установщик не задаёт ни в одном режиме: значения по
  умолчанию выбираются сами, флага подтверждения нет.

  Коды выхода:

  | Код | Значение |
  |---|---|
  | `0` | успех; для `--check` — состояние полностью соответствует пакету |
  | `1` | непредвиденная ошибка выполнения (в т.ч. неуспех шага Desktop при установке — N5-I9/N5-I10 — и провал штатного деинсталлятора Desktop при `--uninstall` — N5-R1) |
  | `2` | ошибка входных данных: аргументы, отсутствующий или невалидный манифест (N5-P4) |
  | `3` | несовместимая среда: ОС/архитектура/версия PowerShell/нет утилиты хеширования (N5-I3) |
  | `4` | несовпадение sha256 (N5-P5) |
  | `5` | нет прав на запись в целевой каталог (N5-I7) |
  | `6` | целевой файл занят другим процессом (N5-I8) |
  | `7` | только для `--check`: обнаружены расхождения (N5-C3) |

  Весь пользовательский вывод — на русском языке. Секреты установщик не печатает и не читает: он не
  обращается ни к `auth.json`, ни к переменным с ключами, ни к `opencode.json`.

- **N5-I2. `install.bat`.** Тонкий лончер, единственная задача — запустить `install.ps1` рядом с
  собой в обход политики выполнения и вернуть его код выхода:
  `powershell -NoProfile -ExecutionPolicy Bypass -File "%~dp0install.ps1" %*` и затем
  `exit /b %ERRORLEVEL%`. Собственной логики (проверок, установки, вывода на русском) в `.bat` нет;
  содержимое файла — только символы ASCII (N5-T6). Аргументы передаются в PowerShell без изменений.

## 5. Правила: шаги установки (N5-I3…N5-I12)

Порядок шагов фиксирован: (1) разбор аргументов → (2) манифест (N5-P4) → (3) ОС/архитектура →
(4) CA → (5) CLI-бинарник и PATH → (6) Desktop → (7) пользовательский конфиг → (8) итог и первый
запуск. Шаг, завершившийся ошибкой с кодом `2`, `3` или `4`, останавливает установку до внесения
изменений в систему.

- **N5-I3. Проверка ОС и архитектуры.** POSIX: `uname -s` (`Darwin` → `darwin`, `Linux` → `linux`,
  прочее → отказ) и `uname -m` (`arm64`/`aarch64` → `arm64`; `x86_64`/`amd64` → `x64`; прочее →
  отказ). Windows: `windows` и `x64` при `$env:PROCESSOR_ARCHITECTURE -eq 'AMD64'`; ARM64-Windows и
  32-разрядная система → отказ (цели `win32-arm64` форк не собирает, S-B2). Несовпадение с `os`/`arch`
  манифеста → код `3`, сообщение вида «пакет собран для `<os>-<arch>`, система — `<os>-<arch>`»;
  запуск сборки `darwin-x64` на Apple Silicon через Rosetta молча не допускается — это тот же отказ.
  Дополнительно `install.ps1` требует PowerShell ≥ 5.1 (`#Requires -Version 5.1`); на более старой
  версии — код `3` с указанием найденной версии.

- **N5-I4. Установка CA-файла.** Каталог конфига:
  `${XDG_CONFIG_HOME:-$HOME/.config}/opencode` на macOS/Linux и `%USERPROFILE%\.config\opencode` на
  Windows (факт §3 `docs/req-mvp.md`). Каталог создаётся при отсутствии (права `0755` на POSIX).
  Файл `certs/<ca.file>` после проверки хеша (N5-P5) копируется в `<config_dir>/<ca.install_name>`
  с правами `0644`. Если файл уже есть и его sha256 совпадает с манифестом — копирование
  пропускается со строкой отчёта «CA: уже установлен». Если отличается — перезаписывается
  (предыдущая копия не сохраняется: это корпоративный CA, а не пользовательские данные).

- **N5-I5. `NODE_EXTRA_CA_CERTS` на macOS/Linux.** Значение записывается в файл профиля shell
  внутри маркированного блока:

  ```
  # >>> opencode-magnit >>>
  export NODE_EXTRA_CA_CERTS="<config_dir>/<ca.install_name>"
  export PATH="<bin_dir>:$PATH"
  # <<< opencode-magnit <<<
  ```

  Файл профиля выбирается по `$SHELL` (по имени исполняемого файла): `zsh` → `~/.zshrc`;
  `bash` → `~/.bash_profile` на macOS и `~/.bashrc` на Linux; `fish` →
  `~/.config/fish/conf.d/opencode-magnit.fish` (тем же блоком, но синтаксисом
  `set -gx NODE_EXTRA_CA_CERTS …` / `fish_add_path …`); всё прочее и пустой `$SHELL` → `~/.profile`.
  Редактируется **ровно один** файл. Отсутствующий файл создаётся.

  Идемпотентность: если блок с маркерами уже есть, его содержимое заменяется целиком, второй блок не
  добавляется; если блок уже содержит нужные строки — файл не изменяется вовсе (mtime не трогается).
  Перед первой вставкой блока делается резервная копия `<файл>.opencode-magnit.bak`; при
  последующих запусках она не перезаписывается.

  **Схлопывание задвоенного блока (ревизия 1.1).** Замена реализуется как «вырезать **все**
  маркированные блоки и дописать ровно один в конец», а не как правка первого найденного. Поэтому
  если в файле профиля по каким-то причинам оказалось два и более маркированных блока (например,
  после ручного копирования строк пользователем), очередной запуск установщика схлопывает их в один.
  Гарантия N5-U1 «в профиле ровно один маркированный блок» держится и при внешних правках файла.

  Строка `export PATH=…` добавляется в блок, только если `bin_dir` ещё не входит в `$PATH` текущего
  процесса.

  **Предупреждение о чужом `NODE_EXTRA_CA_CERTS` (уточнено в ревизии 1.1).** Чужим считается
  **присваивание** переменной вне нашего блока со значением, отличным от нашего пути: строки вида
  `NODE_EXTRA_CA_CERTS=…`, `export NODE_EXTRA_CA_CERTS=…`, `setenv NODE_EXTRA_CA_CERTS …`,
  `set -gx NODE_EXTRA_CA_CERTS …` (с начала строки, ведущие пробелы и табуляции игнорируются). Любое
  другое упоминание имени переменной предупреждения не вызывает — в частности,
  строка-комментарий (`# NODE_EXTRA_CA_CERTS больше не нужен`) и текст, где имя встречается внутри
  другой строки. Чужая строка не изменяется, но в отчёт добавляется предупреждение с именем файла и
  номером строки (наш блок дописывается в конец файла и потому имеет приоритет для новых сессий).

  Переменные окружения для GUI-процессов на macOS/Linux установщик не задаёт: штатного
  пользовательского механизма для этого нет, а изменение `launchd`/`systemd --user` окружения выходит
  за границы «без прав администратора». Desktop-сборка получает CA из файла в каталоге конфига
  (N5-I4). Ограничение печатается отдельной строкой отчёта и описывается в `install-admin.md`
  (N5-D2). **[проверить]** — подтверждается на стороне форка при первом прогоне сквозного сценария.

- **N5-I6. `NODE_EXTRA_CA_CERTS` на Windows.** Значение записывается в переменную **пользователя**:
  `[Environment]::SetEnvironmentVariable("NODE_EXTRA_CA_CERTS", "<config_dir>\<ca.install_name>", "User")`.
  Запись выполняется, только если текущее пользовательское значение отличается от целевого
  (иначе строка отчёта «NODE_EXTRA_CA_CERTS: уже задан»). Переменные уровня `Machine` не
  изменяются никогда, права администратора не требуются. Той же переменной пользуется и Desktop
  (Electron-сборка наследует пользовательское окружение), отдельной переменной для Desktop нет.
  Импорт CA в системное хранилище сертификатов не выполняется (§1.1).

- **N5-I7. CLI-бинарник и PATH на macOS/Linux.** Каталог назначения (`bin_dir`):
  `$HOME/.local/bin` по умолчанию; `/usr/local/bin` при `--system`; `<prefix>/bin` при `--prefix`.
  Каталог создаётся при отсутствии. Порядок: проверка sha256 (N5-P5) → копирование во временный файл
  `<bin_dir>/.opencode.new.<pid>` в том же каталоге → `chmod 0755` → атомарное переименование поверх
  цели. Копирование-с-переименованием обязательно: так уже запущенный процесс `opencode` не ломается,
  а частично записанного бинарника в PATH не появляется ни на одну секунду.

  Права: при отсутствии права на запись в `bin_dir` установщик **не** повышает права молча. Без
  `--system` он завершается кодом `5` с подсказкой. С `--system`: если процесс не root, а `sudo`
  доступен — привилегированные операции выполняются через `sudo` (создание каталога, перенос файла,
  `chmod`); если `sudo` недоступен или отказал — код `5` с текстом «нужны права root: запустите под
  root или без `--system` (установка в `$HOME/.local/bin`)». Установка по умолчанию (без `--system`)
  никогда не вызывает `sudo`.

  Если `bin_dir` не входит в `$PATH`, он добавляется в маркированный блок профиля (N5-I5) и в отчёт
  добавляется строка «откройте новый терминал».

- **N5-I8. CLI-бинарник и PATH на Windows.** Каталог назначения —
  `%LOCALAPPDATA%\Programs\opencode` (или `<Prefix>` при `-Prefix`), создаётся при отсутствии.
  Замена занятого файла: существующий `opencode.exe` сначала переименовывается в `opencode.exe.bak`
  (Windows позволяет переименовать запущенный исполняемый файл), затем записывается новый. Если
  переименование не удалось (файл заблокирован антивирусом или иным процессом) — код `6` с текстом
  «файл занят: закройте OpenCode и повторите запуск», новый файл не записывается.

  PATH пользователя правится через реестр `HKEY_CURRENT_USER\Environment`:
  значение читается с `RegistryValueOptions.DoNotExpandEnvironmentNames` (иначе `%…%` внутри PATH
  будут развёрнуты и запись их уничтожит) и записывается обратно с сохранением исходного
  `RegistryValueKind` (`ExpandString`, если он был таким). Каталог добавляется, только если его ещё
  нет: сравнение поэлементное, регистронезависимое, с отбрасыванием завершающего `\`. После записи
  рассылается `WM_SETTINGCHANGE` (`SendMessageTimeout`, `HWND_BROADCAST`, `"Environment"`,
  таймаут 5000 мс), чтобы новые процессы увидели изменение без перезахода в систему; неуспех рассылки
  — предупреждение, а не ошибка.

- **N5-I9. Desktop на macOS.** Если в манифесте есть артефакт `kind:"desktop"` с
  `installer_type:"dmg"` и не задан `--no-desktop`: проверка sha256 → `hdiutil attach -nobrowse
  -readonly` → копирование `<app_name>` через `ditto` в `/Applications` → `hdiutil detach`. Отмонтирование
  выполняется всегда, в том числе при ошибке копирования и при прерывании (ловушка на выходе):
  оставленный примонтированный образ — дефект. Существующее приложение перед копированием удаляется
  (для каталога `.app` резервная копия не делается — это сборка, а не пользовательские данные).
  При отсутствии прав на `/Applications`: с `--system` — через `sudo`; без него — установка в
  `~/Applications` и предупреждение в отчёте. Совпадение версии установленного приложения с версией
  пакета (`CFBundleShortVersionString` из `Info.plist`) → шаг пропускается со строкой «Desktop: уже
  установлен».

- **N5-I10. Desktop на Windows и его отсутствие.** Если есть артефакт `kind:"desktop"` и не задан
  `-NoDesktop`: проверка sha256 → запуск штатного установщика `Start-Process -Wait -PassThru` с
  аргументами из `silent_args` манифеста. Если `silent_args` в манифесте нет — установщик **не**
  угадывает ключи тихой установки: печатает путь к файлу и строку «Desktop: запустите установщик
  вручную», код выхода не меняется. Ненулевой код штатного установщика → строка
  «Desktop: ошибка (код `<n>`)» и общий код выхода `1`; при этом установка CLI и CA **не
  откатывается** — она уже завершена и работоспособна.

  Если артефакта `kind:"desktop"` в манифесте нет (Linux-пакет, CLI-only пакет) — шаг пропускается со
  строкой «Desktop: не входит в пакет», это не ошибка. При `--no-desktop` — строка
  «Desktop: пропущен (--no-desktop)».

- **N5-I11. Пользовательский конфиг и ключи.** Установщик **не создаёт и не изменяет**
  `<config_dir>/opencode.json`, не пишет туда адрес Hub, провайдера, модель и умолчания (это делает
  корпоративная сборка на уровне build-констант, S-C2/S-C3), не создаёт и не читает `auth.json`, не
  запрашивает и не сохраняет никаких ключей и токенов.

  Семантически сравнить пользовательский конфиг с корпоративными умолчаниями установщик не может и
  не пытается (разбора JSON нет), поэтому конфликтом считается сам факт существования файла: если
  `<config_dir>/opencode.json` существует и рядом ещё нет `opencode.json.bak`, создаётся резервная
  копия `opencode.json.bak` (страховка на случай, если будущая версия сборки изменит формат). При
  повторных запусках существующий `.bak` не перезаписывается — иначе он затрёт заведомо исправную
  копию. Отчёт содержит строку «Конфиг: `<путь>` (не изменялся)».

- **N5-I12. Итог и первый запуск.** После всех шагов установщик печатает отчёт фиксированного вида
  (регистр и порядок строк — часть контракта, на них опираются тесты N5-T3 и `--check`):

  ```
  Готово: OpenCode <version> установлен.
    Бинарник: <путь>
    CA: <путь>
    Desktop: <путь> | не входит в пакет | пропущен (--no-desktop) | ошибка (код <n>)
    Конфиг: <путь> (не изменялся)
    Hub: <hub_url>
  Дальше:
    1. Откройте новый терминал (или выполните: source <файл профиля>)
    2. Запустите: opencode
    Вход по корпоративному SSO предложат при первом запуске.
  ```

  Строка «1. Откройте новый терминал…» печатается только если установщик правил профиль или PATH.
  Затем, если не задан `--no-launch`, выполняется `"<bin_dir>/opencode" corp status` (S-A11): его
  вывод печатается как есть, а его код выхода **игнорируется** — сразу после установки ключа ещё нет,
  и `corp status` штатно возвращает `1` (S-A11, D-13). Автоматически ни `opencode`, ни Desktop
  установщик не запускает: он лишь печатает, что запускать.

## 6. Правила: идемпотентность, обновление, откат (N5-U*)

- **N5-U1. Идемпотентность.** Два подряд запуска установщика с одинаковыми аргументами оставляют
  одинаковое состояние: в профиле ровно один маркированный блок, в PATH ровно один экземпляр
  `bin_dir`, ровно одна пользовательская переменная `NODE_EXTRA_CA_CERTS`, ровно один
  `opencode.json.bak`, ровно один `opencode.bak`. Оба запуска завершаются кодом `0`. Ни один шаг не
  требует «чистой системы»: установка поверх уже установленного — штатный сценарий.

  Гарантия «ровно один маркированный блок» — не только про повторный запуск установщика: если в
  профиле уже оказалось несколько блоков, очередной запуск схлопывает их в один (N5-I5, ревизия 1.1).

- **N5-U2. Обновление.** Если установленный бинарник отличается от бинарника пакета, перед заменой
  он копируется в `<bin_dir>/opencode.bak` (Windows: переименовывается в `opencode.exe.bak`),
  перезаписывая предыдущий `.bak`; хранится ровно одна предыдущая версия. Откат — ручной:
  документируется в `install-admin.md` как переименование `.bak` обратно (N5-D2). Каталог конфига,
  `opencode.json`, `auth.json` и `opencode.json.bak` при обновлении не изменяются.

- **N5-U3. Пропуск при совпадении.** Если sha256 установленного бинарника совпадает с манифестом,
  шаг установки бинарника пропускается целиком: файл не перезаписывается, `.bak` не создаётся и не
  изменяется. Строка отчёта — «Бинарник: уже установлен (`<version>`)». То же для CA (N5-I4) и
  Desktop (N5-I9).

- **N5-U4. Другая версия.** Установщик не сравнивает версии как порядок и не запрещает установку
  более старого пакета поверх более нового: устанавливается ровно то, что лежит в пакете. В отчёте и
  в `--check` при различии печатается «другая версия (установлена `<a>`, в пакете `<b>`)», без слов
  «новее»/«старее».

## 7. Правила: удаление (N5-R*)

- **N5-R1. `--uninstall`.** Удаляются только то, что ставил установщик: файл `opencode`
  (`opencode.exe`) и `opencode.bak` из `bin_dir`; маркированный блок из файла профиля (сам файл и
  строки вне блока не изменяются; блок вырезается целиком, включая обе строки-маркера);
  запись `bin_dir` из пользовательского PATH на Windows (с той же реестровой техникой, что и в
  N5-I8) и рассылка `WM_SETTINGCHANGE`; пользовательская переменная `NODE_EXTRA_CA_CERTS` — только
  если её текущее значение равно установленному нами пути (чужое значение не трогается);
  установленный CA-файл `<config_dir>/<ca.install_name>`; Desktop-приложение (`/Applications/<app_name>`
  или `~/Applications/<app_name>`; на Windows — запуск штатного деинсталлятора, см. ниже).

  Каталог конфига, `opencode.json`, `opencode.json.bak`, `auth.json` и любые пользовательские данные
  при `--uninstall` **сохраняются**. Отчёт перечисляет каждый удалённый и каждый пропущенный объект.

  **Удаление Desktop на Windows (ревизия 1.1).** Установщик не удаляет файлы Desktop-приложения
  сам: приложение ставится своим инсталлятором (nsis/msi), поэтому и снимается своим
  деинсталлятором. Порядок:

  1. По `artifacts[].app_name` ищется запись в `HKCU\…\Uninstall` и `HKLM\…\Uninstall`
     (сопоставление по `DisplayName`).
  2. Команда деинсталляции выбирается так: если у записи непустая `QuietUninstallString` — берётся
     она (она уже содержит тихие ключи); иначе берётся `UninstallString`, и к его аргументам
     добавляются `silent_args` из манифеста (например `["/S"]`). `silent_args` не добавляются к
     `QuietUninstallString`, чтобы не задваивать ключи.
  3. Строка деинсталляции разбирается на исполняемый файл и аргументы (учитываются оба вида:
     `"C:\…\uninstall.exe" /S` и `MsiExec.exe /X{GUID}`), процесс запускается и установщик
     **дожидается его завершения**.
  4. Результат отражается фактическим кодом процесса: `0` → строка отчёта «`Desktop: удалён
     (<путь>)`»; ненулевой код `N` → «`Desktop: ошибка (код N)`».
  5. Если записи в реестре нет либо и `QuietUninstallString`, и `UninstallString` пусты —
     деинсталлятор не запускается, печатается «`Desktop: удалите вручную через «Приложения и
     возможности»`». Это **не ошибка**: код выхода при этом не портится.

  Печатать «`Desktop: удалён`», не запустив деинсталлятор, запрещено: отчёт обязан отражать
  фактически выполненное действие.

  **Код выхода при провале деинсталлятора Desktop.** Ненулевой код деинсталлятора даёт итоговый код
  выхода `1` — по тому же принципу, что и неуспех шага Desktop при установке (N5-I10). Удаление
  CLI, PATH, переменной окружения и CA к этому моменту уже выполнено и **не откатывается**: их
  строки отчёта остаются, за ними идёт строка ошибки Desktop. Все прочие объекты `--uninstall`
  обрабатываются как обычно, `--purge` (если запрошен) выполняется, и только затем возвращается
  код `1`.

- **N5-R2. `--purge`.** Действует только вместе с `--uninstall` и дополнительно удаляет пути из
  `manifest.purge_paths` — по умолчанию каталог конфига (`<config_dir>`) и каталог данных
  (`${XDG_DATA_HOME:-$HOME/.local/share}/opencode`, на Windows `%USERPROFILE%\.local\share\opencode`),
  где лежит в том числе сохранённый ключ LiteLLM. **[проверить]** — фактическое размещение
  auth-store форка подтверждается при сквозном прогоне; поэтому список задаётся манифестом, а не
  зашит в скрипт. Удаляются только пути из списка, прошедшие проверку: путь после подстановки
  переменных лежит внутри домашнего каталога пользователя, не равен самому домашнему каталогу, не
  содержит `..`. Путь, не прошедший проверку, не удаляется, печатается предупреждение, код выхода `2`.
  Перед удалением каждый путь перечисляется в выводе; `--dry-run --uninstall --purge` печатает
  тот же список, ничего не удаляя.

- **N5-R3. Удаление того, чего нет.** `--uninstall` на системе, где ничего не установлено, — не
  ошибка: каждый отсутствующий объект даёт строку «`<объект>`: не найден», код выхода `0`. Повторный
  `--uninstall` идемпотентен так же, как установка (N5-U1).

- **N5-R4. `--purge` без `--uninstall`.** Ошибка аргументов: сообщение «`--purge` применяется только
  вместе с `--uninstall`», код `2`, ничего не удалено (N5-I1).

## 8. Правила: проверка без установки (N5-C*)

- **N5-C1. `--dry-run`.** Печатается нумерованный план шагов с абсолютными путями и конкретными
  значениями (какой файл куда копируется, какой профиль правится, какая переменная в какое значение
  ставится, что запускается для Desktop). Ни один файл и ни один каталог не создаётся, не изменяется
  и не удаляется; переменные окружения не пишутся; внешние установщики не запускаются. Проверка
  манифеста (N5-P4) и sha256 (N5-P5) выполняется — их провал даёт код `2`/`4` и в этом режиме.
  Успешный `--dry-run` завершается кодом `0`. `--dry-run` работает и вместе с `--uninstall`
  (план удаления) и с `--system` (план с путями `/usr/local/bin`, без вызова `sudo`).

- **N5-C2. `--check`: построчный контракт вывода.** Формулировки строк — часть контракта (как
  S-A11a в форке): на них опираются тесты N5-T3 и дымовая проверка CI, поэтому они правятся
  одновременно здесь, в тестах и в CI, а тесты сверяются с подстроками из одного источника констант.

  | Условие | Строка |
  |---|---|
  | всегда | `Пакет: opencode-magnit <version> (<os>-<arch>)` |
  | всегда | `Манифест: корректен` |
  | бинарник найден, версия получена | `Бинарник: установлен <version> (<путь>)` |
  | бинарник найден, версия отличается | `Бинарник: другая версия (установлена <a>, в пакете <b>)` |
  | бинарник найден, `--version` не отработал | `Бинарник: установлен, версия не определена (<путь>)` |
  | бинарника нет | `Бинарник: не установлен` |
  | `bin_dir` в PATH | `PATH: содержит <bin_dir>` |
  | `bin_dir` не в PATH | `PATH: не содержит <bin_dir>` |
  | CA совпадает с пакетом | `CA: установлен (<путь>)` |
  | CA есть, хеш отличается | `CA: отличается от пакета (<путь>)` |
  | CA нет | `CA: не установлен` |
  | переменная равна нашему пути | `NODE_EXTRA_CA_CERTS: задан (<путь>)` |
  | переменная задана иначе | `NODE_EXTRA_CA_CERTS: задан другой путь (<путь>)` |
  | переменной нет | `NODE_EXTRA_CA_CERTS: не задан` |
  | Desktop установлен | `Desktop: установлен (<путь>)` |
  | Desktop есть в пакете, но не установлен | `Desktop: не установлен` |
  | Desktop не входит в пакет | `Desktop: не входит в пакет` |
  | всегда | `Конфиг: <путь> (не изменяется установщиком)` |
  | всегда | `Hub: <hub_url>` |
  | расхождений нет | `Итог: всё установлено` |
  | есть расхождения | `Итог: требуется установка` |

  Версия установленного бинарника определяется запуском `"<путь>" --version`; неуспех запуска или
  ненулевой код — не ошибка `--check`, а строка «версия не определена».

  **Источник данных для строк (ревизия 1.1).** Общее правило: `--check` отвечает на вопрос
  «установлено ли», а не «видит ли это текущая сессия shell». Поэтому:

  - **`NODE_EXTRA_CA_CERTS` (macOS/Linux).** Строка относится к переменной текущего процесса **и** к
    содержимому нашего блока в профиле: если блок есть, переменная считается заданной, даже если
    текущая сессия его ещё не прочитала.
  - **`PATH` (macOS/Linux).** Так же: `PATH: содержит <bin_dir>` печатается, если `bin_dir` входит в
    `$PATH` текущего процесса **либо** упоминается в нашем маркированном блоке файла профиля.
    Признак определяется именно по нашему блоку (наличие маркеров + строка с `bin_dir` внутри), а не
    по произвольному упоминанию каталога в файле. Без этой поблажки `--check`, выполненный сразу
    после установки в том же процессе, всегда печатал бы «не содержит» — что и фиксирует AC-100.
  - **`Desktop` (Windows).** Подставляется не путь на диске, а значение `DisplayTarget` записи
    деинсталляции: `InstallLocation`, если оно в реестре есть, иначе `DisplayName`. Установщик не
    ставит Desktop сам и не знает его каталога — единственный достоверный источник — реестр. То же
    значение используется в строке отчёта `--uninstall` (N5-R1), чтобы вывод был согласован.
    На macOS в этой строке — обычный путь к `.app`.

- **N5-C3. Коды выхода `--check`.** `0` — все проверки в состоянии «установлено и совпадает»
  (Desktop, отсутствующий в пакете, расхождением не считается). `7` — хотя бы одно расхождение.
  `2`/`3`/`4` — как обычно (манифест, среда, хеш файлов пакета). `--check` не создаёт ни одного файла,
  не требует прав на запись и работает на системе, где ничего не установлено (там `7`).

- **N5-C4. Ни один диагностический режим не меняет систему.** `--help`, `--version`, `--check`,
  `--dry-run` не создают каталогов (включая `<config_dir>` и `bin_dir`), не правят профиль, не
  пишут переменные и не запускают внешние установщики. Проверяется сравнением снимка файловой
  системы фейкового `$HOME` до и после (N5-T3).

## 9. Правила: сборка пакета для портала (N5-B*)

- **N5-B1. Интерфейс `installers/release.sh`.**
  `release.sh --artifacts <dir> --version <ver> --ca <file> --hub-url <url> [--out <dir>]
  [--targets darwin-arm64,darwin-x64,linux-x64,windows-x64] [--publish]`.
  `--artifacts` — локальный каталог с уже собранными артефактами CI форка; `--out` по умолчанию
  `installers/dist`; `--targets` по умолчанию все четыре цели. Отсутствие любого обязательного
  аргумента → справка в stderr и код `2`.

  **Валидация `--version` (ревизия 1.1).** Значение обязано проходить ту же проверку формата, что и
  поле `version` в `manifest.schema.json`: регулярное выражение
  `^[0-9]+\.[0-9]+\.[0-9]+-magnit\.[0-9]+$` (например `1.17.9-magnit.1`). Несоответствие →
  сообщение с указанием ожидаемого формата и полученного значения, код выхода `2`, ни один пакет не
  собирается. Без этой проверки собрался бы пакет, не проходящий собственную схему: молчаливый
  выпуск такого пакета запрещён.

  **Экранирование строк в манифесте (ревизия 1.1).** Все строковые значения, которые скрипт
  подставляет в генерируемый `common/manifest.json` (в частности `--hub-url`, `--version`, имя
  desktop-файла и `app_name`), экранируются по правилам JSON: обратный слэш и двойная кавычка
  заменяются на `\\` и `\"`. Кавычка или слэш в аргументе не должны приводить к синтаксически
  битому манифесту. Самопроверка собранного пакета (N5-B2) остаётся обязательной и после этого — она
  вторая линия защиты, а не замена экранированию.

- **N5-B2. Сборка пакета.** Для каждой цели скрипт: находит артефакт CLI — принимается либо
  `opencode-<os>-<arch>-<ver>.zip`, либо распакованный каталог `opencode-<os>-<arch>/bin/opencode`
  (имена — по S-B2 форка, где `win32` в имени каталога записывается как `windows`); собирает дерево
  N5-P2; кладёт CA из `--ca`, установщики из `installers/`, `README.md` (N5-D3); вычисляет sha256
  всех файлов и генерирует `common/manifest.json` (N5-P3) с `version`, `hub_url`, `source_release =
  v<ver>`, `built_at`, `purge_paths` по умолчанию; упаковывает: `tar.gz` для `darwin`/`linux` с
  сохранением бита `+x` на `install.sh` и на `bin/opencode`, `zip` для `windows`. Desktop-артефакт
  (`*.dmg` для `darwin-arm64`, `*.exe`/`*.msi` для `windows-x64`) добавляется, если найден в
  `--artifacts`; для `linux-x64` и `darwin-x64` Desktop не собирается форком (S-B3) и в пакет не
  кладётся. Если версия в имени найденного артефакта не совпадает с `--version` — ошибка с обоими
  значениями, код `2`.

  Собранный пакет обязан проходить собственную проверку: после упаковки скрипт распаковывает архив
  во временный каталог и выполняет установщик с `--dry-run` (для Windows-пакета — только валидацию
  манифеста, если `pwsh` недоступен); неуспех — ошибка сборки.

- **N5-B3. `SHA256SUMS` и публикация.** Рядом с архивами создаётся один файл `SHA256SUMS` в формате
  `sha256sum` (`<хеш>  <имя архива>`), включающий все собранные архивы. Публикация выполняется только
  по явному флагу `--publish` (как S-B4 в форке): черновик GitHub Release приватного репозитория
  тегом `v<ver>` с архивами и `SHA256SUMS`; без флага скрипт печатает «публикация пропущена: добавьте
  --publish». Выкладка на портал AI Lab — ручная, описывается в `install-admin.md` (N5-D2, D-8).

- **N5-B4. Отсутствующий артефакт — ошибка, не пропуск.** Если для запрошенной цели в `--artifacts`
  нет CLI-артефакта, скрипт завершается ненулевым кодом и печатает список ожидаемых имён файлов.
  Молчаливый пропуск цели запрещён (то же правило, что S-B3 в форке).

- **N5-B5. Границы `release.sh`.** Скрипт не собирает форк (не вызывает `bun`, `corp/build.ts`), не
  скачивает артефакты из сети (вход — только локальный каталог) и не подписывает сборки (R-14, S-B9).
  Все три случая при попытке использования дают понятное сообщение со ссылкой на нужный инструмент.

  переменной окружения для GUI на macOS/Linux (N5-I5) и отсутствие Desktop для Linux (S-B3).

- **N5-D3. `README.md` в пакете.** Короткий файл (до одного экрана) внутри каждого пакета: версия,
  ОС/архитектура, одна команда запуска для этой ОС, ссылка на `install-user.md`, отпечаток
  `SHA256SUMS` для самопроверки. Генерируется `release.sh` из шаблона, версия и цель подставляются.

## 11. Правила: тесты и CI (N5-T*)

- **N5-T1. bats: размещение и изоляция.** Тесты POSIX-установщика лежат в
  `installers/tests/bats/*.bats` и запускаются командой `bats installers/tests/bats`. Каждый тест
  выполняется в собственном временном каталоге: `HOME` и корень установки подменяются
  (`HOME="$BATS_TEST_TMPDIR/home"`, `--prefix "$BATS_TEST_TMPDIR/opt"`), `SHELL` задаётся явно.
  Тесты не вызывают `sudo`, не пишут вне временного каталога, не обращаются в сеть и не зависят от
  наличия настоящего OpenCode: «бинарник» в фикстурном пакете — крошечный shell-скрипт, печатающий
  версию по `--version` и строки `corp status` по `corp status`. Фикстурные пакеты и манифесты
  собираются вспомогательной функцией в `installers/tests/fixtures/`, хеши в манифесте считаются на
  лету — захардкоженных sha256 в тестах нет (кроме тестов на заведомо неверный хеш).

- **N5-T2. Pester: что проверяется вне Windows.** `install.ps1` написан так, что его можно
  загрузить через dot-source без выполнения действий: весь исполняемый вход обёрнут условием вида
  `if ($MyInvocation.InvocationName -ne '.') { Invoke-Main @PSBoundParameters }`. Благодаря этому на
  `pwsh` под macOS/Linux (`Invoke-Pester installers/tests/pester`) проверяются: разбор и валидация
  аргументов и взаимоисключающих комбинаций, валидация манифеста, вычисление и сравнение sha256,
  построение плана шагов, текст `--dry-run` и построчный вывод `--check`, коды выхода. Работа с
  реестром, пользовательским PATH, переменными пользователя, `WM_SETTINGCHANGE`, замена занятого
  `opencode.exe` и тихая установка Desktop проверяются только на Windows и помечаются в
  `acceptance-criteria.yaml` типом `manual` (стенд — D-9); соответствующие функции изолированы за
  тонкими обёртками, которые в тестах подменяются моками (`Mock`).

- **N5-T3. Обязательные сценарии.** Набор тестов покрывает как минимум: чистую систему; повторный
  запуск (идемпотентность, N5-U1); обновление с `.bak` (N5-U2); совпадение хеша → пропуск (N5-U3);
  существующий пользовательский `opencode.json` → создаётся ровно один `.bak`, файл не изменён
  (N5-I11); `--dry-run` и `--check` не меняют ФС (N5-C4, сравнение снимка каталога до/после);
  `--check` на чистой системе → код `7`; `--uninstall` и повторный `--uninstall` (N5-R1, N5-R3);
  `--purge` удаляет ровно перечисленные пути (N5-R2). Негативные сценарии обязательны:
  **неверный sha256** → код `4`, ничего не установлено; **повреждённый/отсутствующий манифест**
  (не-JSON, `schema: 2`, отсутствующее поле, `sha256` неверной длины, `file` с `..`) → код `2`;
  **несовпадение ОС/архитектуры** → код `3`; **нет утилиты хеширования** → код `3`; **нет прав на
  запись** в `bin_dir` → код `5`; **занятый бинарник на Windows** → код `6` (`manual`);
  **`--purge` без `--uninstall`** → код `2`; **неизвестный аргумент** → код `2`; **отсутствие сети** —
  полный прогон установки в среде без сети завершается кодом `0` (N5-P6).

- **N5-T4. CI.** Эталонный workflow лежит в `installers/ci/installers.yml` и содержит задания:
  `bats` на `ubuntu-latest` и `macos-latest` (проверяет и Linux-, и macOS-ветку `install-posix.sh`);
  `pester` на `ubuntu-latest` через `pwsh`; `lint` — `shellcheck -s bash` для всех `*.sh` и
  `Invoke-ScriptAnalyzer` для `*.ps1`/`*.psm1`; `release-dry-run` — прогон `release.sh` на
  фикстурных артефактах с последующим `--dry-run` собранного пакета (N5-B2). Любое падение валит PR.
  Файл в `.github/workflows/` копирует человек: каталог `.github/` объявлен защищённым в
  `pipeline.config.yaml` и агентам недоступен; несоответствие `installers/ci/installers.yml` и
  установленного workflow отслеживается вручную.

- **N5-T5. Совместимость языков.** `install-posix.sh`, лончеры и `release.sh` совместимы с
  **bash 3.2** (штатный bash macOS): запрещены ассоциативные массивы (`declare -A`), `mapfile`/
  `readarray`, `${var^^}`/`${var,,}`, `local -n`, `&>>`, `${!prefix@}`, `**` в globstar. Разрешены
  `set -euo pipefail`, `[[ ]]`, функции, `printf`. Проверяется `shellcheck -s bash` без подавлений
  (точечные `# shellcheck disable=` допускаются только с комментарием-обоснованием) и запуском
  bats на macOS-раннере. `install.ps1` совместим с **PowerShell 5.1**: `#Requires -Version 5.1`,
  без тернарного оператора `? :`, без `??`/`?.`, без `ForEach-Object -Parallel`, без `Join-String`,
  без `$PSStyle`; проверяется `Invoke-ScriptAnalyzer` с правилом совместимости и запуском на стенде
  (D-9).

- **N5-T6. Кодировки файлов.** `install.ps1` сохраняется в UTF-8 **с BOM** — иначе PowerShell 5.1
  читает файл в кодировке системы и русские строки отчёта превращаются в мусор. `install.bat`
  содержит только символы ASCII (все сообщения — в `install.ps1`). Файлы `*.sh` — UTF-8 без BOM с
  переводами строк `LF` (BOM в начале shell-скрипта ломает shebang). Проверяется отдельным тестом
  и заданием `lint` в CI.

## 12. Раздел H5-*: бэклог Hub из `reports/review-i3-2.json`

> **Зона реализации — репозиторий Hub, ветка I-3+.** Правила H5-* реализуются в worktree
> `/Users/miroslavshishenkov/Documents/opencode-mcp-hub-i3` (ветка `pipeline/i3-hub-oauth-facade-proxy`
> или ветка, созданная от неё), в файлах `src/hub/proxy.py` и `src/hub/routes/oauth.py`. К
> установщикам они отношения не имеют; их критерии приёмки вынесены в отдельный раздел
> `hub_backlog_criteria` (идентификаторы `HAC-*`) и в общий набор AC I-5 не входят. Все четыре
> находки в `review-i3-2.json` имеют `severity: minor`, `must_fix: false`.

- **H5-1. TTL права на пробу circuit-breaker.** Правило R-P10 уточняется: TTL ключа
  `cb:<alias>:probe` перестаёт равняться `HUB_CB_RESET` и вычисляется как
  `max(HUB_CB_RESET, HUB_UPSTREAM_TIMEOUT, HUB_UPSTREAM_SSE_IDLE_TIMEOUT) + HUB_CB_PROBE_GRACE`, где
  `HUB_CB_PROBE_GRACE` — новая настройка, по умолчанию `5.0` секунды, `gt=0`. Значение `until` в
  записи пробы равно `now + <этот TTL>` и продолжает использоваться для `Retry-After` отказов в
  half-open (`max(until - now, 1.0)`). Наблюдаемая гарантия: пока пробный запрос не завершился —
  сколько бы он ни длился, вплоть до таймаута SSE, — право на пробу второй раз не выдаётся, и на
  лежащий upstream не уходит вторая проба; все прочие запросы получают 503 + JSON-RPC `-32004`
  `upstream_unavailable`. Длинный TTL не задерживает восстановление: право снимается сразу по
  завершении пробы (`record_success` — H5-3, `record_failure` — существующее удаление ключа).

- **H5-2. Валидация `X-Forwarded-For`.** Правило R-T5 уточняется: при `HUB_TRUST_PROXY=true` левое
  значение заголовка принимается, только если оно является корректным IP-адресом
  (`ipaddress.ip_address()`, IPv4 или IPv6; квадратные скобки и суффикс `:<port>` у IPv6/IPv4
  отбрасываются до разбора). До разбора значение длиннее 45 символов (максимальная длина текстового
  представления IPv6) отбрасывается без попытки парсинга. Некорректное значение → откат на
  `request.client.host`, а при его отсутствии — `"unknown"`; факт отклонения пишется в лог уровня
  `WARNING` **без самого значения** (только длина и имя заголовка, R-T4/R-K3). Тем самым в ключи
  `rl:register:<ip>` и `rl:token:<client_id>:<ip>` не попадают произвольные строки клиента: ни обхода
  лимита регистрации подстановкой мусора, ни неограниченной кардинальности и длины ключей Redis.
  Поведение при `HUB_TRUST_PROXY=false` не меняется: заголовок игнорируется полностью.

- **H5-3. Лишний `delete` на горячем пути `record_success`.** `CircuitBreaker.record_success`
  перестаёт безусловно удалять `cb:<alias>:probe`. Удаление выполняется только когда выключатель
  фактически был открыт или в half-open — признак берётся из записи `cb:<alias>`, уже прочитанной в
  `check()`, и передаётся вызывающим кодом (например, параметром `was_open: bool = False`); допустима
  альтернатива — объединение обеих операций KV в одну транзакцию/pipeline. Наблюдаемое поведение
  R-P10 не меняется ни в одном состоянии выключателя. Проверяемое следствие: в закрытом состоянии на
  один успешно проксированный запрос приходится ровно одна операция записи в KV и ноль операций
  удаления (считается счётчиком операций фейкового KV в тесте).

- **H5-4. Упрощение `record_failure`.** В ветке повторного открытия окна (`open_until > 0.0`)
  вместо `failures = max(failures, self.settings.cb_failures)` записывается
  `failures = self.settings.cb_failures`: счётчик в этой ветке никогда не превышает порог, поэтому
  `max` — эквивалентная страховка, скрывающая намерение (мутанты M6/M11 из `review-i3-2` эквивалентны
  именно из-за неё). Окно по-прежнему открывается немедленно на `HUB_CB_RESET` секунд, ключ пробы
  удаляется. Наблюдаемое поведение AC-151 не меняется; после провала пробы состояние в KV равно
  `{failures: HUB_CB_FAILURES, open_until: now + HUB_CB_RESET}` и читается через `state()`.
