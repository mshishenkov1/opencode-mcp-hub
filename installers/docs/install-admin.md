# OpenCode Magnit: сборка пакетов и администрирование установки

Документ для того, кто собирает пакеты и выкладывает их на портал. Пользовательская
инструкция — `install-user.md`. Правила — `installers/docs/spec.md`.

---

## 1. Сборка пакета: `installers/release.sh`

```
release.sh --artifacts <каталог> --version <версия> --ca <файл> --hub-url <адрес>
           [--out <каталог>] [--targets darwin-arm64,darwin-x64,linux-x64,windows-x64]
           [--publish]
```

| Аргумент | Обязателен | Смысл |
|---|---|---|
| `--artifacts` | да | локальный каталог с готовыми артефактами конвейера форка |
| `--version` | да | версия сборки, формат `<upstream>-magnit.<N>`, например `1.17.9-magnit.1` |
| `--ca` | да | корпоративный CA-bundle в формате PEM |
| `--hub-url` | да | адрес Hub; попадает в манифест и в отчёт установщика |
| `--out` | нет | каталог для архивов, по умолчанию `installers/dist` |
| `--targets` | нет | цели через запятую, по умолчанию все четыре |
| `--publish` | нет | создать черновик релиза с архивами и `SHA256SUMS` |

Отсутствие любого обязательного аргумента — справка в stderr и код выхода `2`;
каталог `--out` при этом не создаётся.

`--version` проверяется на формат из схемы манифеста —
`^[0-9]+\.[0-9]+\.[0-9]+-magnit\.[0-9]+$` (например `1.17.9-magnit.1`). Значение другого вида
(`1.17.9`, `v1.17.9-magnit.1`, `1.17.9-magnit`) отвергается с кодом `2` до начала сборки: иначе
получился бы пакет, не проходящий собственную схему. Кавычки и обратные слэши в строковых
аргументах (`--hub-url` и др.) экранируются при записи в `manifest.json` и не ломают его синтаксис.

### Требования к артефактам конвейера форка

Для каждой цели `<os>-<arch>` принимается один из двух вариантов:

- архив `opencode-<os>-<arch>-<версия>.zip` (внутри — файл `opencode` или `opencode.exe`);
- распакованный каталог `opencode-<os>-<arch>/bin/opencode` (`opencode.exe` для Windows).

В именах каталогов Windows записывается как `windows` (в конвейере форка цель называется
`win32`). Если артефакта нет — сборка падает с ненулевым кодом и печатает список ожидаемых
имён; молчаливого пропуска цели нет. Если версия в имени найденного артефакта не совпадает
с `--version` — ошибка с обеими версиями, код `2`.

Desktop-артефакт добавляется, если найден в `--artifacts`: `*.dmg` для `darwin-arm64`,
`*.msi` или `*.exe` для `windows-x64`. Для `darwin-x64` и `linux-x64` Desktop конвейером форка
не собирается и в пакет не кладётся.

Для `*.dmg` в манифест обязательно записывается непустое `app_name` — имя каталога приложения
внутри образа (`OpenCode.app`). Пакет с `installer_type:"dmg"` и без `app_name` установщик
отвергает как повреждённый манифест (код `2`), поэтому такой пакет не пройдёт самопроверку
сборки (шаг 4 ниже) и до портала не доедет. Подробности — раздел 2.

### Что делает скрипт

1. Собирает дерево пакета (см. `spec.md`, N5-P2), кладёт установщики из `installers/`,
   CA из `--ca`, `README.md` пакета.
2. Считает sha256 всех файлов и генерирует `common/manifest.json`.
3. Упаковывает: `tar.gz` для `darwin`/`linux` (с сохранением бита `+x` на `install.sh`
   и `bin/opencode`), `zip` для `windows`.
4. **Самопроверка**: распаковывает архив во временный каталог, сверяет sha256 файлов
   и выполняет установщик с `--dry-run`. Для пакета чужой ОС план не строится (установщик
   штатно отвечает кодом `3`), но целостность проверяется всегда. Неуспех самопроверки —
   ошибка сборки.
5. Кладёт рядом с архивами `SHA256SUMS` в формате `sha256sum` (`<хеш>␣␣<имя архива>`).

### Чего скрипт не делает

- **Не собирает форк.** Сборка корпоративного OpenCode выполняется отдельно, в конвейере форка.
- **Не подписывает сборки** (см. раздел 6).
- **Ничего не скачивает.** Вход — только локальный каталог `--artifacts`; поле `url`
  в манифесте справочное, установщик его никогда не запрашивает.

## 2. Поля `manifest.json`

| Поле | Тип | Обязательное | Смысл |
|---|---|---|---|
| `schema` | целое | да | версия схемы, сейчас ровно `1` |
| `product` | строка | да | ровно `opencode-magnit` |
| `version` | строка | да | версия сборки, `<upstream>-magnit.<N>` |
| `os` | строка | да | `darwin` \| `linux` \| `windows` |
| `arch` | строка | да | `arm64` \| `x64` |
| `hub_url` | строка | да | адрес Hub; печатается в отчёте и в `--check`, никуда не записывается |
| `built_at` | строка | да | момент сборки пакета, ISO-8601 UTC |
| `source_release` | строка | да | тег релиза форка, из которого взяты артефакты (`v<версия>`) |
| `ca` | объект | да | `{file, sha256, install_name}` — CA-bundle |
| `artifacts` | массив | да | `{kind, file, sha256, size, …}`; ровно один `kind:"cli"`, не более одного `kind:"desktop"` |
| `purge_paths` | массив строк | да | пути, удаляемые при `--purge`; подстановки `~`, `${XDG_CONFIG_HOME}`, `${XDG_DATA_HOME}`, `%USERPROFILE%`, `%LOCALAPPDATA%` |

Артефакт `kind:"cli"` дополнительно содержит `install_name` (`opencode` или `opencode.exe`).
Артефакт `kind:"desktop"` — `installer_type` (`dmg` \| `nsis` \| `msi`), `app_name` и
`silent_args` для Windows (массив строк, например `["/S"]`).

**`app_name` обязателен при `installer_type:"dmg"`.** Поле задаёт имя каталога приложения
(`OpenCode.app`): установщик копирует по этому имени в `/Applications` и по нему же удаляет
приложение при `--uninstall`, а на Windows — ищет по нему запись в списке установленных программ.
Отсутствующее, пустое или состоящее из пробелов значение — **невалидный манифест**: установщик
печатает ошибку с именем поля и завершается кодом `2` до любых изменений в системе, во всех
режимах (`--check`, `--dry-run`, `--uninstall`, `--purge` и их комбинации). Умолчания для этого
поля нет и не будет: пустое имя означало бы файловую операцию над самим каталогом `/Applications`.

Требования к значению `app_name` (строже, чем к остальным путевым полям): ровно одно имя каталога —
без разделителей `/` и `\`, не `.` и не `..`, без завершающего `/`, без подстановочных символов
`*`, `?`, `[`, `]`. Нарушение — та же ошибка манифеста и код `2`.

Все `file` — пути относительно корня пакета, с разделителем `/`, без ведущего `/`, без `..`
и без букв дисков; отвергаются также `.`, `./x`, `x/.` и завершающий `/`. Те же ограничения
действуют на `ca.install_name` и `artifacts[].install_name`. Формальная схема —
`installers/common/manifest.schema.json`, заполненный пример —
`installers/common/manifest.example.json`.

## 3. Что установщик пишет в систему

| Путь или переменная | Когда создаётся | `--uninstall` | `--purge` |
|---|---|---|---|
| `<config_dir>/tander-ca-bundle.pem` | всегда (шаг CA) | удаляется | удаляется |
| `<config_dir>/` (каталог) | при отсутствии, права `0755` | сохраняется | удаляется, если указан в `purge_paths` |
| `<config_dir>/opencode.json` | **не создаётся установщиком** | сохраняется | удаляется вместе с каталогом |
| `<config_dir>/opencode.json.bak` | если `opencode.json` есть, а копии ещё нет | сохраняется | удаляется вместе с каталогом |
| `<config_dir>/auth.json` | **не создаётся и не читается** | сохраняется | удаляется вместе с каталогом |
| `<bin_dir>/opencode` (`opencode.exe`) | всегда (шаг бинарника) | удаляется | удаляется |
| `<bin_dir>/opencode.bak` (`opencode.exe.bak`) | при обновлении версии | удаляется | удаляется |
| Блок в файле профиля shell (macOS/Linux) | всегда, ровно один файл по `$SHELL` | вырезается целиком | вырезается |
| `<файл профиля>.opencode-magnit.bak` | перед первой вставкой блока в существующий файл | сохраняется | сохраняется |
| Переменная пользователя `NODE_EXTRA_CA_CERTS` (Windows) | если отличается от целевого значения | снимается, если значение наше | снимается |
| Каталог установки в пользовательском `PATH` (Windows) | если его там ещё нет | удаляется запись | удаляется запись |
| Desktop (`/Applications/<app>` или штатный установщик Windows) | если Desktop есть в пакете | macOS: каталог `.app` удаляется. Windows: запускается штатный деинсталлятор, если он зарегистрирован; иначе — «удалите вручную» (см. ниже) | то же |
| Каталог данных `${XDG_DATA_HOME}/opencode` | создаёт сама программа, не установщик | сохраняется | удаляется, если указан в `purge_paths` |

Каталоги по умолчанию:

- `config_dir` — `${XDG_CONFIG_HOME:-$HOME/.config}/opencode`, на Windows `%USERPROFILE%\.config\opencode`;
- `bin_dir` — `$HOME/.local/bin`; `/usr/local/bin` при `--system`; `<prefix>/bin` при `--prefix`;
  на Windows `%LOCALAPPDATA%\Programs\opencode` или `-Prefix`.

Переменные уровня `Machine` на Windows не изменяются никогда; импорт CA в системное
хранилище сертификатов не выполняется.

`--purge` удаляет только пути из `manifest.purge_paths`, прошедшие проверку: путь после
подстановки лежит внутри домашнего каталога пользователя, не равен самому домашнему каталогу
и не содержит `..`. Одна не прошедшая проверку запись отвергает весь список: ничего не
удаляется, код выхода `2`.

### Удаление Desktop на Windows

Файлы Desktop-приложения установщик не удаляет сам — приложение ставилось своим инсталлятором
(nsis/msi) и снимается своим деинсталлятором. При `-Uninstall` установщик ищет запись в
`HKCU\…\Uninstall` и `HKLM\…\Uninstall` по `app_name` из манифеста и действует так:

| Что найдено в реестре | Что делает установщик | Строка отчёта | Код выхода |
|---|---|---|---|
| непустая `QuietUninstallString` | запускает её как есть (`silent_args` не добавляются — тихие ключи в ней уже есть) и ждёт завершения | `Desktop: удалён (<путь или имя>)` при коде `0` | `0` |
| `QuietUninstallString` пуста, есть `UninstallString` | запускает её, добавив `silent_args` из манифеста (например `/S`), и ждёт завершения | `Desktop: удалён (<путь или имя>)` при коде `0` | `0` |
| деинсталлятор вернул ненулевой код `N` | ничего не откатывает | `Desktop: ошибка (код N)` | **`1`** |
| строка деинсталляции разобрана неоднозначно | **ничего не запускает** | `Desktop: строка деинсталляции разобрана неоднозначно (<строка>), запуск отменён`, следом `Desktop: удалите вручную через «Приложения и возможности»` | `0` |
| записи нет (или обе строки пусты) | деинсталлятор не запускается | `Desktop: удалите вручную через «Приложения и возможности»` | `0` |

**Про разбор `UninstallString`.** Строка из реестра разбирается на исполняемый файл и аргументы.
Понимаются три формы: путь в кавычках (`"C:\…\unins000.exe" /S`), `MsiExec.exe /X{GUID}` и
некавыченный путь с пробелами (`C:\Program Files\App\unins000.exe /S`) — в последнем случае
граница пути определяется по расширению `.exe`, `.com`, `.bat` или `.cmd`. Аргумент с пробелом
внутри кавычек (`/D="C:\Program Files\App"`) остаётся одним аргументом. Если в строке есть
пробел, но однозначной границы исполняемого файла нет, установщик **не запускает ничего**: лучше
попросить удалить приложение вручную, чем запустить чужой процесс с ключами из манифеста. Код
выхода при этом не портится, строка «`Desktop: удалён`» не печатается.

**Про поиск записи.** Сопоставление с `DisplayName` — по литеральной подстроке: подстановочные
символы в `app_name` экранируются, поэтому значение вида `*` не совпадает с первой попавшейся
записью реестра. Такие значения и так отвергаются валидацией манифеста (раздел 2), а экранирование
служит второй, независимой линией защиты.

Код выхода `1` при провале деинсталлятора — то же поведение, что и при неуспехе шага Desktop во
время установки: CLI, запись в `PATH`, переменная `NODE_EXTRA_CA_CERTS` и CA к этому моменту уже
удалены и **не восстанавливаются**, `--purge` (если запрошен) отрабатывает полностью. Отсутствие
записи в реестре ошибкой не считается и код выхода не портит.

В скобках подставляется `InstallLocation` записи, если он в реестре есть, иначе — `DisplayName`:
установщик не ставил приложение и не знает его каталога, достоверный источник — только реестр.
Та же величина печатается в строке `Desktop: установлен (…)` режима `--check`.

## 4. Ручной откат через `.bak`

Установщик хранит ровно одну предыдущую версию бинарника: при обновлении текущий файл
копируется в `opencode.bak` (на Windows переименовывается в `opencode.exe.bak`),
перезаписывая предыдущую копию. Автоматического отката нет — он выполняется руками:

```bash
# macOS / Linux
mv ~/.local/bin/opencode.bak ~/.local/bin/opencode
chmod 0755 ~/.local/bin/opencode
```

```powershell
# Windows
Move-Item "$env:LOCALAPPDATA\Programs\opencode\opencode.exe.bak" `
          "$env:LOCALAPPDATA\Programs\opencode\opencode.exe" -Force
```

Каталог конфигурации, `opencode.json`, `auth.json` и `opencode.json.bak` при обновлении
не изменяются, поэтому откат бинарника ничего больше не затрагивает. Резервная копия файла
профиля (`<файл>.opencode-magnit.bak`) делается один раз — перед первой вставкой блока —
и при последующих запусках не перезаписывается.

Версии не сравниваются как порядок: установщик ставит ровно то, что лежит в пакете, и в
отчёте пишет «другая версия (установлена A, в пакете B)» без слов «новее» и «старее».

## 5. Флаги и переменные

| POSIX | Windows | Смысл |
|---|---|---|
| `--dry-run` | `-DryRun` | напечатать план, ничего не менять |
| `--check` | `-Check` | проверить среду, ничего не менять |
| `--uninstall` | `-Uninstall` | удалить установленное |
| `--purge` | `-Purge` | вместе с `--uninstall` — удалить и пользовательские данные |
| `--system` | — | ставить в `/usr/local/bin` (единственный случай, когда вызывается `sudo`) |
| `--prefix <dir>` | `-Prefix <dir>` | переопределить корень установки |
| `--no-desktop` | `-NoDesktop` | пропустить шаг Desktop |
| `--no-launch` | `-NoLaunch` | не выполнять финальный `opencode corp status` |
| `--quiet` | `-Quiet` | печатать только итог и ошибки |
| `--help` | `-Help` | справка, код выхода `0` |
| `--version` | `-ShowVersion` | версия пакета из манифеста, код выхода `0` |

Взаимоисключающие сочетания (`--dry-run` с `--check`, `--check` с `--uninstall`, `--purge`
без `--uninstall`, `--system` с `--prefix`) дают код `2`. Флага «пропустить проверку хеша»
не существует.

Читаемые переменные окружения: `HOME`, `SHELL`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `PATH`,
`NODE_EXTRA_CA_CERTS`, `USERPROFILE`, `LOCALAPPDATA`. Коды выхода `0`–`7` — в таблице
`install-user.md`.

## 6. Подпись сборок — статус

**Не выполняется.** Пакеты пилота не подписаны: ни Authenticode для Windows, ни Developer ID
с нотаризацией для macOS. Это решение ИБ (требование R-14, решение D-7, правило S-B9
спецификации форка), и до его принятия действует документированный обход предупреждений ОС
из `install-user.md` — **только на время пилота**. **[проверить]** — после решения ИБ раздел
переписывается, а `release.sh` дополняется шагом подписи.

## 7. Выкладка

1. Соберите архивы: `release.sh … --out dist`.
2. Проверьте `dist/SHA256SUMS`: `sha256sum -c SHA256SUMS` в каталоге с архивами.
3. Черновик релиза в приватном репозитории форка создаётся флагом `--publish`
   (тег `v<версия>`, в приложениях — все архивы и `SHA256SUMS`). Без флага скрипт печатает
   «публикация пропущена: добавьте --publish» и ничего не публикует. Черновик проверяется
   человеком и публикуется вручную.
4. Карточка загрузок на портале AI Lab обновляется **вручную** (решение D-8): ссылки на
   архивы по ОС и архитектуре, версия, отпечатки из `SHA256SUMS`, ссылка на `install-user.md`.
   Автообновления сборок в пилоте нет.

## 8. Известные ограничения

- **Нет переменной окружения для GUI-процессов на macOS и Linux.** Штатного пользовательского
  механизма задать переменную для приложений, запускаемых из Finder или из меню рабочего стола,
  без правки окружения `launchd` или `systemd --user` не существует, а это уже изменение
  системных настроек. Поэтому `NODE_EXTRA_CA_CERTS` задаётся только для терминальных сессий,
  а Desktop-сборка берёт CA из файла в каталоге конфигурации. **[проверить]** — подтверждается
  при первом сквозном прогоне; при отрицательном ответе появится отдельное правило.
- **Нет Desktop для Linux** — конвейер форка собирает Desktop только для `mac-arm64` и `win-x64`.
- **Нет `.pkg` для macOS** — бинарник ставится напрямую, установка через `.pkg` в объём не входит.
- **CA не импортируется в системное хранилище сертификатов** — ставится только пользовательская
  копия; это сознательное ограничение «без прав администратора».
- **Установщик не разбирает `opencode.json`.** Конфликтом считается сам факт существования
  файла: рядом создаётся одна резервная копия, содержимое не анализируется.
- **Windows-стенд для проверок реестра, пользовательского `PATH`, занятого `opencode.exe`
  и тихой установки Desktop** пока отсутствует (D-9): соответствующие критерии приёмки имеют
  тип `manual` и проверяются вручную.
