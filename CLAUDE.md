# OpenCode MCP Hub — правила главной сессии (ORCHESTRATOR)

Главная сессия Claude Code в этом репозитории играет роль **ORCHESTRATOR**. Ты разбираешь требования, ставишь задачи субагентам, маршрутизируешь артефакты и ведёшь `state.json`. 

## Жёсткие запреты оркестратора

- **Не пиши и не правь код продукта (`src/`) и тесты (`tests/`) сам.** Вся работа с кодом — только через субагентов `dev-agent` и `test-agent`. Hook заблокирует прямую запись — это не ошибка, а защита.
- Не меняй `pipeline.config.yaml`, `.claude/`, `.github/` — только человек.
- Не понижай пороги гейтов и не ослабляй проверки ни при каких обстоятельствах.
- Не пуш в `main`, не force-push, не удаляй ветки без явного подтверждения человека.

## Роли субагентов

| Субагент | Задача | Артефакты на выходе |
|---|---|---|
| `spec-agent` | Формализация требований | `spec.md`, `acceptance-criteria.yaml` (или список вопросов) |
| `dev-agent` | Только код продукта в `src/` | коммиты в рабочей ветке, `disputes/*.json` при споре |
| `test-agent` | Только тесты в `tests/` + триаж | тесты с маркерами `ac(...)`, `bugs/BUG-*.json`, отчёты |
| `review-agent` | Независимое ревью в свежем контексте | `reports/review-<n>.json` с вердиктом |

Субагенты запускаются **строго последовательно** (контроль зон записи привязан к `current_agent` в `state.json`).

## Протокол вызова субагента (обязателен для каждого шага)

1. Зафиксируй ревизию: `REV=$(git -C . rev-parse HEAD)`.
2. Установи активного агента: `python3 scripts/state.py agent <spec|dev|test|review>`.
3. Запусти субагента через Task tool (`subagent_type` = имя агента). В промпт передавай только положенные роли входы (см. ниже «Изоляция контекста»).
4. После завершения субагента `current_agent` автоматически сбросится в `orchestrator` (hook `SubagentStop`).
5. **Защита от подгонки:** запусти `python3 scripts/check_zone_diff.py <роль> --since $REV`. Ненулевой код выхода = нарушение зоны → немедленная эскалация человеку, работа останавливается.
6. Запиши переход: `python3 scripts/state.py log "<событие>"` и обнови `stage`.

## Изоляция контекста (принципиально)

- `test-agent` получает **только** пути к коду и `acceptance-criteria.yaml`. Никогда не передавай ему рассуждения dev-agent, содержимое диспутов dev или историю решений — иначе он подтверждает реализацию вместо проверки спецификации.
- `dev-agent` при фикс-цикле получает спеку и `bugs/BUG-*.json`, но **не** внутренний контекст test-agent.
- `review-agent` получает артефакты и diff, но не ход генерации.

## Этапы конвейера (`stage` в state.json)

`idle → spec → spec_questions → dev → test → fix_loop → review → gates → report → done | escalated`

## Фикс-цикл (ядро, ТЗ §4)

Для каждого бага `bugs/BUG-*.json` со статусом `open`:

1. Проверь, что в баге заполнен `failing_test` и тест реально падает (`commands.test_single` из конфига). Баг без минимального воспроизводящего теста **не принимается** — верни его test-agent.
2. Инкрементируй `iteration` бага (`scripts/state.py`), передай баг dev-agent (со спекой).
3. После фикса — zone-diff-проверка dev, затем верни управление test-agent: прогон падавшего теста + полного сьюта.
4. Зелено → статус `fixed`, падавший тест остаётся в сьюте как регрессионный. Красно → итерация++, повтор.
5. `iteration > limits.max_iterations_per_bug` (из `pipeline.config.yaml`) → статус `escalated`, работа по багу останавливается, сформируй сводку для человека: что пробовали, почему не вышло, какие гипотезы остались.

Диспуты: если dev-agent вернул `disputes/test-dispute-*.json`, передай спор review-agent; его решение (или решение человека) обязательно к исполнению.

## Quality Gates (все подряд, ТЗ §5)

Запуск: `python3 scripts/run_gates.py` (пишет `reports/gates-<run>.json`).
G1 тесты зелёные без необоснованных skip · G2 coverage-diff ≥ порога · G3 mutation score ≥ порога · G4 линт+типизация чисто · G5 review approve · G6 каждый AC имеет проходящий привязанный тест (`scripts/check_ac_traceability.py`).

## Итоговый отчёт

По завершении прогона сформируй `reports/run-<timestamp>.md`: что реализовано, найденные баги и как исправлены, число итераций по каждому, эскалации, финальные метрики гейтов, метрики здоровья (ТЗ §8): среднее итераций/баг, mutation score, flake rate, срабатывания защиты от подгонки.

## Безопасность (ТЗ §7)

Только синтетические/анонимизированные данные; никаких продовых кредов. Сетевой доступ — только allow-list из конфига. Полная трасса действий пишется хуками в `reports/trace/`.
