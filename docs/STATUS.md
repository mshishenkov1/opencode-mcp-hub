# Снимок состояния проекта на 2026-08-27, вечер (для продолжения в новой сессии)

## Что это за проект
Корпоративный OpenCode для Magnit/Тандер: форк OpenCode с витриной MCP-коннекторов и входом по корпоративному
SSO + серверный Hub (каталог, OAuth, proxy) + собственные MCP-серверы. Требования — `docs/req-mvp.md` (rev 0.2).
Цель MVP: установка на macOS/Windows/Linux; лёгкое добавление новых MCP; понятный процесс переноса каталога при
обновлении OpenCode; Atlassian + GitLab + ТЭГ подключаются «в 2 клика».

**Целевой сценарий заказчика (сформулирован 2026-08-21):** зашёл в OpenCode → авторизовался в LiteLLM →
модель настроилась сама, чат работает на внутренней модели → в каталоге коннекторов нажал «Подключить» у ТЭГ →
авторизовался → коннектор работает.

## Коннектор ТЭГ: как он устроен
Спека — `spec.md` ревизии 3 (часть III, правила R-U1…R-U10), критерии AC-169…AC-194.
Два способа подключения объявляются в каталоге через `auth_methods`:
- `corp_oauth` (`type: oauth2`) — корпоративная авторизация ТЭГ, помечена `available: false` до выдачи
  OAuth-приложения администраторами; попытка подключиться ею даёт 409;
- `session_token` (`type: user_token`) — пользователь вводит свой токен ТЭГ, Hub проверяет его запросом к
  Mattermost, хранит зашифрованным и подставляет заголовком при проксировании.

ТЭГ-MCP при этом поднят в режиме **сквозной передачи** (`MM_HTTP_AUTH=passthrough`): он проверяет пришедший токен
у самого Mattermost и работает от имени его владельца. Права двухуровневые: потолок задаёт развёртывание
ТЭГ-MCP (`MM_WRITE_MODE`), персональный срез — Hub через `permission_model.kind: tool_filter`.

### Hub, ревизия 4.4 «граница публикации по типу способа» — ЗАКРЫТА (approve, 8 циклов ревью)
Ветка i3, HEAD после закрытия `172ef9c`, **запушена в GitHub** (в GitLab не долито — VPN не
поднимался). Сьют **984 passed**, гейт **G6 OK: все 252 критериев**.
Зачем делалась: ревизия 1.13 форка подключает MCP напрямую, поэтому Hub обязан публиковать
`verify`, `exchange` (с вложенным `revoke`) для доступного `user_token` и блок `upstream` карточки.
**Главное, что вскрылось:** довод «в этих полях секретов нет по построению» **неверен** — ссылка
`env:VAR` допустима в `credential_headers`/`static_headers` по схеме, а подстановка `${VAR}` идёт
**до** валидации, поэтому `static_headers: {X-Key: "${GW_SECRET}"}` — валидный каталог, и первая
реализация опубликовала бы секрет. Закрыто правилом **дословности** (наружу только строка,
записанная как есть; исключение — четыре адреса, без них прямого режима нет) плюс **след**: каждый
снятый блок пишет WARNING при загрузке, чтобы потеря прямого режима не была молчаливой.

**Почему восемь циклов.** Каждый круг находил новое **завышенное утверждение** — текст обещал
покрытие, которого нет, — и всякий раз на уровень глубже: перечень в тексте правила → перечень в
прогоне → модульная константа вместо фактического аргумента → аргумент верхнего вызова вместо всех
обращений → значение параметра вместо логики, которая по нему решает. **Сплошная вычитка не нашла
ни одного уровня и не могла.**

**Чем закрылось (решение заказчика + решения 130/131):** остановились по решению заказчика, остаток
записан в открытые хвосты, и — ключевое — **перечень границ объявлен ОТКРЫТЫМ**: число названо
«оценкой снизу», новый вход дописывается пунктом. После этого найденные входы (их дописали ещё два)
перестали опровергать текст. Плюс записано правило порядка: **перечень пишется после того, как
заданный вопрос проверен инъекцией на текущей редакции**, а не одновременно с ней.

**Открытый остаток Hub (осознанно, механизм известен):** N33 — послабление в способе использования
параметра (закрывается property-прогоном над функцией решения, цена — пришитая семантика приватной
функции); N32 — послабление по форме значения, механизма нет, закрыто оговоркой в тексте; плюс
дописанные N34…N37. Риск **принят, а не компенсирован**.

(а) охранником служит **только предикат**, поля ответа каталога — предъявление; (б) **неизвестное
запрещено**; (в) довод «этой записи взяться неоткуда» действителен, пока её никто не создаёт;
(ж) **источник свидетельства обязан обновляться той записью**, после которой из него берут состояние.
Честно записано: **полнота перечня точек не проверяется ничем** — сторожа у неё нет.

### УРОКИ СЕССИИ (ценнее самих правок)
- **Проверять утверждения наблюдением, а не вычиткой.** Все находки уровней дала инъекция с
  оракулом против чистого baseline; вычитка не дала ни одной.
- **У сторожа спрашивают не «что он проверяет», а «чего он не увидит»** — и ответ проверяют руками.
- **Самопроверка вычиткой сама усиливает утверждения.** Коммит «сняты безусловные обещания»
  ввёл более сильное и ложное утверждение о механизме. У обоснования нет сторожа: правило краснеет,
  довод молчит.
- **Отрицательный результат инъекции ничего не доказывает**, пока не показано, что инъекция вообще
  меняет наблюдаемое поведение.
- **Диагноз, сделанный для одного места, обязан быть проверен на всех однородных.** Предок BLK-4
  лежал диагностированным в комментарии три цикла и не был перенесён с провайдеров на конфиг.
- **Два настоящих дефекта нашёл заказчик обычным использованием за минуту**, пока конвейер спорил о
  защите от намеренной правки кода.

## Известные проблемы, требующие решения
1. **Лимит расходов GitHub Actions** — прогоны там не стартуют. За GitHub остаются Windows-ветка Pester
   и сборка Desktop: в корпоративном GitLab нет ни Windows-, ни macOS-раннеров.
2. **Каталог кеша обновлений общий с ванильной сборкой** (`~/Library/Caches/@opencode-aidesktop-updater`).
   Подсунуть чужой файл нельзя — апдейтер сверяет sha512 и чистит кеш при расхождении, — но каталог
   разделяется. Поля нет ни в перечне разрешённых правок S-B9, ни в AC-138/AC-152: нужна правка спеки.
3. **Встроенный сервер ходит в чужой репозиторий**: `Installation.latest()` зовёт
   `api.github.com/repos/anomalyco/opencode/releases/latest` при явном апгрейде CLI. Десктопного апдейтера
   это не касается (он выключен), но для корпоративного контура канал наружу остаётся.
4. **Заголовок окна** `OpenCode` захардкожен в разметке и одинаков у всех каналов — стоит привести
   к имени сборки.
5. **Сертификат**: Desktop не видит CA из `NODE_EXTRA_CA_CERTS` (Electron ходит через стек Chromium).
6. **Автослой MCP** строится из ванильного спека Mattermost — кастом ТЭГ им не покрывается.
7. **ТЭГ-MCP не умеет CA-набор**: настройка `verify_ssl` булева, httpx берёт certifi и корпоративный корень
   не видит. На стенде обходится `MM_VERIFY_SSL=false`, в бою понадобится путь к набору.
8. **Мина в тестах ТЭГ**: `tests/resilience/test_supervisor.py::TestLoggingAndEntry::test_module_is_executable`
   виснет навсегда у любого, у кого в корне есть рабочий `.env`. Важно: без имени класса в идентификаторе
   `--deselect` **молча не срабатывает** — прогон повиснет, хотя тест как будто исключён.

**Закрыто с прошлого снимка:** автообновление Desktop и совпадающий идентификатор — канал `magnit`,
`appId ai.opencode.desktop.magnit`, имя «OpenCode Magnit», апдейтер идёт на внутренний сервер из переменной
сборки `CORP_DESKTOP_UPDATE_URL`, а без неё выключается целиком. Проверено на собранном бандле и живым
запуском: в логе `auto updater disabled`, обращений к чужим релизам нет, каталог данных отдельный.

```

```
Переменные коннектора в `deploy/.env`: `TAG_MCP_URL=http://host.docker.internal:8765/mcp`,
`TAG_VERIFY_URL=https://tag-test.corp.tander.ru/api/v4/users/me`, `TAG_MCP_AUTH_MODE=passthrough`.
Приложение: `~/Documents/opencode/packages/desktop/dist/mac-arm64/OpenCode.app`.
Пересборка CLI: `cd ~/Documents/opencode && CORP_HUB_URL=http://localhost:8080 bun run corp/build.ts --targets darwin-arm64`.
**ВАЖНО (найдено 2026-08-27):** локальный стенд поднимается ТОЛЬКО с `HUB_REPLICAS=1` — иначе вторая
реплика не может занять фиксированный `8080:8000` из local-http-оверлея и падает с

`HUB_REPLICAS=1 docker compose -p hubi3 -f docker-compose.yml -f docker-compose.local-http.yml up -d --build`
Адрес Hub для CLI переопределяется переменной `OPENCODE_CORP_HUB_URL`.

## Внешние зависимости
1. OAuth-приложения: GitLab ×2, Jira, Confluence (не запрашивались), ТЭГ (отказали, склоняются к PAT —
   поэтому и сделано подключение токеном сессии).
2. Внутренняя Linux-ВМ с DNS-именем и сертификатом — нужна и для Hub, и как адрес канала автообновления Desktop.
3. Согласование ИБ: хранение токенов, распространение корпоративной сборки, подпись бинарников.
4. AI Lab: право CLI-JWT на `/key/generate` — **закрыто фактически**: LiteLLM выдаёт постоянный ключ,
   фолбэк на суточный JWT не срабатывает.
5. Лимит расходов GitHub Actions либо решение остаться в корпоративном GitLab.

## Как ведётся разработка
Агентный конвейер: spec → dev → test → review → гейты (G1–G6), зоны записи по ролям, отчёты в `reports/`.
Субагенты запускаются с моделью `opus`; оркестрация — на основной сессии. Каталог (`catalog.yaml`), `.github/`,
`.gitlab-ci.yml` и `deploy/` — зона оркестратора, агентам недоступны.
Особенности: `mutmut` на macOS требует `no_proxy='*'`; при обрыве субагента его работа в дереве сохраняется —
перезапускать с «продолжи с текущего дерева»; `uv run` в этой среде виснет, нужно звать `.venv/bin/…` напрямую.

## Безопасность — требует внимания
- В `~/.local/share/opencode/log/opencode.log` открытым текстом лежит GitLab PAT, попавший туда через журнал
  разрешений на bash-команду. Токен стоит отозвать, а логирование команд — пересмотреть.
- Токен GitLab, выданный для настройки MCP, был передан в переписке — его тоже стоит перевыпустить.
