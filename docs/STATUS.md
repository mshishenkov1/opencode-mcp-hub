# Снимок состояния проекта на 2026-08-21 (для продолжения в новой сессии)

## Что это за проект
Корпоративный OpenCode для Magnit/Тандер: форк OpenCode с витриной MCP-коннекторов и входом по корпоративному
SSO + серверный Hub (каталог, OAuth, proxy) + собственные MCP-серверы. Требования — `docs/req-mvp.md` (rev 0.2).
Цель MVP: установка на macOS/Windows/Linux; лёгкое добавление новых MCP; понятный процесс переноса каталога при
обновлении OpenCode; Atlassian + GitLab + ТЭГ подключаются «в 2 клика».

**Целевой сценарий заказчика (сформулирован 2026-08-21):** зашёл в OpenCode → авторизовался в LiteLLM →
модель настроилась сама, чат работает на внутренней модели → в каталоге коннекторов нажал «Подключить» у ТЭГ →
авторизовался → коннектор работает.

## Коннектор ТЭГ: как он устроен
Спека — `spec.md` ревизии 3 (часть III, правила R-U1…R-U10), критерии AC-169…AC-194.
Два способа подключения объявляются в каталоге через `auth_methods`:
- `corp_oauth` (`type: oauth2`) — корпоративная авторизация ТЭГ, помечена `available: false` до выдачи
  OAuth-приложения администраторами; попытка подключиться ею даёт 409;
- `session_token` (`type: user_token`) — пользователь вводит свой токен ТЭГ, Hub проверяет его запросом к
  Mattermost, хранит зашифрованным и подставляет заголовком при проксировании.

ТЭГ-MCP при этом поднят в режиме **сквозной передачи** (`MM_HTTP_AUTH=passthrough`): он проверяет пришедший токен
у самого Mattermost и работает от имени его владельца. Права двухуровневые: потолок задаёт развёртывание
ТЭГ-MCP (`MM_WRITE_MODE`), персональный срез — Hub через `permission_model.kind: tool_filter`.

## CI/CD — переехал в корпоративный GitLab
**Причина переезда:** прогоны GitHub Actions упёрлись в лимит расходов аккаунта («recent account payments have
failed or your spending limit needs to be increased»). Репозитории приватные, минуты платные с множителями:
Windows ×2, macOS ×10. Пока лимит не поднят, задания в GitHub не стартуют вовсе.

Пайплайны GitLab: `.gitlab-ci.yml` в Hub (обе ветки) и в форке; в ТЭГ-MCP он был портирован раньше.
Раннер — `gitlab-docker-runner-saas-shared`, образы тянутся с Docker Hub (при закрытом доступе подменяются
переменной `REGISTRY_PREFIX`).

**Что дал первый настоящий прогон** (до него все цифры были получены только локально):
- гейты Hub на ветке I-1: G1 тесты, G3 mutation 89,2 %, G4 линт/типы, G6 покрытие AC — зелёные; G2 падал из-за
  отсутствия `origin/main` в клоне (починено явным refspec), G5 красный законно — вердикт ревью;
- **набор установщиков никогда не гонялся нигде, кроме macOS**: на Linux из 227 тестов 221 зелёный, шесть падают
  по существу (ожидание `/Applications/OpenCode.app`, чистка `PATH` без `bash`, проверки прав под root);
- **набор Pester запустился впервые в истории и упал** — локально нет `pwsh`, в GitHub Actions до него не доходило;
- PSScriptAnalyzer нашёл реальные замечания, включая отсутствие BOM у файлов тестов;
- в форке корп-CI не выполнялся **ни разу** (триггер был только на PR в main и теги) — исправлено, добавлен пуш
  в ветки `corp/**`; первые прогоны потребовали доустановки Python и компилятора для нативных модулей.

**Известное:** в GitHub Actions workflow установщиков отвергался целиком из-за выражения в `shell:`
(`shell: ${{ matrix.shell }}`) — прогон падал на старте без единого задания и без сообщения в API. Три комбинации
Pester разведены по двум заданиям с явными оболочками. Windows- и macOS-проверки в корпоративном GitLab
невозможны — там нет соответствующих раннеров; это записано в шапке пайплайна, чтобы не создавать ложного
ощущения покрытия.

## Известные проблемы, требующие решения
1. **Автообновление Desktop тянет ванильный OpenCode.** Корень: `corp/build.ts` переводит канал `latest` в
   десктопный `prod`, а `prod` в `electron-builder.config.ts` — это identity апстрима (`appId ai.opencode.desktop`
   и `publish` на релизы `anomalyco/opencode`). Решение принято: собственный канал `magnit`, имя
   **OpenCode Magnit**, `appId ai.opencode.desktop.magnit`, обновления с внутреннего сервера. Требует изменения
   спеки (файл заморожен правилом S-B9/AC-112).
2. **Лимит расходов GitHub Actions** — прогоны там не стартуют. Обновление включённых минут — начало расчётного
   периода аккаунта; если дело в отклонённом платеже, ожидание не поможет.
3. **Сертификат**: Desktop не видит CA из `NODE_EXTRA_CA_CERTS` (Electron ходит через стек Chromium).
4. **Автослой MCP** строится из ванильного спека Mattermost — кастом ТЭГ им не покрывается.
5. **ТЭГ-MCP не умеет CA-набор**: настройка `verify_ssl` булева, httpx берёт certifi и корпоративный корень
   не видит. На стенде обходится `MM_VERIFY_SSL=false`, в бою понадобится путь к набору.
6. **Мина в тестах ТЭГ**: `tests/resilience/test_supervisor.py::test_module_is_executable` виснет навсегда
   у любого, у кого в корне есть рабочий `.env`.

## Как ведётся разработка
Агентный конвейер: spec → dev → test → review → гейты (G1–G6), зоны записи по ролям, отчёты в `reports/`.
Субагенты запускаются с моделью `opus`; оркестрация — на основной сессии. Каталог (`catalog.yaml`), `.github/`,
`.gitlab-ci.yml` и `deploy/` — зона оркестратора, агентам недоступны.
Особенности: `mutmut` на macOS требует `no_proxy='*'`; при обрыве субагента его работа в дереве сохраняется —
перезапускать с «продолжи с текущего дерева»; `uv run` в этой среде виснет, нужно звать `.venv/bin/…` напрямую.

## Безопасность — требует внимания

- Токен GitLab, выданный для настройки MCP, был передан в переписке — его тоже стоит перевыпустить.
