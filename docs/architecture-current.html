2. Поток подключения коннектора (direct-token)

Пример: пользователь подключает Jira через персональный токен
1
Пользователь открывает витрину коннекторов в Desktop
→
opencode CLI: GET /corp/catalog
→
Hub: GET /api/catalog (Bearer key)
2
UI рисует карточку Jira (mode: facade, auth: personal_token)
→
Пользователь вводит Jira PAT в поле «Токен»
3
UI: POST /corp/connect-token с паролем
→
opencode CLI: verify() — HTTP-запрос на Jira API
→
Jira: GET /rest/api/3/myself с заголовком Authorization: Bearer <PAT>
4
Verify OK (200 + account)
→
opencode CLI: POST /api/me/connections/jira/token на Hub
→
Hub шифрует токен (AES-GCM) → PostgreSQL
5
Hub отвечает status: connected
→
opencode CLI: регистрирует MCP-сервер http://localhost:8080/mcp/jira
→
UI показывает статус «Подключено»
Ключевой момент: verify выполняется из opencode CLI (на машине пользователя), а не из Hub. Hub только хранит зашифрованный токен и подставляет его в заголовки при проксировании MCP-запросов.

3. Поток MCP-вызова (проксирование через Hub)

Пример: ассистент вызывает инструмент jira_search
1
AI-модель возвращает tool_call: jira_search
→
opencode CLI отправляет JSON-RPC на MCP-сервер Jira
2
MCP-сервер Jira = http://localhost:8080/mcp/jira (Hub)
→
Hub: авторизация (Bearer access-token)
→
Hub: извлекает зашифрованный PAT из PostgreSQL
3
Hub: дешифрует PAT, подставляет в credential_headers
→
Hub: проксирует JSON-RPC на mcp-atlassian.../mcp
→
Jira MCP: выполняет jira_search с заголовком Authorization: Bearer <PAT>
4
Jira API отвечает данными
→
Hub: фильтрует инструменты по permission_groups
→
opencode CLI получает результат
→
AI-модель формирует ответ

4. Хранение секретов

🔑 Токены пользователя (PAT, пароли)

Где: PostgreSQL, таблица connections, колонка token

Как: AES-256-GCM, ключ HUB_ENCRYPTION_KEY (env)

Жизнь: до отключения пользователем

Доступ: только Hub-процесс

🎫 Access-токен Hub (API key)

Где: ~/.local/share/opencode/auth.json (права 0600)

Как: plaintext, но привязан к SSO-сессии

Жизнь: до выхода из SSO

Формат: sk-... (LiteLLM-совместимый)

🔒 Подпись JWT

Где: env HUB_SECRET_KEY

Как: HS256, срок жизни access-token

Назначение: подпись MCP-proxy-токенов

Ротация: вручную, с инвалидацией всех сессий

Важно: Пароли Exchange (NTLM) не кэшируются на диске. Hub передаёт их в HTTP-заголовках в каждом MCP-запросе, а локальный outlook-ews-mcp держит их в памяти только на время вызова. После ответа креды удаляются из ContextVar.

Сетевая схема продуктива:
Desktop → Caddy (8443/TLS) → Hub (8000) → MCP-серверы → Корпоративные системы
Все соединения внутри кластера — plain HTTP. Внешний трафик — только через Caddy с TLS. Корпоративный CA (tander-ca-bundle.pem) монтируется во все контейнеры.

6. Модель разрешений

Два уровня контроля
Уровень Где настраивается Что контролирует Пример
tool_filter catalog.yaml → permission_model.presets Какие инструменты доступны при preset readonly / readwrite Outlook: readonly = 22 инструмента, readwrite = все 56
header_groups catalog.yaml → permission_model.groups + permissions/{alias}.yaml Группы инструментов с default allow/ask/deny Jira: read = allow, write = ask, admin = deny
runtime ask Desktop UI (пользователь) Подтверждение перед каждым write-вызовом «Отправить письмо? [Да] [Нет]»
