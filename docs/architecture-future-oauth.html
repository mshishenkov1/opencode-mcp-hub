2. Поток OAuth-подключения (Authorization Code + PKCE)

Пример: пользователь подключает Jira через OAuth
1
Пользователь нажимает «Войти через Jira» в витрине
→
opencode CLI: POST /corp/connect-oauth {alias: "jira"}
→
Hub: генерирует PKCE code_verifier + state
2
Hub отвечает: {authorize_url, state, code_challenge}
→
Desktop открывает системный браузер по authorize_url
→
Jira: экран согласия «OpenCode запрашивает доступ»
3
Пользователь нажимает «Разрешить»
→
Jira redirect: opencode://oauth/callback?code=...&state=...
→
Desktop перехватывает deep link
4
Desktop: POST /corp/connect-oauth/callback {code, state}
→
Hub: проверяет state, обменивает code на access_token + refresh_token
→
Hub: шифрует токены (AES-GCM) → PostgreSQL
5
Hub: status: connected
→
opencode CLI: регистрирует MCP-сервер
→
UI: статус «Подключено через Jira SSO»
Преимущества OAuth над direct-token:
• Пользователь не вводит пароль/PAT — только соглашается в браузере
• Refresh-токен автоматически обновляет access-токен (нет истечения сессии)
• Scopes ограничивают доступ на стороне системы (принцип минимальных прав)
• Отзыв через систему (Jira admin → revoke), а не через Hub только
• Аудит-лог в системе показывает «доступ через OpenCode»

3. Унификация через Keycloak (Token Exchange)

Единый IdP: один логин — все системы
1
Desktop: SSO-вход через Keycloak (OIDC)
→
Keycloak: access_token (subject: user, realm: OpenCode)
2
Пользователь нажимает «Подключить Jira»
→
Hub: Token Exchange — меняет Keycloak-token на Jira-token
3
Keycloak → Jira: OIDC federation
→
Jira: выдаёт свой access_token (доверяет Keycloak)
→
Hub: хранит Jira-token (refresh не нужен — Keycloak переобменяет)
4
MCP-вызов: Hub подставляет Jira-token в заголовок
→
Jira выполняет запрос
Token Exchange (RFC 8693): Keycloak выступает посредником. Пользователь входит один раз (SSO), а Keycloak обменивает свой токен на системные — для Jira, Exchange, GitLab. Ни одна система не видит пароль пользователя, а Hub не хранит refresh-токены отдельных систем.

4. Сравнение: сейчас → будущее

Аспект Сейчас (direct-token) Будущее (OAuth + Keycloak)
Аутентификация PAT / пароль вручную OAuth Code + PKCE в браузере
Жизнь токена До ручного отключения / истечения PAT Refresh自动 обновляет access_token
Отзыв Только через Hub (удаление из БД) Через систему + через Hub
Scopes Все или ничего (preset readonly/readwrite) Granular scopes на стороне системы
SSO Нет (отдельный логин в каждую систему) Keycloak SSO → Token Exchange
MFA Нет Через Keycloak (TOTP, WebAuthn)
Аудит Только в Hub В Hub + в каждой системе (OAuth client_id)
Onboarding Инструкция: «создай PAT, вставь в поле» Кнопка «Войти» → браузер → готово
Outlook (Exchange) NTLM-пароль в заголовках OAuth2 (Azure AD / ADFS)
Хранение секретов AES-GCM: PAT / пароль в PostgreSQL AES-GCM: refresh_token (access_token обновляется)

5. План миграции

Фаза 1: OAuth broker в Hub

1. Реализовать auth_methods[].type: "oauth2" в каталоге

2. Добавить роуты /api/me/connections/{alias}/oauth

3. PKCE + state + callback через deep link

4. Хранение refresh_token в PostgreSQL

5. Фоновый refresh access_token

Зависит от: OAuth-приложения в системах

Фаза 2: Keycloak

1. Развёртывание Keycloak в корпоративном кластере

2. Realm «OpenCode», клиент opencode-desktop

3. Federation с Jira/Confluence (OIDC)

4. Trust с ADFS (Exchange)

5. Token Exchange (RFC 8693)

Зависит от: админы Jira/Exchange

Фаза 3: Sunset direct-token

1. Оба метода работают параллельно

2. UI предлагает OAuth первым, direct-token — «расширенные»

3. Миграция пользователей: кнопка «Переподключить через SSO»

4. После миграции — отключение direct-token в каталоге

Зависит от: 100% миграция пользователей
